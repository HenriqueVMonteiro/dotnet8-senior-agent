- **Nunca use `async void` fora de event handler** — sem `Task` de retorno não existe canal para a falha: o `try/catch` do chamador não vê a exceção e ela sobe para o handler de último recurso, derrubando o processo. Em .NET: troque por `async Task` e faça `await`; em `IHostedService`/handler de fila, `async void` transforma erro de negócio em crash do host. {EVIDENCIA: `try/catch` do chamador não capturou a exceção de `async void` e capturou a de `async Task`, mesma exceção e mesmo delay — `validacao/repro/F4-linguagem-2`}
- **Nunca use `.Result` ou `.Wait()` onde exista `SynchronizationContext` de fila única** — a continuação precisa da mesma thread que está bloqueada esperando o resultado, e as duas se esperam para sempre. Em .NET: sob contexto de uma thread, `TrabalhoAsync().Result` não concluiu e `await TrabalhoAsync()` concluiu; `ConfigureAwait(false)` mitiga o sintoma, mas a correção é `await` até o topo. {EVIDENCIA: `.Result` não concluiu em 3 s (deadlock) e `await` devolveu 42 no mesmo contexto — `validacao/repro/F4-linguagem-2`}
- **Padrão com quantificador aninhado sofre backtracking catastrófico; use `RegexOptions.NonBacktracking` ou reescreva** — o motor clássico explora exponencialmente as partições possíveis quando o padrão é ambíguo e a entrada não casa. Em .NET: `^(a+)+$` contra 31 caracteres estourou timeout de 2 s; o mesmo padrão com `NonBacktracking` respondeu em 137 ms. Timeout limita o dano, não corrige a causa. {EVIDENCIA: TIMEOUT em 2111 ms contra 137 ms com `NonBacktracking`, mesmo padrão e mesma entrada — `validacao/repro/F4-linguagem-2`}
- **Boxing de `int` custa 24 bytes por caixa em x64; e microbenchmark sem barreira mede o otimizador** — cada caixa é um objeto no heap com cabeçalho; se o resultado não escapa, o JIT pode eliminar a alocação e o benchmark mente. Em .NET: guarde o resultado numa coleção viva antes de medir com `GC.GetAllocatedBytesForCurrentThread`. {EVIDENCIA: 2.400.000 bytes para 100.000 caixas = 24,0 bytes/caixa com barreira; o mesmo laço com apenas `GC.KeepAlive` rendeu 23.976 bytes, 1% do real — `validacao/repro/F4-linguagem-2`}
- **Enumerar o mesmo `IEnumerable` mais de uma vez reexecuta a fonte inteira** — a query é diferida; cada operador terminal reabre o iterador. Em .NET: `Count()`, `Sum()` e `ToList()` sobre a mesma query executaram o iterador **3 vezes**; materializar com `ToList()` antes reduziu para **1**. - **Struct mutável perde mutação através do indexador de `List<T>`, mas não através do índice de array** — `List<T>` devolve cópia, array devolve referência. A armadilha é da coleção com indexador, não de "struct em coleção" em geral. Em .NET: `lista[0].Incrementar()` deixou `Valor=0`, enquanto `array[0].Incrementar()` deixou `Valor=1`. Prefira struct imutável a trocar para classe por reflexo. {EVIDENCIA: 0 via `List<T>` contra 1 via array, mesmo struct e mesmo método — `validacao/repro/F4-runtime-linguagem`}

## Correção

- **Garanta limpeza determinística com using ou finally, inclusive para iteradores e enumeradores explícitos** — `using` é açúcar sintático para um `try/finally` cujo `finally` chama `Dispose` no objeto, incluindo a checagem implícita de null; isso garante que o `Dispose` execute mesmo diante de uma exceção lançada entre a criação do recurso e o fim do escopo, algo que uma chamada manual ao final do bloco não garante. Em .NET: envolver `SqlConnection`, `SqlCommand` e `SqlDataReader` (ou o próprio `DbContext` do EF Core 8, quando criado manualmente fora do DI) em `using`/`using var` assegura liberação determinística mesmo quando a query falha, evitando vazamento de conexões no pool do SQL Server. [CS12-03-A-23, CS12-04-A-13, CS12-04-A-15, CS12-04-A-7, CS12-04-A-8, CS12-04-B-7 +2] {ACORDO 3 / media}
  - Limite: não se aplica a objetos gerenciados pelo contêiner de DI com ciclo de vida próprio (ex.: um `DbContext` com escopo por requisição em ASP.NET Core), cujo `Dispose` já é chamado automaticamente pelo framework ao final do escopo.
- **Valide anulabilidade em runtime e use ! somente depois de garantir um valor não nulo** — Nullable reference types são puramente uma construção de compilação — geram avisos, não impedem a atribuição de `null` em tempo de execução, e não existe diferença de runtime entre `string` e `string?`. Em .NET: Uma propriedade declarada como `string` (não-nulável) em uma classe de configuração de um serviço .NET 8, populada via desserialização JSON (`System.Text.Json`) de uma configuração externa com o campo ausente, recebe `null` em runtime sem qualquer erro de compilação ou exceção imediata; o `NullReferenceException` só ocorre no primeiro acesso a um membro dessa referência, longe do ponto onde o dado inválido entrou no sistema. [CS12-04-A-22, CS12-04-A-23, CS12-04-B-12, CS12-04-C-22, CS12-04-C-23] {ACORDO 3 / media}
  - Limite: Não se aplica a value types nuláveis (`Nullable<T>`), que introduzem uma estrutura de runtime real (`HasValue`/`Value`) e não dependem de disciplina de compilação.
- **Não exponha nem persista nomes de elementos de tupla como parte estável de contratos externos** — Os nomes de elementos de tupla existem só no código-fonte e nos metadados do compilador; em tempo de execução, o tipo real é `ValueTuple<T1,T2,...>` com campos `Item1`, `Item2`, etc., e serializadores/reflexão genéricos não têm acesso a esses nomes declarados. Em .NET: Um endpoint minimal API do .NET 8 que retorna diretamente uma tupla nomeada `(string Nome, int Idade)` é serializado pelo `System.Text.Json` como `{"Item1":"...","Item2":...}` em vez de `{"Nome":"...","Idade":...}`, quebrando o contrato esperado pelo cliente da API sem qualquer erro de compilação. [CS12-01-A-68, CS12-01-C-15, CS12-04-A-28, CS12-04-B-15, CS12-04-C-28] {ACORDO 3 / media}
  - Limite: Não se aplica a `record`, cujas propriedades são membros reais do tipo gerado e são serializadas pelo nome declarado.
- **Considere a execução adiada do LINQ e copie variáveis de iteração antes de capturá-las** — Um operador padrão devolve um objeto decorador cujo `GetEnumerator`/`MoveNext` é que dispara a avaliação da lambda por elemento; construir a consulta apenas monta essa cadeia de objetos, sem chamar `MoveNext` em nada. Em .NET: Em C# 12/.NET 8, `var q = numbers.Select(n => n * 10); numbers.Add(2);` inclui o elemento adicionado depois, porque o `foreach` sobre `q` é o primeiro ponto em que `numbers` é de fato percorrida. [CS12-08-A-2, CS12-08-A-5, CS12-08-B-1, CS12-08-C-3] {ACORDO 3 / alta}
  - Limite: Operadores de elemento/escalar (`First`, `Count`, `Sum`...) e os operadores de conversão `ToArray`, `ToList`, `ToDictionary`, `ToLookup`, `ToHashSet` executam imediatamente, pois seus tipos de retorno não têm como representar execução adiada.
- **Declare predicados reutilizáveis de IQueryable como Expression** — `Func<T,bool>` é IL comum compilado pelo JIT, sem nenhuma representação inspecionável em tempo de execução; `Expression<Func<T,bool>>` é uma árvore de dados que o compilador gera a partir da mesma sintaxe de lambda quando o tipo de destino pede isso, e é essa árvore que um provedor como o EF Core percorre para montar o SQL — sem ela, não há nada para traduzir. Em .NET: Em C# 12, `Func<Product,bool> p1 = x => !x.Discontinued;` usado em `dbContext.Products.Where(p1)` não tem sobrecarga de `Queryable` compatível e força resolução local, enquanto `Expression<Func<Product,bool>> p2 = x => !x.Discontinued;` usado em `dbContext.Products.Where(p2)` compila contra `Queryable.Where` e traduz para SQL Server. [CS12-08-A-13, CS12-08-A-14, CS12-08-B-19, CS12-08-C-16] {ACORDO 3 / alta}
  - Limite: Não importa para consultas 100% locais (`IEnumerable<T>`), onde só `Func<>` é aceito e não há tradução envolvida.
- **Trate consultas adiadas como definições reexecutáveis: revise capturas e materialize resultados remotos antes de reutilizá-los** — A lambda captura a variável em si (por referência ao slot de armazenamento), não uma cópia do valor; o corpo da lambda só lê essa variável quando o delegate é de fato invocado, ou seja, durante a enumeração. Em .NET: Em C# 12, `int factor = 10; var q = numbers.Select(n => n * factor); factor = 20;` produz resultados multiplicados por 20, não por 10, porque a leitura de `factor` ocorre no `foreach`, não na declaração. [CS12-08-A-4, CS12-08-B-2, CS12-08-B-5, CS12-08-C-1] {ACORDO 3 / alta}
  - Limite: Não se aplica a parâmetros passados por valor para métodos comuns (não lambdas), nem a variáveis locais que nenhum closure captura.
- **Instancie cada elemento de arrays de referências, mesmo sob análise nullable** — O compilador não rastreia se os elementos individuais de um array foram efetivamente atribuídos após a criação; um array recém-criado de um tipo referência não-nulável tem todos os elementos `null` por padrão, sem gerar aviso algum ao acessá-los. Em .NET: Um array de entidades (`Cliente[] clientes = new Cliente[10];`) alocado antes de popular via um loop de leitura de um `SqlDataReader` no .NET 8, acessado antes do loop terminar de preencher todas as posições, lança `NullReferenceException` em runtime numa linha que o compilador nunca sinalizou com CS8602. [CS12-02-A-38, CS12-02-A-46, CS12-02-C-48, CS12-04-B-13] {ACORDO 3 / alta}
  - Limite: Não se aplica a coleções inicializadas via inicializador de coleção ou LINQ que garante todos os elementos populados antes do primeiro acesso.
- **Compare classes e tipos anônimos por conteúdo com a implementação apropriada de Equals** — para tipos referência a igualdade padrão é de referência, não de valor; dois objetos com todos os campos iguais são diferentes porque são endereços diferentes. Em .NET: `Distinct()`, `Contains()` e `GroupBy()` em memória sobre uma `List<Cliente>` materializada duas vezes do SQL Server não deduplicam nada, porque cada materialização cria instâncias novas. [CS12-02-C-8, CS12-04-B-14, CS12-04-C-27] {ACORDO 2 / alta}
  - Limite: string sobrescreve os operadores e compara por conteúdo; tipos que sobrecarregam `==` ou sobrescrevem Equals também fogem da regra, e tipos-valor já comparam por valor.
- **Use & e | para lógica bool? de três estados** — quando aplicados a `bool?`, os operadores `&` e `|` tratam `null` como "desconhecido" e seguem a álgebra de três valores (ex.: `null | true` é `true`, porque o resultado seria `true` independentemente de o lado desconhecido ser verdadeiro ou falso); essa é exatamente a mesma semântica de `AND`/`OR` do SQL Server com `NULL`. Em .NET: montar uma condição composta em C# que deve corresponder byte a byte ao resultado de um `WHERE (a AND b)` no SQL Server, onde `a`/`b` podem ser `NULL`, exige usar `&`/`|` sobre `bool?` em vez de `&&`/`||` (que não têm essa forma levantada de três valores da mesma maneira) para obter paridade de comportamento entre o filtro calculado em memória e o filtro equivalente executado no banco. [CS12-04-A-20, CS12-04-B-11, CS12-04-C-20] {ACORDO 3 / alta}
  - Limite: aplica-se apenas ao tipo `bool?`; para tipos numéricos anuláveis, `&`/`|` bit a bit seguem a regra geral de propagação de null (ver item sobre operadores aritméticos), não a lógica de três valores.
- **Evite dynamic ao acessar resultados de consultas ou invocar LINQ e extension methods** — uma expressão sobre um valor `dynamic` é empacotada pelo compilador para ser resolvida em runtime pelo DLR; se o membro acessado não existir no tipo real do objeto naquele momento, o runtime lança `RuntimeBinderException` — o equivalente, mas adiado, de um erro de compilação por membro inexistente. Em .NET: consumir como `dynamic` o resultado de uma projeção EF Core 8/JSON gerado por `FOR JSON`/`OPENJSON` do SQL Server (em vez de mapear para um DTO tipado) faz qualquer erro de digitação em um nome de propriedade (ex.: `linha.Nome` quando a coluna real se chama `NomeCliente`) passar despercebido até a execução daquele trecho específico, possivelmente só em produção, em vez de ser pego no build. [CS12-04-A-36, CS12-04-A-37, CS12-04-C-37] {ACORDO 2 / alta}
  - Limite: não se aplica quando o objeto implementa `IDynamicMetaObjectProvider` com binding customizado (ex.: um `DynamicObject` que intercepta e trata qualquer nome de membro), caso em que não existe "nome errado" a ser detectado.
- **Preserve IQueryable escolhendo operadores pelo tipo estático da fonte e não o interrompa com IEnumerable** — `Where`/`Select`/etc. existem em duas sobrecargas — uma recebendo `Func<T,bool>` para `IEnumerable<T>`, outra recebendo `Expression<Func<T,bool>>` para `IQueryable<T>` — e a resolução de sobrecarga do C# escolhe a mais específica; para um `DbSet<T>` (que implementa ambas as interfaces), a sobrecarga de `Queryable` vence, forçando a lambda a virar árvore de expressão em vez de IL comum. Em .NET: Em C# 12 com EF Core 8, `dbContext.Customers.Where(c => c.Name.Contains("a"))` gera uma `Expression<Func<Customer,bool>>` que o provedor traduz para `CHARINDEX` em T-SQL; a mesma sintaxe sobre um `List<Customer>` gera um `Func<Customer,bool>` comum executado em IL. [CS12-08-A-6, CS12-08-A-8, CS12-08-B-6] {ACORDO 2 / alta}
  - Limite: Não se aplica quando a fonte implementa somente `IEnumerable<T>` (a sobrecarga de `Queryable` nunca fica disponível) nem quando o tipo é forçado explicitamente via `AsEnumerable`/`AsQueryable`.
- **Materialize resultados dependentes antes de descartar seu DbContext ou JsonDocument** — A consulta é executada de forma adiada — a instrução SQL só é gerada e enviada quando alguém enumera o resultado — mas a conexão/contexto necessário para essa execução já foi fechado e liberado no `Dispose`, então não sobra nada vivo para atender à enumeração posterior. Em .NET: Em EF Core 8, `IQueryable<Customer> GetCustomers(string p) { using var ctx = new NutshellContext(); return ctx.Customers.Where(c => c.Name.StartsWith(p)); }` seguido de `foreach (var c in GetCustomers("a"))` no chamador falha, porque o `foreach` é o primeiro ponto de enumeração e o `ctx` já foi descartado ao sair do método. [CS12-08-A-19, CS12-11-A-2, CS12-11-B-5] {ACORDO 2 / alta}
  - Limite: Não é um problema se o método materializa o resultado antes de retornar (`.ToList()`/`.ToArray()` dentro do `using`), pois aí a query já rodou por completo enquanto o contexto ainda estava vivo.
- **Não tente obter polimorfismo reimplementando na subclasse um membro default de interface** — A implementação padrão vive na interface, não no tipo: para alcançá-la é preciso que a referência seja da interface. Uma referência do tipo concreto, que não redeclara o membro, não o enxerga. Em .NET: Em .NET 8, `new Logger().Log("x")` não compila se `Log` só existe como padrão em `ILogger`; é preciso `((ILogger)new Logger()).Log("x")`. [CS12-01-A-27, CS12-01-C-24, CS12-03-A-81] {ACORDO 2 / alta}
  - Limite: Tipos que reimplementam o membro explicitamente não têm o problema.
- **Aplique padrões de lista somente a coleções contáveis e indexáveis, materializando outras sequências antes** — list patterns exigem que o tipo alvo seja simultaneamente "contável" (tenha uma propriedade `Count` ou `Length`) e "indexável" (tenha um indexador `int` ou `System.Index`); uma sequência ainda não enumerada, como um `IEnumerable<T>`/`IQueryable<T>` bruto, não expõe nenhuma das duas capacidades até ser materializada. Em .NET: uma consulta EF Core 8 armazenada em uma variável `IQueryable<T>` (ainda não convertida com `ToList()`/`ToArray()`) não pode ser testada diretamente com `resultado is [primeiro, .. , ultimo]`; é preciso materializar a query primeiro, o que também tem o efeito colateral de disparar a execução contra o SQL Server naquele ponto. [CS12-01-A-36, CS12-04-A-32, CS12-04-C-36] {ACORDO 2 / alta}
  - Limite: não se aplica a arrays, `List<T>`, `Span<T>` e qualquer outro tipo já contável e indexável, que suportam list patterns diretamente sem materialização adicional.
- **Faça cópias profundas quando objetos mutáveis precisarem ser independentes; caso contrário, trate-os como compartilhados, inclusive após with** — Para tipo por referência a variável contém uma referência, não o objeto; passar ou atribuir copia a referência, de modo que as duas variáveis endereçam o mesmo bloco no heap e qualquer mutação de estado é vista pelos dois lados. Em .NET: Em .NET 8, um método que recebe `List<T>` ou `StringBuilder` e chama `Clear()` ou `Append()` altera o objeto do chamador; devolver `IReadOnlyList<T>` ou copiar na entrada é o que impede o efeito colateral. [CS12-02-A-7, CS12-04-A-29, CS12-07-B-7] {ACORDO 2 / media}
  - Limite: Não se aplica a tipos imutáveis, como string, onde não existe mutação de estado observável.
- **Inicialize explicitamente elementos de arrays de referências, inclusive arrays internos** — O array em si é sempre um objeto de tipo por referência, independentemente do tipo do elemento; logo o valor padrão de uma variável ou campo de array é null, e não um array de comprimento zero. Em .NET: Em .NET 8, `int[] a = null;` é atribuição legal, e um campo `int[] Itens;` de uma entidade recém-construída vale null; qualquer leitura de `.Length` ou `foreach` sobre ele lança antes de qualquer validação de negócio. [CS12-02-A-39, CS12-02-B-23, CS12-02-C-49] {ACORDO 3 / alta}
  - Limite: Nenhum conhecido; vale para arrays de qualquer tipo de elemento e qualquer dimensão.
- **Implemente igualdade estrutural explícita para arrays e coleções contidos em records** — A igualdade padrão gerada para records compara campos e propriedades automáticas membro a membro; campos de tipos referência sem semântica de valor (arrays, `List<T>`) são comparados por referência, não pelo conteúdo, então a comparação estrutural do record quebra silenciosamente nesses campos. Em .NET: Um `record` usado como DTO de comparação de snapshot (ex.: para detectar mudanças antes de um `SaveChanges` no EF Core 8) que contém uma propriedade `List<ItemDto> Itens` considera dois snapshots com os mesmos itens, mas listas diferentes, como diferentes (`Equals` retorna `false`), disparando updates desnecessários. [CS12-04-A-30, CS12-04-B-16, CS12-04-C-31] {ACORDO 3 / media}
  - Limite: Não se aplica a records cujos campos/propriedades são todos tipos de valor, `string`, ou outros records/tipos com igualdade estrutural própria.
- **Defina e verifique explicitamente o overflow de cada operação integral, inclusive em agregações** — Por padrão o overflow integral não é verificado em tempo de execução: a operação é feita e os bits significativos que não caberiam no tipo são descartados, produzindo giro do valor; decrementar int.MinValue devolve int.MaxValue sem qualquer sinal de erro. Em .NET: Em .NET 8, somar uma coluna `int` de muitas linhas num acumulador `int` pode virar negativo silenciosamente; usar `long` ou envolver a soma em `checked` transforma o mesmo caso em OverflowException. [CS12-01-C-4, CS12-02-A-19, CS12-02-A-20] {ACORDO 2 / media}
  - Limite: Não se aplica a expressões cujos limites você consegue provar dentro do domínio do tipo.
- **Aplique ?. ao primeiro operando possivelmente nulo e propague a anulabilidade pela cadeia sem repeti-lo desnecessariamente** — ao encontrar nulo o operador curto-circuita o resto da expressão inteira, então um único `?.` no ponto certo já protege toda a cadeia à direita; repetir depois dele é ruído. Em .NET: em .NET 8, `sb?.ToString().ToUpper()` avalia para null sem erro mesmo com ponto comum nas chamadas seguintes; `x?.y?.z` só precisa do segundo `?.` porque `x.y` também pode ser nulo. [CS12-02-A-64, CS12-02-B-17, CS12-02-C-35] {ACORDO 3 / media}
  - Limite: o curto-circuito faz a expressão inteira devolver nulo, então a expressão final tem de aceitar nulo — `int length = sb?.ToString().Length;` não compila, exige `int?`; e um `?.` a menos onde havia nulo real volta a lançar.
- **Valide argumentos antes de criar e retornar um iterador** — O compilador transforma um método com `yield return` em uma classe de estado; chamar o método apenas instancia essa classe — nenhuma linha do corpo original executa até o primeiro `MoveNext()`, chamado tipicamente pelo primeiro `foreach` ou enumeração explícita. Em .NET: `IEnumerable<Row> Query(int pageSize) { if (pageSize <= 0) throw new ArgumentException(...); ... yield return ...; }` não lança a exceção na chamada `Query(-1)`; ela só é lançada quando alguém começa a enumerar o resultado (`foreach` ou `.ToList()`), potencialmente longe do ponto de chamada original. [CS12-04-A-14, CS12-04-B-6, CS12-04-C-14] {ACORDO 3 / media}
  - Limite: Não se aplica a métodos comuns (sem `yield`) nem a métodos que retornam `IEnumerable<T>` materializando eagerly (ex.: retornando uma `List<T>` já pronta em vez de usar `yield return`).
- **Restrinja T antes de usar membros estáticos abstratos ou tratá-lo como um tipo específico** — Membros estáticos virtuais/abstratos de interface (recurso usado por `INumber<T>` e interfaces de operadores em `System.Numerics`, .NET 7+) só ficam acessíveis através de um parâmetro de tipo quando esse parâmetro carrega a restrição de interface correspondente; sem a restrição, o compilador não sabe que `T` implementa aqueles membros, mesmo que toda instanciação concreta pretendida de fato os implemente. Em .NET: `T Sum<T>(params T[] numbers) where T : INumber<T> { T total = T.Zero; foreach (var n in numbers) total += n; return total; }` compila e funciona para `int`, `double`, `decimal` em .NET 8; remover o `where T : INumber<T>` faz `T.Zero` e `total += n` falharem na compilação, mesmo chamando o método só com tipos numéricos. [CS12-03-A-69, CS12-03-A-71, CS12-04-C-41] {ACORDO 2 / media}
  - Limite: Não se aplica quando o código já opera sobre um tipo concreto (não genérico) — ali os operadores estáticos do tipo funcionam diretamente, sem qualquer restrição necessária; a exigência é exclusiva de contexto genérico.
- **Use deslocamento à direita lógico, sem sinal, para padrões de bits** — O operador de deslocamento à direita comum replica o bit de mais alta ordem ao operar sobre inteiros com sinal, para preservar o sinal do número; isso preenche as posições liberadas com uns quando o valor é negativo, enquanto o operador sem sinal preenche com zeros. Em .NET: Em C# 12, `int.MinValue >>> 1` devolve 0x40000000, e `int.MinValue >> 1` devolve um valor negativo; misturar hash de objeto, que pode ser negativo, com `>>` produz máscaras contaminadas por uns. [CS12-02-A-24, CS12-02-B-47, CS12-02-C-75] {ACORDO 3 / alta}
  - Limite: Não se aplica quando o deslocamento é usado como divisão por potência de dois com sinal, onde a replicação é o comportamento correto.
- **Capture o retorno de operações que não alteram a instância** — Uma expressão só é statement válido se puder mudar estado, mas o compilador aceita a chamada sem consumir o resultado; quando o método é puro, o único efeito estava no valor retornado, então descartá-lo torna a linha equivalente a nada. [CS12-05-A-1, CS12-05-A-2] {ACORDO 1 / media}
  - Limite: só se manifesta quando o recurso de C# 12 usado depende de tipo novo do BCL; sintaxe puramente estrutural pode compilar em runtimes mais antigos se LangVersion for elevado manualmente.
- **Reprojete antes de `into` as variáveis que continuarão necessárias** — O compilador traduz uma consulta com `into` numa cadeia sequencial de operadores fluentes onde cada estágio seguinte só recebe como parâmetro de entrada o que o `select` anterior devolveu; como a lambda do próximo `Where`/`OrderBy` só enxerga o parâmetro desse estágio (o resultado da projeção), qualquer identificador de uma lambda anterior já saiu de escopo léxico, exatamente como uma variável local que deixou de existir. Em .NET: Em C# 12, `from n1 in names select n1.ToUpper() into n2 where n1.Contains("x") select n2;` não compila com erro de nome inexistente no contexto atual, porque a tradução equivalente é `names.Select(n1 => n1.ToUpper()).Where(n2 => n1.Contains("x"))`, onde o segundo lambda não tem acesso ao `n1` do primeiro. [CS12-08-A-29, CS12-08-C-14] {ACORDO 2 / alta}
  - Limite: Não se aplica antes de qualquer `into` (as cláusulas anteriores compartilham escopo normalmente) nem quando a variável necessária é reprojetada dentro do `select` que antecede o `into` (por exemplo, via tipo anônimo contendo ambos os valores).
- **Verifique a tradução SQL de operadores e extensões próprias usados em `IQueryable`** — Como IQueryable<T> herda de IEnumerable<T>, se o método seguinte na cadeia só tiver overload aceitando IEnumerable<T> (e não IQueryable<T>), a resolução de sobrecarga do C# liga a chamada ao operador local de Enumerable, e a partir dali a query deixa de ser uma árvore de expressão e passa a rodar em memória no processo .NET. Em .NET: Em EF Core 8, encadear uma extensão local (que só aceita `IEnumerable<string>`) depois de `.Select()`/`.OrderBy()` de um DbSet força os operadores seguintes a executar no cliente; tudo que veio antes é trazido para a memória do processo antes de continuar, mesmo que sintaticamente pareça uma única cadeia fluente. [CS12-08-C-4, CS12-09-A-3] {ACORDO 2 / media}
  - Limite: Não se aplica quando o método seguinte tem overload aceitando IQueryable<T> (a cadeia continua interpretada); o padrão recomendado é colocar operadores locais só na ponta externa da cadeia, depois de todos os operadores que ainda podem ser traduzidos.
- **Preserve o tipo ordenado e refine a ordenação com vírgula ou `ThenBy`** — Cada cláusula orderby autônoma (não encadeada com vírgula) é traduzida pelo compilador para uma chamada independente a OrderBy, que resorteia a sequência do zero a partir da chave dada; ThenBy é o único operador que refina uma ordenação já existente sem descartá-la, e o compilador só o usa quando as chaves aparecem na mesma cláusula orderby. Em .NET: `orderby s.Length` seguido de `orderby s[1]` em outra linha ordena apenas por `s[1]`, descartando a ordenação por Length; contra EF Core, a query final emite ORDER BY somente pela última chave. [CS12-09-A-5, CS12-09-C-18] {ACORDO 2 / alta}
  - Limite: nenhum conhecido; sempre verdadeiro em C# 12 para query syntax.
- **Converta elementos numéricos por projeção, não com `Cast` ou `OfType`** — Cast<TSource> implementa a conversão testando `(TSource)element` sobre um `object`, que o CLR trata como operação de unboxing (exige correspondência exata de tipo em tempo de execução), não como a conversão numérica implícita/explícita que o operador de cast do C# faria sobre valores tipados diretamente. Em .NET: Em C# 12/.NET 8, `new int[] { 1, 2, 3 }.Cast<long>()` lança InvalidCastException ao ser enumerado, mesmo que `(long)i` para um `int i` local compile e funcione normalmente como conversão numérica implícita. [CS12-09-B-6, CS12-09-C-22] {ACORDO 2 / alta}
  - Limite: Não se aplica a conversões de referência/downcasting entre tipos referência compatíveis (o cenário para o qual Cast foi desenhado) nem quando se usa Select com um cast explícito por elemento.
## Performance

- **Marque lambdas e funções locais sem captura como `static`, especialmente em hot paths** — `static` é apenas uma checagem do compilador que barra o uso de qualquer variável, campo de instância ou `this` externo dentro da lambda; quando não há captura, o compilador já reaproveita uma única instância de delegate em cache durante toda a vida da aplicação — com ou sem a palavra-chave. Em .NET: `Func<int,int> f = static n => n * 2;` falha em compilar se depois alguém adicionar referência a uma variável local `factor`; sem `static`, esse mesmo erro de acoplamento passaria despercebido até o code review. [CS12-01-A-19, CS12-01-C-26, CS12-02-A-3, CS12-04-B-5, CS12-04-C-4] {ACORDO 3 / media}
  - Limite: Não se aplica a métodos locais/lambdas que legitimamente precisam de estado externo; forçar `static` nesses casos exige refatorar para passar o estado como parâmetro.
- **Calcule agregados invariantes fora de predicados locais** — Uma subconsulta é reavaliada toda vez que a lambda que a contém é invocada; num operador local como `Where`, essa lambda roda uma vez por elemento da sequência externa, então uma subconsulta não correlacionada (que não referencia a variável de alcance externa) acaba sendo recomputada do zero em cada uma dessas N chamadas, gerando custo O(N × custo-da-subconsulta) em vez de O(N + custo-da-subconsulta). Em .NET: Em C# 12, `names.Where(n => n.Length == names.Min(n2 => n2.Length))` percorre `names` inteiro dentro de `Min` para cada elemento de `names` na cláusula `Where` — para uma lista local de N itens isso é O(N²); calcular `int shortest = names.Min(n => n.Length);` uma vez fora do `Where` reduz para O(N). [CS12-08-A-11, CS12-08-B-17] {ACORDO 2 / alta}
  - Limite: Não se aplica a subconsultas correlacionadas (que referenciam a variável de alcance externa), pois essas precisam mesmo ser recalculadas por elemento; também não é um problema relevante em consultas interpretadas pelo EF Core, que compõe tudo numa única instrução SQL processada como unidade pelo servidor.
- **Declare record structs imutáveis como readonly** — A regra de geração diverge entre as duas formas: no record de classe as propriedades geradas são init-only, enquanto no record struct elas nascem graváveis, a menos que a declaração seja prefixada com `readonly`. Em .NET: `record struct Ponto(int X, int Y);` em .NET 8 permite `p.X = 9;` depois de construído; `readonly record struct Ponto(int X, int Y);` rejeita a atribuição em compilação. [CS12-01-A-22, CS12-01-C-9] {ACORDO 2 / alta}
  - Limite: Casos em que a mutação após construção é intencional.
- **Trate operações `*With` como mutações e agrupe alterações de coleções imutáveis** — Esses métodos de `HashSet<T>` têm retorno `void` e alteram o conjunto original destrutivamente, diferindo dos operadores LINQ de nome parecido (`Union`, `Intersect`, `Except`), que são não destrutivos e retornam uma nova sequência. Em .NET: Código que faz `var overlap = permissionsA; overlap.IntersectWith(permissionsB);` pensando estar calculando uma interseção temporária para uma checagem pontual, mas o `HashSet<string>` `permissionsA` original é destruído no processo, quebrando qualquer verificação subsequente que dependesse do conjunto completo original. [CS12-07-B-11, CS12-07-B-9] {ACORDO 1 / alta}
  - Limite: Não se aplica quando a intenção é realmente mutar o conjunto original, ou quando se cria uma cópia (`new HashSet<T>(original)`) antes de chamar o método destrutivo.
- **Desative o tracking em consultas somente leitura** — O rastreamento normal obriga o `DbContext` a manter, para cada entidade materializada, uma cópia snapshot dos valores originais (para comparar depois e detectar mudanças) e a registrá-la no cache de identidade por chave primária; desligando o rastreamento, o EF Core pula ambos os passos, reduzindo alocação de memória e trabalho de CPU por linha materializada. Em .NET: Em EF Core 8, `dbContext.Customers.AsNoTracking().Where(...)` usado num endpoint de leitura evita o custo de snapshot por entidade retornada; chamar `dbContext.SaveChanges()` depois não gravará nenhuma alteração feita nessas entidades, porque elas nunca entraram no `ChangeTracker`. [CS12-08-A-17, CS12-08-B-10] {ACORDO 2 / alta}
  - Limite: Não use em entidades que você pretende modificar e persistir com `SaveChanges` na mesma unidade de trabalho — sem rastreamento, alterações feitas nas propriedades não são detectadas nem gravadas.
- **Declare value objects como readonly record struct** — quando um `record struct` é declarado com uma lista de parâmetros, o compilador gera propriedades graváveis (não somente-init) por padrão; só ao prefixar a declaração com `readonly` o compilador gera propriedades somente-leitura, impedindo mutação da struct depois de criada. Em .NET: uma projeção leve de resultado de query EF Core 8 modelada como `record struct` simples e usada como chave em um `Dictionary<TChave, TValor>` para cache em memória pode ser mutada em algum ponto do código depois de já ter sido usada para calcular um hash/posição no dicionário, corrompendo silenciosamente a estrutura interna do dicionário (a chave "muda de identidade" sem que o dicionário seja notificado); usar `readonly record struct` elimina essa classe de bug pela raiz. [CS12-04-A-31, CS12-04-C-33] {ACORDO 2 / media}
  - Limite: não se aplica quando o `record struct` é declarado sem lista de parâmetros e com propriedades explicitamente somente-leitura escritas à mão, que já seriam imutáveis independentemente do `readonly` na declaração do tipo.
- **Execute a contagem no banco antes de materializar resultados** — `Count()` sobre `IQueryable<T>` resolve para `Queryable.Count`, traduzido em `SELECT COUNT(*)` executado no servidor; `.ToList().Count` primeiro transfere todas as linhas e colunas projetadas para o cliente e só então conta em memória. Em .NET: Em EF Core 8, `dbContext.Customers.Count()` gera `SELECT COUNT(*) FROM [Customer]`; `dbContext.Customers.ToList().Count` transfere toda a tabela `Customer` pela rede antes de retornar o mesmo número. [CS12-08-B-14] {ACORDO 1 / alta}
  - Limite: Não se aplica se a lista já foi materializada por outro motivo anterior na mesma unidade de trabalho e a contagem é só reaproveitada, sem nova consulta.
- **Use BitArray para grandes conjuntos de flags** — Um valor booleano precisa logicamente de um bit, mas o runtime usa um byte porque essa é a menor porção que ele e o processador manipulam com eficiência; num array esse arredondamento se repete por elemento, gastando oito vezes o necessário. Em .NET: Em .NET 8, `bool[10_000_000]` ocupa cerca de 10 MB, enquanto `BitArray` do namespace System.Collections guarda o mesmo conjunto em cerca de 1,25 MB. [CS12-02-A-28] {ACORDO 1 / alta}
  - Limite: Não se aplica a poucos flags, onde o acesso direto ao byte é mais rápido que a máscara de bits.
- **Monte texto em laços com StringBuilder** — string é uma sequência imutável de caracteres, então o operador de concatenação não pode estender o objeto existente: ele aloca uma nova string e copia os dois lados; repetir isso a cada iteração torna o custo total quadrático no tamanho final. Em .NET: Em .NET 8, montar um script T-SQL ou um CSV com `s += linha` dentro de um laço de milhares de iterações aloca e copia o acumulado inteiro por iteração, enquanto `StringBuilder` do namespace System.Text mantém um buffer que cresce por amortização. [CS12-02-A-31] {ACORDO 1 / alta}
  - Limite: Não se aplica a poucas concatenações de tamanho conhecido, onde o compilador pode resolver ou o custo é irrelevante.
- **Não escolha struct apenas para presumir alocação fora do heap** — instâncias de tipo de valor vivem onde a variável foi declarada — declarada como campo de uma classe ou como elemento de array, a instância mora no heap junto com o objeto que a contém. Em .NET: trocar um DTO de `class` para `struct` num pipeline .NET 8 que o guarda em `List<T>` ou como campo não tira nada do heap; o ganho real é eliminar o cabeçalho de objeto e a referência por elemento, não sair do heap. [CS12-02-B-20] {ACORDO 1 / alta}
  - Limite: variáveis locais e parâmetros de fato ficam na pilha e não geram trabalho para o GC.
- **Chame diretamente métodos implementados por structs para evitar boxing e despacho inesperado** — Chamar um membro implicitamente implementado diretamente na variável de tipo struct não faz boxing; já converter (implícita ou explicitamente) a struct para o tipo da interface aloca uma cópia no heap (boxing) antes de expor o valor através dela. Em .NET: Em um caminho de alto throughput em .NET 8 que compara/ordena valores de uma struct de domínio (por exemplo, um objeto de valor `Dinheiro` implementando `IEquatable<Dinheiro>`) antes de uma inserção em lote no SQL Server, armazenar ou passar essas structs como `IEquatable<Dinheiro>` força uma alocação de boxing por elemento; manter o tipo concreto da struct (ou usar genéricos com constraint de interface, que evitam boxing) preserva o comportamento sem alocação. [CS12-03-C-16] {ACORDO 1 / alta}
  - Limite: Não se aplica quando o membro é chamado através de um parâmetro genérico com constraint na interface (`where T : IEquatable<T>`), porque o compilador gera código especializado por tipo fechado sem boxing nesse caso.
- **Evite `ImmutableArray<T>` quando houver mutações frequentes** — `ImmutableArray<T>` é implementado sobre um array simples, sem estrutura em árvore para reaproveitar partes da versão anterior; cada `Add`/`Remove` recopia o array inteiro, tornando-o mais lento para escrita do que até mesmo `ImmutableList<T>` (que reaproveita nós de uma árvore). Em .NET: Um serviço escolhe `ImmutableArray<T>` para uma lista de assinantes de evento montada incrementalmente a cada `Subscribe()` chamado em runtime (em vez de compor tudo de uma vez na inicialização), pensando que "array imutável = mais rápido"; sob muitas assinaturas dinâmicas, cada `Add` individual passa a custar proporcionalmente ao tamanho atual da coleção. [CS12-07-B-12] {ACORDO 1 / alta}
  - Limite: Não se aplica quando a coleção é montada uma única vez (via `Create`/`CreateRange`/`Builder`) e depois só é lida — cenário em que `ImmutableArray<T>` é a melhor opção por ter leitura tão rápida quanto um array comum.
- **Implemente `IEquatable<T>` em chaves struct usadas em alto volume** — `EqualityComparer<T>.Default`, usado internamente pelas tabelas hash, primeiro verifica se `T` implementa `IEquatable<T>`; se não, cai para `object.Equals`, que exige boxing do valor a cada comparação. Em .NET: Uma `struct` de chave composta (por exemplo, uma chave `TenantId`+`OrderId`) usada como chave de `Dictionary<OrderKey, Order>` em um serviço de alto throughput, sem `IEquatable<OrderKey>`, força uma alocação de boxing a cada `TryGetValue`/inserção sob carga. [CS12-07-B-14] {ACORDO 1 / media}
  - Limite: Não se aplica quando `T` já é um tipo primitivo (`int`, `Guid` etc., que implementam `IEquatable<T>` nativamente) nem quando a chave é um tipo referência.
- **Considere o custo de localizar nós antes de escolher `LinkedList<T>`** — A inserção em `LinkedList<T>` só é O(1) quando já se possui a referência ao `LinkedListNode<T>` de destino; localizar esse nó por valor exige `Find`, que percorre a lista inteira, na mesma ordem de grandeza da busca em `List<T>`, mas com overhead extra de ponteiros por nó. Em .NET: Um serviço de alto throughput mantém uma fila de tarefas ordenada por prioridade em `LinkedList<Task>` pensando ganhar desempenho em inserções, mas cada inserção primeiro percorre a lista para achar a posição correta antes de `AddAfter`/`AddBefore` — o custo total por inserção fica igual ou pior do que simplesmente usar `List<T>`, que também tem melhor localidade de cache. [CS12-07-B-15] {ACORDO 1 / media}
  - Limite: Não se aplica quando o código já possui a referência ao nó de inserção (por exemplo, um iterador que caminha e insere durante a mesma passagem) — nesse caso o ganho de `LinkedList<T>` é real.
- **Evite recompilar expressões locais por meio de `AsQueryable`** — `AsQueryable()` embrulha a sequência local numa implementação de `IQueryable<T>` que constrói expression trees para os operadores subsequentes (para compartilhar a mesma assinatura de método com o lado do banco); ao enumerar, essa implementação local decompõe a árvore e a compila de volta para delegates antes de rodar contra a coleção em memória. Em .NET: Em C# 12, `FilterSortProducts(localProducts.AsQueryable())` executa a mesma lógica da versão puramente local, mas paga o custo extra de montar e compilar a árvore de expressão a cada enumeração — custo que `FilterSortProducts` chamado direto sobre `IEnumerable<T>` (sem `AsQueryable`) não paga. [CS12-08-A-15] {ACORDO 1 / media}
  - Limite: O custo é pequeno e normalmente irrelevante fora de laços quentes executados milhões de vezes; não se aplica quando a sequência já é `IQueryable<T>` de origem (banco), caso em que não há embrulho algum.
- **Calcule expressões repetidas uma vez com `let`** — O compilador resolve `let` projetando, antes das cláusulas seguintes, um tipo anônimo temporário que carrega tanto a variável de alcance original quanto o novo valor calculado; as cláusulas seguintes leem esse valor já pronto do tipo anônimo, em vez de reinvocar a expressão original — sem `let`, cada cláusula que repete a mesma expressão dispara sua própria avaliação independente por elemento. Em .NET: Em C# 12, `from n in names let vowelless = n.Replace("a","").Replace("e","")... where vowelless.Length > 2 orderby vowelless select n` calcula a versão sem vogais uma vez por elemento; escrever a mesma cadeia de `Replace` separadamente dentro do `where` e de novo dentro do `orderby` (sem `let`) faz esse trabalho rodar duas vezes por elemento. [CS12-08-A-30] {ACORDO 1 / media}
  - Limite: Não traz vantagem quando a expressão repetida é trivial (leitura direta de propriedade), nem em consultas interpretadas pelo EF Core, onde o mecanismo de reaproveitamento depende do provedor de tradução SQL, não deste comportamento local do `let`.
- **Materialize a consulta externa antes de executar lazy loading aninhado** — Por padrão, uma conexão SQL Server só permite um result set ativo por vez; iterar diretamente sobre `dbContext.Customers` (sem materializar) enquanto o laço interno dispara outra consulta (lazy loading de `Purchases`) tenta abrir um segundo result set na mesma conexão ainda em uso pelo primeiro. Em .NET: Em EF Core 8 com lazy loading habilitado, `foreach (var c in dbContext.Customers) foreach (var p in c.Purchases) ...` lança exceção do SQL Server, a menos que a connection string tenha `MultipleActiveResultSets=True`; trocar por `dbContext.Customers.ToArray()` no laço externo resolve sem precisar de MARS. [CS12-08-B-16] {ACORDO 1 / alta}
  - Limite: Não se aplica se `MultipleActiveResultSets=True` estiver na connection string, ou se a navegação já estiver eager-loaded/projetada.
- **Junte coleções materializadas com `Join`** — O padrão SelectMany-com-where reavalia o predicado de junção para cada combinação possível entre as duas coleções (produto cartesiano completo antes de filtrar), enquanto Join constrói uma vez um lookup indexado pela chave interna e depois só percorre os elementos correspondentes, evitando o produto cartesiano. Em .NET: Em C# 12/.NET 8, aplicar `from c in customers from p in purchases where c.ID == p.CustomerID select ...` sobre dois arrays já carregados com `.ToArray()` do EF Core executa o predicado de igualdade até customers.Length * purchases.Length vezes, contra apenas customers.Length + purchases.Length avaliações de chave com `customers.Join(purchases, c => c.ID, p => p.CustomerID, ...)`. [CS12-09-B-11] {ACORDO 1 / alta}
  - Limite: Não se aplica enquanto a query ainda é executada como IQueryable contra o EF Core (nesse caso Join e SelectMany geram o mesmo SQL) — a diferença de custo só existe para coleções já em memória.
- **Avalie o SQL gerado por `Contains` conforme o tipo da coleção** — Para uma coleção local de valores escalares, o provider tem uma tradução direta e compacta (IN); para uma coleção de entidades ou tipos não escalares, essa tradução direta não existe, e o provider recorre a uma subconsulta EXISTS por elemento. Em .NET: Em EF Core 8, `where chosenNames.Contains(c.Name)` com `chosenNames` sendo `string[]` gera `WHERE customer.Name IN (...)`; a mesma chamada com uma coleção de objetos gera uma cláusula EXISTS em vez de IN. [CS12-09-C-12] {ACORDO 1 / media}
  - Limite: Aplica-se apenas quando a coleção do lado do Contains é avaliada localmente; se a coleção também vier de uma consulta ao banco, o comportamento de tradução é outro e não está coberto por esta regra.
- **Não recomprima dados densos ou criptografados** — A compressão explora repetição; dados densos não repetitivos e dados cifrados projetados para não ter regularidade oferecem pouco padrão aproveitável. Em .NET: Evite colocar payload criptografado em `DeflateStream`, `GZipStream` ou `BrotliStream` sem medir ganho real. [CS12-15-A-46] {ACORDO 1 / alta}
  - Limite: Dados textuais ou binários altamente repetitivos podem continuar obtendo redução significativa.
- **Prefira arrays retangulares para linhas uniformes** — O array retangular representa um bloco n-dimensional único de memória, enquanto o jagged é um objeto por linha; cada acesso ao jagged passa por uma referência adicional, e as linhas podem estar espalhadas pelo heap em vez de contíguas. Em .NET: Em .NET 8, `int[,]` de mil por mil é uma alocação contígua, e `int[][]` equivalente são mil e um objetos com indireção por acesso; em varreduras densas isso muda a localidade de cache e o número de objetos que o GC precisa rastrear. [CS12-02-A-47] {ACORDO 1 / alta}
  - Limite: Não se aplica quando as linhas têm comprimentos diferentes, que é exatamente o que o jagged permite e o retangular não.
- **Marque como `readonly` structs passadas por `in`** — O modificador in passa por referência somente leitura para evitar a cópia de um struct grande, mas o compilador precisa garantir que o método chamado não altere o valor original; se o tipo não é declarado readonly, ele insere uma cópia defensiva antes de cada uso, o que devolve exatamente o custo que o in pretendia remover. Em .NET: Em .NET 8, chamar um método de instância sobre um parâmetro `in SomeBigStruct` de um struct não readonly copia a struct por chamada; marcar o tipo `readonly struct` elimina a cópia e preserva o ganho, o mesmo valendo para retorno ref readonly. [CS12-02-A-55] {ACORDO 1 / alta}
  - Limite: Não se aplica a structs pequenos, onde a cópia é mais barata que a indireção.
- **Evite cópias defensivas em métodos readonly** — Quando um método marcado `readonly` chama um membro que não é `readonly`, o compilador não pode garantir que esse membro não vai mutar a struct, então gera uma cópia defensiva da struct inteira antes da chamada — isso é só um aviso do compilador, não um erro. Em .NET: Em um laço de alto throughput em .NET 8 que itera um array de structs (por exemplo, DTOs de linhas lidas do SQL Server) chamando um método por elemento, se esse método não estiver marcado `readonly` mas for chamado a partir de um contexto `readonly`, cada iteração paga o custo invisível de copiar a struct inteira antes da chamada — trabalho extra na pilha repetido a cada iteração do laço quente, sem aparecer como alocação de heap. [CS12-03-C-18] {ACORDO 1 / alta}
  - Limite: Não se aplica a métodos que já modificam a struct (esses legitimamente não devem ser `readonly`), nem a structs pequenas onde o custo de cópia é desprezível mesmo em laços — o impacto real depende do tamanho da struct e da frequência de chamada.
- **Use coleções Frozen para dados construídos uma única vez** — Frozen collections trocam um custo de construção maior — elas pré-computam uma estrutura de busca otimizada no momento da criação — por lookups mais rápidos depois; ao contrário de `ImmutableDictionary`, elas não expõem métodos de mutação não destrutiva, então não pagam o overhead estrutural que essas operações exigem. Em .NET: Um cache estático montado uma vez na inicialização (ex.: tabela de mapeamento enum→string usada para montar filtros de uma query EF Core 8) deve ser materializado como `FrozenDictionary` via `.ToFrozenDictionary()` fora do caminho por requisição; recriar esse dicionário a cada requisição anula o ganho, porque o custo de construção do Frozen é maior que o de um `Dictionary` comum. [CS12-05-A-6] {ACORDO 1 / media}
  - Limite: não se aplica quando a coleção é mutada com frequência, ou quando é pequena o suficiente para que a diferença de desempenho de lookup seja irrelevante frente ao custo de construção.
- **Analise números UTF-8 diretamente do span** — Decodificar bytes UTF-8 para `string` antes do parsing aloca uma nova string na heap gerenciada só para descartá-la logo em seguida; os tipos numéricos do .NET 8 implementam `IUtf8SpanParsable<TSelf>`, permitindo `int.Parse(ReadOnlySpan<byte>)`, que analisa os bytes diretamente sem essa alocação intermediária. Em .NET: Um parser de protocolo binário de alto throughput que faz `Encoding.UTF8.GetString(byteSpan)` seguido de `int.Parse(string)` para cada campo numérico gera uma alocação de string por campo por mensagem; trocar para a sobrecarga `int.Parse(ReadOnlySpan<byte>, ...)` elimina essas alocações. [CS12-05-A-12] {ACORDO 1 / media}
  - Limite: não se aplica quando o texto já está disponível como `string` gerenciada vinda de uma API que só expõe `string` — nesse caso não há bytes UTF-8 a evitar.
## Manutenção

- **Generalize algoritmos numéricos com INumber<T>** — A unificação não vem de conversão: a interface declara os operadores aritméticos como membros estáticos abstratos, e o `INumber<TSelf>` é implementado por todos os tipos numéricos reais e integrais, de modo que `+` dentro do método genérico resolve para o operador do tipo concreto. Em .NET: Em .NET 8, um único `T Sum<T>(T[] n) where T : INumber<T>` atende `int`, `double` e `decimal`, e `T.Zero` fornece o elemento neutro correto para cada um. [CS12-01-A-61, CS12-04-A-42] {ACORDO 1 / media}
  - Limite: `char` também implementa a interface, o que pode admitir instanciações indesejadas.
- **Resolva colisões entre namespaces e tipos com aliases ou renomeação explícita** — o compilador sempre dá precedência a identificadores do namespace atual, então um tipo aninhado com o mesmo nome do namespace vence a qualificação — e a intenção de referenciar o outro tipo não é expressável assim. Em .NET: em C# 12, com um namespace `A` e uma classe aninhada `A.B`, `new A.B()` instancia a aninhada; alcançar a outra exige `global::A.B`, forma comum em código gerado justamente por esse motivo. [CS12-02-C-91, CS12-02-C-92] {ACORDO 1 / alta}
  - Limite: nomes de namespace distintos dos nomes de tipos eliminam o problema na origem; e o `::` só qualifica em relação ao namespace global ou a aliases extern, não a qualquer escopo.
- **Reserve _ para descartes** — por compatibilidade retroativa, o `_` deixa de ser discard e volta a ser uma variável comum quando existe um `_` real em escopo; a atribuição passa a acontecer de verdade. Em .NET: `int.TryParse(s, out _)` num método .NET 8 que declarou `string _` (ou recebeu um `_` de um lambda) sobrescreve silenciosamente aquela variável em vez de descartar o valor. [CS12-02-B-34, CS12-02-C-59] {ACORDO 2 / alta}
  - Limite: sem nenhum `_` declarado em escopo, o discard funciona como esperado, inclusive múltiplas vezes na mesma chamada.
- **Distribua traduções em assemblies satélites** — ResourceManager procura primeiro uma versão localizada no satélite correspondente ao idioma do sistema antes de usar o recurso principal. Em .NET: Uma aplicação .NET 8 com `welcome.de.resx` pode retornar `hallo` quando Thread.CurrentThread.CurrentUICulture é `de`, sem alterar o código que chama GetString. [CS12-17-A-29, CS12-17-C-26] {ACORDO 2 / alta}
  - Limite: Satélites carregam recursos localizáveis, não assemblies de código executável.
- **Use retornos covariantes em overrides especializados** — A partir do C# 9, o compilador aceita que o tipo de retorno de um override seja mais derivado que o da assinatura virtual, desde que ainda satisfaça o contrato original — assim o chamador que já sabe estar lidando com a subclasse recebe o tipo certo sem precisar de downcast manual. Em .NET: Um método `Clone()` de uma entidade base .NET 8 sobrescrito numa subclasse como `public override House Clone()` permite ao chamador que já tem uma referência a `House` continuar com `House` sem fazer `(House)base.Clone()`. [CS12-03-A-33] {ACORDO 1 / alta}
  - Limite: O tipo de retorno do override precisa continuar sendo compatível (subtipo) do tipo declarado no membro virtual original.
- **Retorne tipos nomeados em vez de tipos anônimos** — Um tipo anônimo não tem nome que possa ser escrito como tipo de retorno, e `var` não é um tipo de retorno válido para métodos — a única forma de "usá-lo" além do escopo de criação é via inferência local (`var`), que não cruza a fronteira de um método. Em .NET: Extrair uma projeção LINQ `new { Id, Nome }` de dentro de uma consulta EF Core 8 para um método reutilizável `BuscarResumo()` força a troca do tipo anônimo por um `record ResumoDto(int Id, string Nome)` ou por uma tupla nomeada `(int Id, string Nome)`. [CS12-04-C-26] {ACORDO 1 / alta}
  - Limite: Não afeta o uso do tipo anônimo inteiramente dentro do mesmo método/expressão (ex.: dentro de um `.Select()` cujo resultado é imediatamente materializado no mesmo escopo); a restrição só aparece ao tentar cruzar uma fronteira de método.
- **Exponha coleções covariantes por interfaces somente leitura** — Essas interfaces marcam T como covariante (out T) porque T só aparece em posições de saída (o indexador só tem get); IList<T>/ICollection<T> não podem ser covariantes porque T também aparece em posições de entrada (Add(T), indexador com set), e permitir a variância ali quebraria a segurança de tipos em tempo de compilação. Em .NET: Em C# 12/.NET 8, um método `IReadOnlyList<Animal> GetAll()` pode retornar internamente uma `List<Dog>` e ser atribuído a uma variável `IReadOnlyList<Animal>` sem erro; a mesma atribuição usando `IList<Animal>` como tipo de retorno não compila. [CS12-07-A-5] {ACORDO 1 / alta}
  - Limite: Se o consumidor realmente precisa adicionar ou remover itens pela interface, a covariância não se aplica e IList<T>/ICollection<T> continuam corretos.
- **Delegue o enumerador não genérico ao enumerador genérico** — A implementação explícita de interface remove o membro da superfície pública padrão do tipo; assim, quem chama GetEnumerator() diretamente na variável estaticamente tipada como sua classe recebe o IEnumerator<T> tipado, e só obtém o IEnumerator não genérico se explicitamente fizer cast para IEnumerable. Em .NET: Em .NET 8, uma classe wrapper `class ProdutoFeed : IEnumerable<Produto>` construída sobre resultados brutos de uma consulta EF Core 8/Dapper deve implementar `IEnumerable.GetEnumerator()` explicitamente delegando para a versão genérica, garantindo que `foreach` e chamadas diretas a `GetEnumerator()` sempre entreguem o enumerador tipado, sem risco de um consumidor cair no caminho não genérico (com boxing) por engano. [CS12-07-A-25] {ACORDO 1 / alta}
  - Limite: Não se aplica a classes que implementam apenas IEnumerable<T> sem também implementar a versão não genérica (caso em que não há ambiguidade a esconder).
- **Use chaves em condicionais aninhadas** — o `else` sempre se liga ao `if` imediatamente anterior no bloco, independentemente da indentação; mover as chaves é o que muda o fluxo, não recuar o código. Em .NET: em C# 12, um `else` recuado como se pertencesse ao `if` externo pertence ao interno e executa quando o autor esperava que não; num filtro de gravação isso decide se o UPDATE sai ou não. [CS12-02-C-81] {ACORDO 1 / alta}
  - Limite: a cadeia `else if` em sequência é exceção aceita — semanticamente cada if está aninhado no else anterior, mas a leitura é padronizada e o auto-formatador preserva a indentação.
- **Obtenha nomes de símbolos com nameof** — `nameof` é resolvido pelo compilador contra o símbolo real referenciado, então ferramentas de refatoração que renomeiam esse símbolo atualizam automaticamente todo uso de `nameof` associado a ele, o que uma string solta nunca acompanharia. Em .NET: Uma checagem `ArgumentNullException` num interceptor de EF Core 8, ou a ordenação dinâmica de uma consulta LINQ a partir do nome de uma propriedade, usando `nameof(Entidade.Propriedade)` continua correta automaticamente após um `rename` da propriedade, enquanto uma string literal ficaria desatualizada silenciosamente. [CS12-03-A-27] {ACORDO 1 / alta}
  - Limite: Não substitui nomes que precisam corresponder a algo fora do código C# (por exemplo, um nome de coluna já fixado no schema do SQL Server, independente do nome da propriedade).
