- **Nunca use `NOT IN` contra subquery que possa conter NULL; use `NOT EXISTS`** — um NULL na subquery torna toda comparação `UNKNOWN`, e o predicado nunca é verdadeiro, então o resultado vem vazio em vez de vir errado — o que é pior, porque não parece defeito. Em .NET: um relatório em `FromSql` com `WHERE Id NOT IN (SELECT ClienteId FROM Pedido)` devolve zero linhas silenciosamente se `ClienteId` for anulável. {EVIDENCIA: `NOT IN` devolveu 0 linhas e `NOT EXISTS` devolveu 1 sobre os mesmos dados — `validacao/repro/F4-query`}
- **`COUNT(coluna)` ignora NULL e `COUNT(*)` não; escolha pela pergunta, não pelo hábito** — o agregado descarta linhas com NULL na coluna contada, e o servidor avisa em vez de errar. Em .NET: `Select(x => x.Total).Count()` e `Count()` no EF Core traduzem para agregados diferentes e podem divergir na mesma tabela. {EVIDENCIA: `COUNT(*)=4` contra `COUNT(Total)=3`, com aviso "Null value is eliminated by an aggregate" — `validacao/repro/F4-query`}
- **Alias do SELECT não existe no WHERE/GROUP BY/HAVING, mas existe no ORDER BY** — a ordem lógica processa WHERE antes do SELECT e ORDER BY depois; encapsule em CTE ou derived table para reusar o alias nas cláusulas anteriores. Em .NET: SQL escrito à mão em `FromSqlRaw` ou `migrationBuilder.Sql` falha em runtime com erro 207, independentemente do EF Core. {EVIDENCIA: alias no WHERE falhou com erro 207 `Invalid column name`; o mesmo alias no ORDER BY executou — `validacao/repro/F4-query`}
- **Função sobre coluna indexada no WHERE troca busca por varredura do índice inteiro** — o predicado deixa de ser sargável, então o motor não consegue delimitar a faixa e percorre todas as páginas do índice. Em .NET: `Where(e => e.Quando.Year == 2023)` no EF Core traduz para `YEAR(Quando) = 2023`; reescreva como intervalo meio-aberto sobre a coluna crua. {EVIDENCIA: mesmo resultado (525.599 linhas) custou 15.594 leituras lógicas via `YEAR(Quando)=2023` contra 1.177 via intervalo — 13,2x — `validacao/repro/F4-query`}
- **"UDF escalar mata o paralelismo" vale apenas abaixo do compatibility level 150** — a partir de 150 o scalar UDF inlining remove a UDF do plano e o paralelismo volta; a UDF continua mais caro que o predicado sargável, mas por outra razão. Em .NET: antes de recomendar reescrita de UDF, leia `compatibility_level` do banco — o argumento muda completamente. {EVIDENCIA: mesma UDF, compat 140 → 56.471 ms elapsed e plano serial; compat 160 → 321 ms elapsed com `Paralelismo=SIM` e UDF ausente do plano, 176x; predicado inline sargável 59 ms — `validacao/repro/F4-query`}

## Correção

- **Remova ordenações de apresentação dos ramos e expressões de tabela e ordene apenas na consulta externa** — Uma table expression representa uma relação, e o corpo de uma relação é um conjunto sem ordem garantida; o T-SQL só tolera ORDER BY ali quando ele deixa de ser apresentação e passa a integrar a especificação de um filtro TOP ou OFFSET-FETCH. Em .NET: SQL bruto (`FromSqlRaw`/`FromSqlInterpolated`) do EF Core 8, ou uma string enviada via `SqlCommand`, que define uma CTE/derived table com ORDER BY sem TOP/OFFSET-FETCH falha em tempo de execução com o mesmo erro do SQL Server, porque o texto é executado tal como escrito — o LINQ do EF Core nunca produz essa combinação sozinho, mas SQL manual embutido em C# está sujeito à mesma regra. [TSQL-01-C-1, TSQL-05-A-2, TSQL-05-A-3, TSQL-05-B-1, TSQL-05-C-2, TSQL-06-B-6 +2] {ACORDO 3 / baixa}
  - Limite: Não se aplica à query externa final, fora de qualquer table expression, onde ORDER BY sempre é permitido e é o único jeito de garantir ordem de apresentação.
- **Encapsule a expressão e filtre seu alias na consulta externa** — o T-SQL processa as cláusulas em ordem lógica fixa (FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY); um nome introduzido no SELECT ainda não existe quando WHERE/GROUP BY são resolvidos, então é preciso encapsular a expressão em uma table expression (derived table/CTE) para reutilizar o alias nas cláusulas processadas antes. Em .NET: SQL bruto escrito à mão dentro de `FromSqlRaw`/`ExecuteSqlRaw`/`migrationBuilder.Sql` no estilo `SELECT YEAR(OrderDate) AS OrderYear ... GROUP BY OrderYear` falha em tempo de execução com SqlException, independentemente do EF Core — é um erro de sintaxe T-SQL puro, não algo que o provider possa mitigar. [TSQL-02-A-1, TSQL-02-B-1, TSQL-02-C-1, TSQL-05-A-6, TSQL-05-C-4, TSQL-07-A-7 +1] {ACORDO 3 / media}
  - Limite: Não se aplica à cláusula ORDER BY da mesma consulta — ORDER BY é processada depois do SELECT e pode referenciar diretamente um alias ali definido, sem necessidade de table expression; a restrição vale só para WHERE, GROUP BY e HAVING.
- **Use ordenação total com desempate único antes de paginar ou numerar linhas** — T-SQL trata OFFSET-FETCH como uma extensão da cláusula ORDER BY, não como um filtro independente; sem uma ordenação definida não há uma noção coerente de "quais linhas pular", então o padrão exige a presença de ORDER BY para que OFFSET/FETCH sejam sintaticamente válidos. Em .NET: O EF Core 8 reflete essa exigência na API: `dbSet.Skip(10).Take(5)` sem uma chamada `.OrderBy(...)` anterior lança `InvalidOperationException` na tradução da query em vez de gerar SQL sem ORDER BY. [TSQL-02-A-17, TSQL-02-A-6, TSQL-02-A-7, TSQL-02-C-7, TSQL-07-A-3, TSQL-07-B-1] {ACORDO 3 / media}
  - Limite: Não se aplica quando apenas OFFSET é usado sem FETCH (T-SQL permite "pular e devolver o resto"), nem a provedores LINQ que, ao contrário do EF Core, aceitem Skip/Take sem OrderBy e apliquem uma ordenação implícita não documentada.
- **Use GROUPING e interprete o valor 1 como linha agregada para distinguir NULL de subtotal** — O SQL Server usa NULL tanto como placeholder de "esta coluna não participa deste conjunto de agrupamento" quanto como valor real de dado ausente; se a coluna de agrupamento permite NULL na tabela de origem, não há como distinguir os dois casos apenas olhando o valor retornado. Em .NET: Uma query EF Core 8 raw SQL que filtra `WHERE ClienteId IS NULL` sobre um resultado de `GROUP BY CUBE(ClienteId, Ano)` para extrair "o total geral por ano" mistura, incorretamente, pedidos legítimos sem cliente atribuído (ClienteId NULL nos dados reais) com as linhas de subtotal do CUBE. [TSQL-07-A-12, TSQL-07-A-13, TSQL-07-B-8, TSQL-07-B-9, TSQL-07-C-15, TSQL-07-C-16] {ACORDO 3 / alta}
  - Limite: Não se aplica quando a coluna de agrupamento é NOT NULL na tabela de origem — nesse caso todo NULL no resultado é garantidamente um placeholder de agregação.
- **Use NOT EXISTS para anti-joins quando houver valores anuláveis** — EXISTS usa lógica bivalorada — sempre TRUE ou FALSE, nunca UNKNOWN; quando a subquery correlacionada encontra um NULL, apenas aquela comparação específica vira UNKNOWN e é descartada da checagem de existência, sem contaminar a avaliação das demais linhas da query externa, ao contrário do NOT IN que propaga o UNKNOWN para o predicado inteiro. Em .NET: Trocar `!ctx.Orders.Select(o => o.CustomerId).Contains(c.Id)` por `!ctx.Orders.Any(o => o.CustomerId == c.Id)` no EF Core 8 gera `NOT EXISTS` e neutraliza o risco de FK anulável sem precisar adicionar `.Where(o => o.CustomerId != null)` manualmente na subquery. [TSQL-04-A-4, TSQL-04-A-5, TSQL-04-B-3, TSQL-04-C-3, TSQL-04-C-4] {ACORDO 3 / media}
  - Limite: Não se aplica quando a intenção de negócio realmente é tratar a presença de qualquer NULL como "não sei responder" e propagar essa incerteza para o resultado (por exemplo, relatórios de auditoria de completude de dados); nesse cenário raro, o comportamento do NOT IN é o desejado, não um bug.
- **Ordene explicitamente o resultado externo** — o SQL Server trata qualquer table expression intermediária como uma tabela virtual sem ordem; a ORDER BY interna, mesmo combinada com TOP/OFFSET-FETCH, garante apenas qual conjunto de linhas é filtrado — a ordem final observada sem uma ORDER BY explícita na consulta externa é um artefato acidental do plano atual, não um contrato. Em .NET: Uma query LINQ do EF Core 8 que envolve `OrderBy().Take(n)` dentro de uma subconsulta (view mapeada, ou subquery composta) e depois é consumida por outra consulta sem `.OrderBy()` final não tem garantia de ordem no resultado materializado, mesmo que hoje, localmente, os registros pareçam ordenados. [TSQL-05-B-2, TSQL-05-C-3, TSQL-06-A-6, TSQL-07-A-9, TSQL-07-C-23] {ACORDO 3 / media}
  - Limite: Aplica-se apenas à propagação implícita de ordem entre a table expression interna e a consulta externa; adicionar uma ORDER BY explícita como operador mais externo (LINQ `.OrderBy()` antes da materialização final) garante a ordem independentemente do que acontece dentro das table expressions aninhadas.
- **Use IN quando a subquery puder retornar várias linhas** — O SQL Server compila a subquery escalar assumindo cardinalidade 1 no plano, mas não pode provar isso em tempo de compilação a partir do texto da consulta; por isso insere uma checagem em runtime que aborta com erro 512 assim que uma segunda linha do lado interno é produzida, porque o operador `=` escalar não tem semântica definida para comparar um valor único com dois. Em .NET: Em SQL bruto executado via EF Core 8 (`FromSqlRaw`/`ExecuteSqlRaw`) ou `SqlCommand` direto com um predicado `coluna = (SELECT ...)`, uma mudança nos dados que passa a produzir uma segunda linha do lado interno faz o comando lançar `Microsoft.Data.SqlClient.SqlException` (erro 512) só na execução — o `SqlException` chega ao código C# exatamente como o SQL Server o produziu, sem tradução ou amortecimento pela camada ADO.NET/EF Core. [TSQL-04-A-1, TSQL-04-A-3, TSQL-04-B-1, TSQL-04-C-1] {ACORDO 3 / media}
  - Limite: Não se aplica a subqueries usadas com IN, EXISTS, ANY/ALL ou dentro de funções de agregação (MAX, SUM, COUNT), que toleram qualquer cardinalidade do lado direito.
- **Preserve a semântica de NULL ao substituir operadores de conjunto** — EXCEPT e INTERSECT comparam linhas usando o predicado distinct do padrão SQL, no qual um NULL não é distinto de outro NULL; um predicado de igualdade comum (coluna = coluna) usado em JOIN ou NOT EXISTS trata NULL como desconhecido e nunca considera duas colunas NULL como iguais. Em .NET: Um repositório em .NET 8 que reescreve `... EXCEPT ...` como `WHERE NOT EXISTS (SELECT 1 FROM Sales.Customers C WHERE C.Region = E.Region AND C.Country = E.Country AND C.City = E.City)` via Dapper ou ADO.NET puro, sem tratar NULL, faz com que uma linha de Employees com Region NULL — mesmo tendo correspondência exata em Customers com Region também NULL — seja incluída no resultado do NOT EXISTS, porque `C.Region = E.Region` nunca é verdadeira quando ambos os lados são NULL. [TSQL-06-A-1, TSQL-06-A-10, TSQL-06-B-2, TSQL-06-C-6] {ACORDO 3 / media}
  - Limite: Não se aplica se as colunas comparadas tiverem restrição NOT NULL, ou se o NOT EXISTS/JOIN já incluir `OR (C.Region IS NULL AND E.Region IS NULL)` para cada coluna nullable.
- **Escolha a variante de COUNT que conte apenas as linhas ou entidades pretendidas** — Toda função de agregação aplicada a uma expressão de entrada ignora NULLs por definição — soma, média, contagem por coluna, mínimo e máximo operam apenas sobre os valores conhecidos do grupo; COUNT(*) é a exceção porque não tem expressão de entrada, apenas conta linhas independentemente do conteúdo. Em .NET: No LINQ do EF Core 8, `.Count()` sobre um `IQueryable<T>` traduz para `COUNT(*)`, enquanto `.Average(x => x.Prop)` sobre uma propriedade anulável traduz para `AVG(coluna)`, herdando automaticamente a mesma exclusão de NULLs do SQL Server — um dev que espera que `.Average()` conte as linhas com valor NULL como zero está enganado tanto em LINQ quanto em SQL cru. [TSQL-02-A-20, TSQL-03-A-11, TSQL-03-B-5, TSQL-03-C-9] {ACORDO 3 / media}
  - Limite: Não se aplica a colunas NOT NULL, onde COUNT(*) e COUNT(coluna) sempre coincidem, nem a SUM/AVG sobre colunas sem nenhum NULL presente nos dados.
- **Qualifique colunas para eliminar ambiguidades em subqueries e expressões de tabela** — A resolução de um nome de coluna não prefixado dentro de uma subquery é feita de dentro para fora: o mecanismo procura primeiro nas tabelas da própria subquery e, se não encontrar, procura nas tabelas da consulta externa; se um nome de coluna parecido (mas não idêntico) existir só na tabela externa, a subquery vira correlacionada com essa coluna silenciosamente, comparando a tabela externa consigo mesma, sem qualquer erro de sintaxe ou de resolução. Em .NET: Em uma view, migration ou stored procedure escrita à mão para SQL Server e chamada por .NET 8 (via `FromSqlRaw` no EF Core 8 ou ADO.NET), uma subquery `WHERE shipper_id IN (SELECT shipper_id FROM Orders WHERE custid = @c)` — quando Orders na verdade tem a coluna `shipperid`, sem underscore — compila sem erro e devolve todas as linhas da tabela externa, porque `shipper_id` é resolvido para a coluna homônima da tabela externa, mascarando completamente o filtro pretendido. [TSQL-04-A-7, TSQL-04-B-4, TSQL-04-C-7, TSQL-05-A-5] {ACORDO 3 / media}
  - Limite: Não se aplica se os nomes de colunas forem idênticos em todas as tabelas do schema (não há ambiguidade a explorar) ou se toda subquery já prefixar suas colunas com alias.
- **Termine instruções T-SQL com ponto e vírgula, especialmente antes de CTEs e após MERGE** — O WITH é usado em T-SQL para múltiplos propósitos (hints de tabela, definição de CTE); para evitar ambiguidade, o SQL Server exige que a instrução anterior no mesmo lote termine com ponto e vírgula quando um WITH de CTE se segue, e a mensagem de erro resultante da ausência desse ponto e vírgula aponta para o próprio WITH, não para a instrução anterior que realmente causou o problema. Em .NET: Um script de migração ou uma string SQL multi-instrução passada para `ExecuteSqlRaw`/`FromSqlRaw` no EF Core 8, herdada de um código-base que não termina consistentemente as instruções com ponto e vírgula, lança `SqlException` de sintaxe apontando para a linha do WITH assim que alguém adiciona uma consulta baseada em CTE ao final do script, mesmo que a sintaxe da CTE em si esteja perfeitamente correta. [TSQL-01-A-37, TSQL-05-B-13, TSQL-08-B-22, TSQL-08-C-20] {ACORDO 3 / media}
  - Limite: Não se aplica quando cada instrução do lote já é terminada com ponto e vírgula de forma consistente.
- **Interprete períodos temporais pelo início da transação** — o SQL Server grava nas colunas de período o horário de início da transação corrente, não o horário de cada statement isoladamente; assim, dentro de uma única transação que executa vários UPDATEs espaçados no tempo antes do commit, todas as versões geradas recebem o mesmo carimbo — o do BEGIN TRAN, não o do momento em que cada UPDATE foi de fato executado. Em .NET: em um serviço .NET 8, abrir uma transação com `context.Database.BeginTransactionAsync()` e chamar `SaveChanges()` várias vezes com processamento (e portanto tempo real) entre as chamadas antes do commit produz linhas de histórico cujo validfrom/validto são todos idênticos ao instante do início da transação, não ao instante de cada `SaveChanges()`. [TSQL-09-A-1, TSQL-09-A-2, TSQL-09-B-7, TSQL-09-C-5] {ACORDO 3 / alta}
  - Limite: nenhum conhecido dentro do escopo de uma transação; sem transação explícita, cada instrução tem sua própria transação implícita e o problema não ocorre.
- **Valide a disponibilidade dos recursos T-SQL antes de usá-los** — Esses recursos exigem nível de compatibilidade 160 ou superior; um banco de dados migrado ou restaurado que permaneceu em um nível de compatibilidade anterior rejeita a sintaxe mesmo rodando em uma instância física do SQL Server 2022. Em .NET: Um comando raw SQL disparado por `Database.ExecuteSqlRaw` em EF Core 8 usando `DATE_BUCKET(hour, 12, Ts)` funciona perfeitamente no container de desenvolvimento (banco novo, compat level 160) e falha em produção com erro de sintaxe porque o banco de produção foi restaurado de uma versão anterior e ficou no compat level 150. [TSQL-02-C-19, TSQL-07-B-10, TSQL-07-C-22, TSQL-07-C-6] {ACORDO 2 / media}
  - Limite: Não se aplica a bancos criados do zero em uma instância SQL Server 2022/Azure SQL Database recente, onde o compatibility level padrão já é 160.
- **Aplique lógica trivalorada às comparações anuláveis** — T-SQL usa lógica de três valores; um operador de comparação aplicado a um NULL não retorna FALSE, retorna UNKNOWN, e a fase WHERE só deixa passar linhas onde o predicado é TRUE — UNKNOWN é descartado exatamente como FALSE. Em .NET: O EF Core 8, por padrão (sem `UseRelationalNulls`), reescreve `x.Region == region` como `(x.Region = @region OR (x.Region IS NULL AND @region IS NULL))` para simular a igualdade do C# (onde `null == null` é `true`), compensando essa diferença de semântica em relação ao SQL puro. [TSQL-01-C-3, TSQL-02-A-2, TSQL-02-C-3, TSQL-03-C-7] {ACORDO 2 / media}
  - Limite: Não se aplica a predicados que já usam IS NULL/IS NOT NULL explicitamente, nem a filtros sobre colunas NOT NULL.
- **Capture identities gerados com OUTPUT** — @@IDENTITY retorna o último valor de identity gerado na sessão, atravessando escopos — incluindo triggers disparadas pela própria instrução —, enquanto SCOPE_IDENTITY é isolado ao escopo que executou o INSERT. Em .NET: Se uma stored procedure chamada a partir do EF Core 8 (via `ExecuteSqlRaw`/`FromSqlRaw`) retorna @@IDENTITY como chave gerada, e a tabela alvo tem trigger AFTER INSERT que insere em outra tabela com identity, o valor devolvido ao .NET será o identity dessa outra tabela — corrompendo silenciosamente a chave primária atribuída à entidade após o SaveChanges. [TSQL-08-A-18, TSQL-08-A-8, TSQL-08-B-23, TSQL-08-C-7] {ACORDO 3 / media}
  - Limite: Aplica-se apenas quando existe trigger na tabela alvo; sem trigger, @@IDENTITY e SCOPE_IDENTITY retornam o mesmo valor. Nenhuma das duas é segura entre sessões diferentes — para isso só resta IDENT_CURRENT, que também não é seguro sob inserts concorrentes.
- **Refaça toda a unidade de trabalho após deadlock ou conflito SNAPSHOT** — Sob REPEATABLE READ o shared lock da leitura é mantido até o fim da transação; se duas transações concorrentes leem a mesma linha e depois tentam atualizá-la, nenhuma consegue obter o exclusive lock necessário porque a outra ainda segura o shared lock, e a situação vira deadlock. Em .NET: Uma transação EF Core 8 aberta com IsolationLevel.RepeatableRead que lê uma entidade e mais adiante chama SaveChangesAsync para atualizá-la — sob concorrência, ambas as sessões terminam em exceção de deadlock em vez de uma delas simplesmente esperar e ter sucesso depois. [TSQL-10-B-11, TSQL-10-B-14, TSQL-10-C-4, TSQL-10-C-5] {ACORDO 2 / media}
  - Limite: Não se aplica se apenas um lado do par ler-então-gravar existir por vez, sem leitura concorrente do mesmo recurso por ambas as transações.
- **Não use IDENTITY ou SEQUENCE como contador sem gaps; exponha a numeração definitiva somente após o commit** — a atribuição de variável T-SQL não participa do log/rollback da linha; se a transação for revertida após o UPDATE, a coluna volta ao estado anterior e fica disponível para reuso por outra sessão, mas a variável em memória da sessão que fez a leitura continua com o valor gerado, criando dessincronia entre o número que a aplicação acredita ter reservado e o que de fato persistiu. Em .NET: um serviço .NET 8 via ADO.NET que captura esse valor com ExecuteScalar dentro de uma transação mais ampla e já o expõe ao chamador (ex.: número de protocolo numa resposta HTTP) antes do commit final corre o risco de, num Rollback() posterior, permitir que o mesmo número seja gerado de novo por outra requisição. [TSQL-08-A-11, TSQL-08-B-10, TSQL-08-B-7, TSQL-08-C-6] {ACORDO 3 / media}
  - Limite: não se aplica se a aplicação só usa o valor retornado após confirmar commit bem-sucedido da transação inteira.
- **Alinhe os tipos dos ramos de operadores de conjunto** — O operador de conjunto só exige que o tipo de menor precedência seja implicitamente convertível para o de maior precedência entre colunas correspondentes; essa conversão ocorre silenciosamente e pode alterar precisão (truncar casas decimais), comprimento de string ou collation, sem erro de compilação da consulta. Em .NET: Unir via EF Core 8, com `.Union()`/`.Concat()`, uma projeção `decimal(10,4)` de uma tabela com uma projeção `decimal(10,2)` de outra tabela legada compila e executa normalmente, mas o tipo da coluna resultante segue a regra de precedência do SQL Server, truncando silenciosamente as casas decimais extras vindas da consulta de maior precisão. [TSQL-06-A-3, TSQL-06-B-7, TSQL-06-C-2] {ACORDO 3 / media}
  - Limite: Não se aplica quando ambas as consultas de entrada usam exatamente o mesmo tipo de coluna (mesma precisão/escala/collation), o que é automático quando as duas vêm da mesma entidade EF Core mapeada uma única vez.
- **Modele a unicidade de colunas anuláveis conforme a semântica do SQL Server** — O padrão SQL trata cada NULL como um valor "desconhecido" distinto e permitiria vários; o SQL Server, ao contrário, trata todos os NULLs como iguais para fins de unicidade, então o segundo INSERT com NULL viola a constraint. Em .NET: `modelBuilder.Entity<Customer>().HasIndex(c => c.Email).IsUnique()` sobre uma propriedade `string? Email` gera um índice único no SQL Server; inserir dois clientes com `Email = null` via EF Core 8 faz o segundo `SaveChanges()` lançar `DbUpdateException` envolvendo violação de unique index, mesmo que a intenção do modelo fosse "múltiplos e-mails ausentes permitidos". [TSQL-01-C-4, TSQL-02-B-6, TSQL-02-C-5] {ACORDO 2 / media}
  - Limite: Não se aplica a bancos com comportamento SQL padrão para UNIQUE (não é o caso do SQL Server); filtered unique index (`WHERE Email IS NOT NULL`) contorna o problema.
- **Reconstrua a tabela para alterar a propriedade IDENTITY** — SQL Server não permite adicionar nem remover a propriedade identity de uma coluna já existente via ALTER COLUMN; a única forma é recriar a tabela, copiar os dados e trocar. Em .NET: Uma migração do EF Core 8 que tenta mudar uma propriedade `Id` de `int` comum para `ValueGeneratedOnAdd()` (identity) ou vice-versa não pode ser expressa como um `AlterColumn` simples; a migração correta precisa criar tabela nova, copiar dados, remover a antiga e renomear — em tabela grande de produção isso implica bloqueio/indisponibilidade que uma revisão superficial da migração gerada não antecipa. [TSQL-08-A-6, TSQL-08-B-6, TSQL-08-C-8] {ACORDO 3 / media}
  - Limite: Nenhum conhecido para contornar via ALTER; a reconstrução é obrigatória independentemente do tamanho da tabela ou da versão do SQL Server mencionada no capítulo.
- **Finalize explicitamente a transação após qualquer erro** — Com XACT_ABORT desligado (o padrão), somente erros considerados severos disparam rollback automático; violações de chave primária/unicidade não encerram a transação — as instruções seguintes no mesmo lote continuam executando dentro da transação ainda aberta. Em .NET: Um script multi-instrução enviado via `context.Database.ExecuteSqlRawAsync()` dentro de uma transação explícita do EF Core 8, sem `SET XACT_ABORT ON` no início, onde uma segunda instrução (ex.: um UPDATE de auditoria) é executada e commitada mesmo depois que a primeira falhou com violação de constraint.   - Limite: Não se aplica a FIRST_VALUE com o quadro padrão implícito quando a intenção é "do início até a linha atual" — ali o comportamento padrão coincide com o caso mais comum, mas ainda assim deve ser explícito por razões de desempenho.
- **Calcule funções de janela antes da cláusula SET** — Funções de janela só podem aparecer nas cláusulas SELECT ou ORDER BY; T-SQL levanta o erro 4108 quando usadas na cláusula SET de uma modificação. Em .NET: Um dev que já usa EF Core 8 para tudo tenta "resolver" uma numeração de linhas via SQL bruto no próprio projeto, chamando `context.Database.ExecuteSqlRaw("UPDATE T SET Rank = ROW_NUMBER() OVER(ORDER BY Col1)")` para popular uma coluna de ranking, assumindo que, se ROW_NUMBER funciona em um SELECT, também funciona em um UPDATE direto. [TSQL-08-B-17, TSQL-08-C-19] {ACORDO 2 / media}
  - Limite: não se aplica se a numeração for calculada em uma expressão de tabela (CTE/derived table) e o UPDATE for feito contra essa expressão, que é o contorno padrão para esse cenário.
- **Trate explicitamente valores NULL ao concatenar com o operador +** — O padrão SQL define que uma concatenação envolvendo NULL deve produzir NULL — o operador `+` não tem noção de "valor ausente tratado como vazio"; só funções dedicadas como CONCAT/CONCAT_WS substituem NULL por string vazia automaticamente. Em .NET: O EF Core 8 traduz a concatenação de strings do LINQ (`a + b` em C#, onde `null + "x"` produz `"x"` porque o operador `+` do CLR trata null como string vazia) usando a função `CONCAT` do SQL Server por padrão, não o operador `+`, justamente para preservar essa semântica do C#; só ao escrever SQL cru com `+` (Dapper/ADO.NET/FromSqlRaw) o dev reintroduz a propagação de NULL que o C# não tem. [TSQL-02-A-9, TSQL-02-C-14] {ACORDO 2 / alta}
  - Limite: Não se aplica quando se usa explicitamente CONCAT/CONCAT_WS em SQL cru, que já replicam a semântica de substituição por string vazia do C#.
- **Teste valores e parâmetros NULL com IS NULL, não com igualdade simples** — Na lógica de três valores do SQL Server, qualquer comparação de igualdade envolvendo NULL — inclusive NULL = NULL — avalia UNKNOWN, e cláusulas WHERE/ON descartam linhas UNKNOWN, não apenas as FALSE. Em .NET: SQL bruto executado via EF Core 8 (`FromSqlRaw` ou stored procedure) com `WHERE Coluna = @parametro`, onde `@parametro` chega NULL em tempo de execução (ex.: filtro opcional não informado), devolve zero linhas — inclusive as que têm Coluna NULL — mesmo que a intenção fosse ignorar o filtro ou casar nulos. [TSQL-02-B-3, TSQL-03-B-7] {ACORDO 1 / media}
  - Limite: Não se aplica a comparações usando IS NULL, IS NOT DISTINCT FROM, ou quando o parâmetro nunca pode ser NULL em tempo de execução.
- **Defina os nomes das colunas do resultado no primeiro ramo do UNION** — o SQL Server nomeia as colunas do resultado de um operador de conjunto usando somente os nomes/aliases da primeira consulta de entrada; qualquer alias definido apenas na segunda consulta é descartado na saída final, mesmo que as duas consultas sejam sintaticamente válidas isoladamente. Em .NET: se a primeira SELECT de um `UNION ALL` passado a `FromSqlRaw<Dto>` referenciar a coluna física sem alias (`SELECT Country, Region, City FROM ...`) e a propriedade do DTO esperar o nome `Pais` (definido como alias só na segunda SELECT do UNION), o EF Core não encontra a coluna `Pais` no result set e falha ao materializar o DTO. [TSQL-06-A-4, TSQL-06-B-8] {ACORDO 2 / media}
  - Limite: só relevante para SQL bruto composto manualmente (FromSqlRaw, views, stored procedures); consultas LINQ com `Union`/`Concat` sempre usam o mesmo tipo/nomes de propriedade nos dois lados por exigência do compilador C#, então o problema não ocorre.
- **Agrupe operadores de conjunto com parênteses para explicitar a precedência** — INTERSECT tem precedência maior que UNION e EXCEPT, que são avaliados na ordem de aparição no texto; essa regra é fácil de ler errado, e o uso de ALL não altera a precedência. Em .NET: Uma stored procedure ou bloco de SQL cru via `FromSqlRaw` em EF Core 8 combinando `... EXCEPT ... INTERSECT ...` sem parênteses é avaliado como `Query1 EXCEPT (Query2 INTERSECT Query3)`, não na ordem visual do texto, alterando o resultado de negócio sem erro de sintaxe. [TSQL-06-A-5, TSQL-06-C-10] {ACORDO 2 / alta}
  - Limite: Essa ambiguidade só existe em texto SQL puro (raw SQL, procedures, views); não se manifesta ao compor os mesmos operadores via encadeamento de métodos LINQ, onde a ordem de avaliação é definida pela ordem das chamadas em C#.
- **Modifique apenas as colunas atualizáveis de um único lado do join** — uma table expression não armazena dados — é uma reescrita lógica resolvida contra as tabelas base; o motor precisa mapear cada coluna alvo de volta para exatamente uma coluna física de uma única tabela base, e uma coluna derivada de expressão (ex.: discount + 0.05 AS newdiscount) não tem coluna física correspondente para receber a escrita. Em .NET: uma rotina de manutenção em .NET 8 que executa UPDATE via CTE (ExecuteSqlRaw com WITH C AS (SELECT ... JOIN ...) UPDATE C SET colA = colB) para simular um UPDATE com join mais legível falha em tempo de execução se o desenvolvedor tentar, na mesma instrução, também alterar uma coluna do outro lado do join ou uma coluna calculada da projeção. [TSQL-08-A-13, TSQL-08-B-18] {ACORDO 2 / media}
  - Limite: não se aplica quando a table expression envolve apenas uma tabela base, caso em que não há ambiguidade de destino.
- **Trate inserções multivaloradas como atômicas e delimite explicitamente sua atomicidade** — Um INSERT VALUES ou INSERT SELECT com múltiplas linhas roda como uma única transação implícita — se qualquer linha falhar, nenhuma é gravada — mas essa garantia é local à instrução, não a um conjunto de instruções relacionadas. Em .NET: Um `SaveChanges()` do EF Core 8 que insere várias entidades novas gera essa mesma garantia de tudo-ou-nada para as instruções daquela chamada, mas duas chamadas separadas a `SaveChanges()` no mesmo `DbContext` não compartilham a atomicidade — a segunda pode persistir mesmo que a primeira já tenha sido revertida por outro motivo, a menos que ambas sejam envolvidas manualmente em uma `IDbContextTransaction`. [TSQL-08-B-1, TSQL-08-C-1] {ACORDO 2 / media}
  - Limite: A atomicidade documentada só vale para uma instrução INSERT multivalorada (ou uma chamada `SaveChanges()`); não cobre múltiplas chamadas, múltiplos DbContexts, nem lotes de `SaveChanges` sucessivos sem transação explícita.
- **Remova ou trate as foreign keys antes de usar TRUNCATE** — TRUNCATE é rejeitado sempre que a tabela alvo é referenciada por qualquer FK, mesmo que a tabela referenciadora esteja vazia ou a FK esteja desabilitada; a única solução é remover a constraint antes. Em .NET: Um helper .NET de limpeza de testes que executa `TRUNCATE TABLE dbo.Orders` via `ExecuteSqlRaw` lança `SqlException` assim que o modelo do EF Core ganha qualquer relacionamento de FK apontando para `Orders`, mesmo que a tabela filha esteja vazia — quebrando um helper que funcionava em versões anteriores do schema. [TSQL-08-B-11, TSQL-08-C-14] {ACORDO 2 / media}
  - Limite: Desabilitar a FK (`NOCHECK CONSTRAINT`) não é suficiente para permitir o TRUNCATE; é necessário removê-la (DROP CONSTRAINT) e recriá-la depois.
- **Projete explicitamente as colunas de período ocultas** — a opção HIDDEN faz o SQL Server omitir as colunas de qualquer expansão de SELECT * e de INSERT sem lista de colunas explícita, mas as colunas continuam existindo fisicamente no schema e podem ser lidas por nome; a ocultação é uma conveniência de expansão sintática do motor, não uma remoção real da coluna. Em .NET: um serviço .NET 8 que executa SELECT * FROM dbo.Employees via ADO.NET/Dapper contra essa tabela não recebe as colunas validfrom/validto no SqlDataReader, mesmo que o schema físico as contenha; é preciso escrever SELECT empid, ..., validfrom, validto explicitamente para obtê-las. [TSQL-09-A-12, TSQL-09-B-4] {ACORDO 2 / media}
  - Limite: não se aplica se as colunas de período não tiverem sido marcadas com a opção HIDDEN na criação/alteração da tabela.
## Performance

- **Não altere a projeção de EXISTS por suposto ganho de desempenho** — O predicado EXISTS só precisa responder "a subquery produziu ao menos uma linha?", então o otimizador nunca materializa nem usa as colunas da lista SELECT para decidir índices ou operadores do plano — a única fase que toca a lista de colunas é a resolução/binding de nomes (para checar permissões e existência das colunas), que é comparável entre `*` e `1` e ocorre fora do laço de execução. Em .NET: Em stored procedures, views ou blocos `FromSqlRaw` chamados a partir do EF Core 8 que usam `IF EXISTS(SELECT ...)`, trocar `*` por `1` dentro do EXISTS não muda o plano medido; o próprio `.Any()` do LINQ do EF Core já gera a forma equivalente automaticamente, tornando essa microotimização manual desnecessária mesmo em SQL escrito à mão. [TSQL-04-A-8, TSQL-04-B-5, TSQL-04-C-5] {ACORDO 3 / alta}
  - Limite: Não vale para SELECT fora de um predicado EXISTS — nesse contexto a lista de colunas tem custo real de materialização e a escolha de colunas importa.
- **Teste existência com Any ou EXISTS** — EXISTS (e IN) permite ao motor parar assim que encontra a primeira linha correspondente, funcionando como uma checagem de curto-circuito; contar todas as linhas correspondentes para depois comparar com zero exige que o motor processe o conjunto de correspondências inteiro antes de responder à mesma pergunta booleana. Em .NET: Em EF Core 8, `ctx.Orders.Any(o => o.CustomerId == id)` traduz para `EXISTS` com curto-circuito, enquanto `ctx.Orders.Count(o => o.CustomerId == id) > 0` traduz para uma agregação `COUNT(*)` completa seguida de comparação — mesma resposta booleana, custo potencialmente muito maior quando a coluna filtrada tem baixa seletividade em tabela grande. [TSQL-04-A-12, TSQL-04-B-8, TSQL-04-C-12] {ACORDO 3 / media}
  - Limite: A diferença de custo só é relevante quando o número de linhas correspondentes pode ser grande (baixa seletividade) em tabela sem índice adequado; em tabelas pequenas ou com índice altamente seletivo casando poucas linhas, o custo de COUNT completo e de EXISTS converge e a distinção deixa de ser prática.
- **Use UNION ALL somente para fontes comprovadamente disjuntas** — a variante DISTINCT (UNION) precisa comparar todas as linhas combinadas entre si para eliminar duplicatas, o que exige uma etapa extra de ordenação ou hashing no plano de execução; a variante ALL (UNION ALL) apenas concatena as linhas, sem essa etapa — quando os dois conjuntos de entrada não podem ter linhas em comum, o resultado das duas variantes é idêntico, mas só a ALL evita o custo de eliminação. Em .NET: `ctxA.Select(...).Union(ctxB.Select(...))` gera UNION e adiciona um operador de agregação/ordenação ao plano do SQL Server mesmo quando `ctxA` e `ctxB` já são particionados por uma coluna discriminadora (por exemplo, um ano ou um tipo) que garante ausência de sobreposição; trocar por `.Concat(...)` produz o mesmo resultado final sem essa etapa extra. [TSQL-06-A-2, TSQL-06-B-1, TSQL-06-C-7] {ACORDO 3 / media}
  - Limite: não se aplica quando duplicatas entre as duas fontes são realmente possíveis e precisam ser removidas — nesse caso UNION é necessário.
- **Atualize no MERGE somente quando os valores tiverem mudado** — por padrão a cláusula WHEN MATCHED dispara UPDATE para toda linha correspondida pela condição de junção, independentemente de qualquer coluna ter mudado; o motor apenas casa chaves e executa a ação declarada, então mesmo um UPDATE que reescreve os mesmos valores conta como escrita física completa da linha. Em .NET: uma coluna RowVersion/Timestamp usada como token de concorrência otimista pelo EF Core 8 muda de valor em toda execução de um job de sincronização via MERGE sem predicado diferencial, mesmo quando nenhum dado de negócio realmente mudou, porque o SQL Server incrementa o rowversion em qualquer UPDATE físico da linha. [TSQL-08-A-14, TSQL-08-B-21, TSQL-08-C-21] {ACORDO 3 / baixa}
  - Limite: não se aplica quando a tabela alvo não tem coluna rowversion/timestamp nem triggers sensíveis a UPDATE físico — nesse caso a regravação é apenas custo de I/O.
- **Considere o Recovery Model ao avaliar minimal logging e cargas em massa** — o modo de log mínimo grava apenas a alocação de extents em vez de cada linha individual, e só é elegível quando o modelo de recuperação é SIMPLE ou BULK_LOGGED; sob FULL o motor precisa preservar log linha a linha para permitir restauração point-in-time, então a mesma instrução vira uma operação totalmente logada. Em .NET: um job de seed em .NET 8 usando ExecuteSqlRaw("SELECT ... INTO staging_table FROM ...") que roda em segundos em staging (recovery SIMPLE) pode ter a mesma duração de um INSERT totalmente logado ao rodar contra produção (tipicamente FULL), sem nenhuma mudança de código. [TSQL-08-A-4, TSQL-08-B-4, TSQL-08-C-5] {ACORDO 3 / baixa}
  - Limite: não se aplica se a tabela de destino já existe (SELECT INTO só cria tabela nova), nem a Azure SQL Database com modelo de recuperação simplificado por padrão.
- **Prefira TRUNCATE para apagar grandes volumes quando seu uso for permitido** — DELETE registra no log de transação a remoção individual de cada linha, o que se traduz em I/O de log proporcional ao número de linhas; TRUNCATE registra apenas a desalocação de páginas/extents inteiros, com custo de log praticamente constante independentemente da quantidade de linhas. Em .NET: um endpoint administrativo em .NET 8 que implementa "esvaziar tabela" via context.Set<T>().ExecuteDeleteAsync() (EF Core 8, que sempre traduz para DELETE, nunca TRUNCATE) numa tabela de milhões de linhas de log/histórico expõe a aplicação a timeout de comando ou bloqueios longos que ExecuteSqlRaw("TRUNCATE TABLE ...") evitaria. [TSQL-08-A-17, TSQL-08-B-14, TSQL-08-C-26] {ACORDO 3 / baixa}
  - Limite: não se aplica quando é necessário excluir apenas um subconjunto de linhas (TRUNCATE não aceita filtro), nem quando triggers de exclusão precisam disparar por linha (TRUNCATE não dispara triggers DELETE).
- **Explicite e alinhe o tipo dos parâmetros ao tipo da coluna** — Quando os dois lados de uma comparação têm tipos de dados diferentes, o tipo de precedência mais baixa é implicitamente convertido para o mais alto; se a coluna é VARCHAR e o parâmetro chega como NVARCHAR (ou vice-versa), a conversão implícita acontece do lado da coluna, o que impede o otimizador de usar um índice em busca (seek) sobre essa coluna, forçando varredura completa. Em .NET: O ADO.NET/EF Core 8 mapeia `string` do C# para `NVARCHAR` por padrão ao criar parâmetros; se a coluna do banco foi definida como `VARCHAR` (comum em bancos legados ou colunas configuradas com `.IsUnicode(false)`), toda comparação parametrizada sofre conversão implícita silenciosa no lado da coluna, mesmo havendo índice nela. [TSQL-02-A-10, TSQL-02-A-11] {ACORDO 1 / media}
  - Limite: Não se aplica quando a coluna já é NVARCHAR, ou quando `.IsUnicode(false)` foi explicitamente configurado no `OnModelCreating` para colunas VARCHAR, alinhando o tipo do parâmetro gerado.
- **Não adicione DISTINCT desnecessário dentro de IN** — O predicado IN testa apenas pertencimento a um conjunto — duplicatas no lado direito não mudam se um valor pertence ou não ao conjunto —, e o otimizador já reconhece essa propriedade ao gerar o plano de semi-junção, eliminando (ou nunca materializando) as duplicatas internamente antes de qualquer DISTINCT explícito ter efeito adicional no resultado ou no custo. Em .NET: `.Where(x => ctx.Orders.Select(o => o.CustomerId).Distinct().Contains(x.CustomerId))` no EF Core 8 gera uma etapa de deduplicação (`SELECT DISTINCT`) extra que não muda o plano final comparado à mesma consulta sem `.Distinct()` antes de `.Contains()` — é código a mais sem ganho de custo, medível por leituras lógicas equivalentes. [TSQL-04-A-10, TSQL-04-C-8] {ACORDO 2 / alta}
  - Limite: Não se aplica quando DISTINCT é necessário por outro motivo, como quando a mesma subquery é reaproveitada em um contexto que expõe as linhas (não só o teste de pertencimento).
- **Restrinja a entrada do PIVOT às colunas necessárias** — O PIVOT deriva o elemento de agrupamento por eliminação — todas as colunas da entrada que não são o elemento de propagação nem o de agregação viram, implicitamente, colunas de GROUP BY; qualquer coluna extra (como uma chave de linha) fragmenta os grupos. Em .NET: Uma consulta raw SQL em EF Core 8 (`FromSqlRaw`) que aplica `PIVOT(SUM(Qtd) FOR ClienteId IN([A],[B],[C])) AS P` diretamente sobre a tabela `Pedidos` (que ainda tem a coluna `PedidoId`) devolve uma linha por pedido em vez de uma linha por funcionário, porque `PedidoId` entra no conjunto de agrupamento implícito. [TSQL-07-B-6, TSQL-07-C-8] {ACORDO 2 / alta}
  - Limite: Não se aplica quando a tabela de origem já contém exatamente as colunas de agrupamento, propagação e agregação necessárias, sem nenhuma coluna adicional.
- **Filtre datas com intervalos sargáveis** — Quando um filtro envolve manipulação da coluna (como `YEAR(orderdate) = 2021`), o motor não consegue, na maioria dos casos, usar diretamente um índice na coluna original para busca (seek), porque o valor indexado é o valor bruto da coluna, não o resultado da função aplicada a ele; o motor teria que calcular a função para cada linha, degradando para varredura. Em .NET: `dbSet.Where(o => o.OrderDate.Year == 2021)` no EF Core 8 traduz literalmente para `WHERE YEAR(orderdate) = 2021`, preservando o mesmo problema de não-sargabilidade descrito no capítulo — o LINQ, por ser expressivo o suficiente para chamar `.Year`, não impede o dev de escrever a versão ineficiente; só reescrever como `o.OrderDate >= inicio && o.OrderDate < fim` produz um filtro de intervalo sargável. [TSQL-02-A-14, TSQL-02-B-20] {ACORDO 2 / media}
  - Limite: Não se aplica quando não existe índice útil na coluna de qualquer forma, nem a colunas computadas persistidas e indexadas que já materializam o resultado da função.
- **Use CTEs para evitar duplicação textual, mas considere o custo de cada referência** — Como a expressão de tabela é expandida e não materializada, cada ponto de referência no FROM gera sua própria varredura e processamento da consulta subjacente; não existe cache implícito entre as referências dentro da mesma execução. Em .NET: Uma CTE T-SQL usada duas vezes para calcular "ano atual" e "ano anterior" num relatório de crescimento (`FromSqlInterpolated` no EF Core 8 ou stored procedure chamada via ADO.NET) faz o SQL Server varrer e agregar a tabela base duas vezes; se o volume de dados justificar evitar essa repetição, é necessário persistir o resultado intermediário numa tabela temporária real (`#temp`) via `ExecuteSqlRaw`, não confiar na CTE. [TSQL-05-B-4, TSQL-05-C-7] {ACORDO 2 / alta}
  - Limite: Não se aplica a casos em que o otimizador consegue eliminar a segunda varredura por outros meios (por exemplo, um índice que cobre totalmente o predicado, tornando o custo da segunda varredura desprezível).
- **Calcule totais correntes com função de janela** — Uma subquery correlacionada é avaliada logicamente uma vez para cada linha da consulta externa; para um total acumulado sobre N linhas isso significa N agregações separadas, cada uma potencialmente somando até N linhas — um custo que cresce quadraticamente com o número de linhas, enquanto uma função de janela computa o mesmo resultado em uma única passada ordenada. Em .NET: Uma projeção LINQ em EF Core 8 como `ctx.Sales.Select(o => new { o, Total = ctx.Sales.Where(o2 => o2.Year <= o.Year).Sum(o2 => o2.Qty) })` é traduzida em uma subquery correlacionada por linha; para uma tabela de poucas centenas de linhas isso passa despercebido, mas em uma tabela com dezenas de milhares de linhas o tempo de execução no SQL Server cresce muito mais rápido do que o de uma consulta com `SUM(...) OVER (ORDER BY ...)` escrita via SQL bruto (`FromSqlRaw`). [TSQL-04-B-7, TSQL-04-C-9] {ACORDO 2 / media}
  - Limite: Não se aplica a tabelas pequenas (dezenas a poucas centenas de linhas) ou a consultas executadas raramente fora de um caminho quente, onde o custo quadrático é irrelevante perto de outros custos do sistema.
- **Considere os range locks impostos por SERIALIZABLE** — SERIALIZABLE bloqueia logicamente todo o intervalo de chaves que qualifica para o filtro da consulta, incluindo linhas que ainda não existem; isso impede que outra transação insira uma linha nova que se qualificaria para o mesmo filtro até que a transação leitora termine. Em .NET: Um relatório em EF Core 8 aberto com IsolationLevel.Serializable que filtra por categoria para ter certeza que os dados não mudam durante o relatório também bloqueia qualquer INSERT concorrente de um novo produto na mesma categoria, mesmo que esse insert não toque nenhuma linha já lida. [TSQL-10-B-13, TSQL-10-C-9] {ACORDO 2 / alta}
  - Limite: Não se aplica a SNAPSHOT, que oferece a mesma prevenção de phantom read sem bloquear escritores.
- **Use funções de janela para totais correntes e outros cálculos por linha** — o quadro ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW restringe, para cada linha, a janela a todas as linhas da partição desde o início até a linha atual; a engine calcula esse total em uma única passada ordenada sobre a partição, enquanto tanto uma subquery correlacionada por linha quanto um laço em C# recalculam a soma do zero para cada linha, custando trabalho proporcional ao quadrado do número de linhas na partição no pior caso. Em .NET: um serviço .NET 8 que materializa os pedidos de um funcionário via EF Core 8 e calcula o saldo corrente com um `foreach` acumulando `runningTotal += order.Val` faz uma única passada; mas se em vez disso o total corrente for obtido consultando o banco pedido a pedido dentro de um loop (uma query por linha), o custo cresce quadraticamente com o número de pedidos. [TSQL-04-A-11, TSQL-07-A-2] {ACORDO 1 / baixa}
  - Limite: não se aplica quando o total corrente já pode ser mantido incrementalmente em memória durante uma única leitura sequencial dos dados já ordenados, sem re-consultar o banco por linha.
- **Deixe o otimizador escolher a ordem dos inner joins** — A ordem em que os operadores de tabela são escritos fixa apenas o resultado lógico (baseado em álgebra relacional), não a ordem física de execução; o otimizador do SQL Server é livre para rearranjar internamente cross e inner joins com base em estimativas de cardinalidade e índices, desde que o conjunto de resultados produzido permaneça idêntico — a ordem textual dos Joins no LINQ não garante nenhum efeito sobre o plano de execução gerado. Em .NET: Escrever `context.A.Join(B,...).Join(C,...)` em vez de `context.C.Join(B,...).Join(A,...)` produz T-SQL logicamente equivalente contra o SQL Server; o plano de execução real é decidido pelo otimizador com base em estatísticas e índices, não pela ordem textual dos Joins no LINQ. [TSQL-03-A-7, TSQL-03-B-9] {ACORDO 2 / media}
  - Limite: Não se aplica quando há um outer join na cadeia, pois nesse caso a ordem em que os joins são processados altera o resultado lógico, não apenas o plano físico, e portanto não pode ser rearranjada livremente.
- **Meça antes de substituir JOIN por subquery** — O otimizador do SQL Server às vezes produz o mesmo plano de execução para uma consulta escrita com subquery e sua equivalente com JOIN, mas nem sempre; qual forma é mais rápida depende de estatísticas, índices e versão do motor, então não existe uma regra fixa de qual construção é sempre superior. Em .NET: Em code review de LINQ no EF Core 8, rejeitar um `ctx.Orders.Where(o => ctx.Employees.Any(e => e.Id == o.EmpId && e.LastName.StartsWith("D")))` em favor de um `Join` explícito — só porque "join é sempre mais rápido que subquery" — é uma decisão sem base, já que o EF Core pode gerar o mesmo plano físico no SQL Server para as duas formas. [TSQL-04-B-6, TSQL-04-C-11] {ACORDO 2 / media}
  - Limite: Não se aplica quando a escolha entre IN/EXISTS e JOIN muda a semântica do resultado por causa de NULLs (ver item sobre NOT IN vs NOT EXISTS); nesse caso a decisão deve ser guiada por correção, não por performance.
- **Indexe a coluna usada na correlação** — Logicamente a subquery correlacionada é reavaliada para cada linha da consulta externa porque seu resultado depende do valor correlacionado daquela linha; fisicamente, sem um índice que permita localizar diretamente as linhas internas que casam esse valor, o motor precisa varrer (ou re-varrer) a tabela interna inteira a cada nova sonda externa, fazendo o custo total escalar com o produto das cardinalidades das duas tabelas em vez da soma. Em .NET: LINQ do EF Core 8 como `.Select(o => o.Customer.Orders.Max(x => x.OrderId))`, ou qualquer subquery correlacionada embutida em `.Select()`/`.Where()` por agregação sobre uma navegação, herda esse custo por linha; a mitigação de código é configurar o índice na FK usada como correlação (`modelBuilder.Entity<Order>().HasIndex(o => o.CustomerId)`) antes de liberar esse padrão em produção. [TSQL-04-A-6] {ACORDO 1 / media}
  - Limite: Não se aplica quando o otimizador consegue reescrever a subquery correlacionada como junção com hash ou merge sem depender de acesso por índice — comum quando não há filtro seletivo adicional na correlação.
- **Não aguarde I/O externo com uma transação aberta** — O lock exclusivo obtido por uma modificação é mantido até o fim da transação; qualquer tempo adicional entre a modificação e o commit, inclusive tempo gasto esperando uma resposta externa, estende proporcionalmente a duração desse lock e a espera de qualquer sessão concorrente que precise do mesmo recurso. Em .NET: Um método assíncrono em C# 12 que abre `await context.Database.BeginTransactionAsync()`, executa um UPDATE via EF Core 8, depois faz `await httpClient.PostAsync(...)` para notificar um serviço externo, e só então chama `CommitAsync()` — o lock exclusivo da linha fica retido pela latência de rede do serviço externo, não apenas pelo tempo da instrução SQL. [TSQL-10-B-5] {ACORDO 1 / media}
  - Limite: Não se aplica se a chamada externa ocorrer antes do BEGIN TRAN ou depois do COMMIT/ROLLBACK.
- **Não espere otimização por mero encapsulamento da consulta** — T-SQL nunca materializa uma expressão de tabela fisicamente; toda referência a ela é expandida ("inlined") na consulta externa antes da otimização, então o plano final é idêntico ao da consulta equivalente escrita sem a expressão de tabela. Em .NET: Trocar uma consulta LINQ complexa por uma chamada a uma view mapeada via `ToView` ou a uma inline TVF chamada via `FromSqlInterpolated` no EF Core 8, na expectativa de que o SQL Server "cacheie" o resultado da view entre chamadas, não reduz custo de I/O nem tempo de CPU — o plano de execução gerado é o mesmo da consulta expandida. [TSQL-05-B-3] {ACORDO 1 / alta}
  - Limite: Não se aplica quando a view é combinada com materialização real (view indexada com SCHEMABINDING e índice clustered, ou tabela temporária) — nesses casos há armazenamento físico e o ganho é real.
- **Indexe considerando o resultado combinado da consulta** — o T-SQL não permite aplicar WHERE, GROUP BY ou HAVING diretamente sobre o resultado de um operador de conjunto na mesma consulta — apenas ORDER BY é aceito nesse nível; qualquer outra fase exige definir uma tabela derivada baseada na consulta com o operador e aplicar a fase na consulta externa, o que introduz um nível extra de processamento sobre o conjunto já combinado. Em .NET: `ctxA.Select(...).Concat(ctxB.Select(...)).GroupBy(x => x.Country).Select(g => new { g.Key, Count = g.Count() })` sempre gera SQL com o UNION ALL envolto em `FROM (...) AS T` seguido de `GROUP BY Country` na consulta externa; não existe tradução alternativa em que o GROUP BY seja empurrado para dentro de uma das metades do UNION, então um índice isolado em cada tabela de origem não elimina a etapa de agregação sobre o conjunto unificado. [TSQL-06-A-7] {ACORDO 1 / media}
  - Limite: nenhum conhecido — vale para qualquer fase lógica além de ORDER BY aplicada sobre Concat/Union/Except/Intersect.
- **Orce no deploy o custo da verificação do histórico temporal** — Ao habilitar SYSTEM_VERSIONING apontando para uma tabela de histórico já existente, SQL Server valida esquema e ausência de sobreposição de períodos entre as linhas antes de aceitar a operação. Em .NET: Uma migration EF Core 8 que execute via `migrationBuilder.Sql(...)` o ALTER TABLE que habilita SYSTEM_VERSIONING contra uma tabela de histórico com grande volume de linhas pode travar `dotnet ef database update` por um tempo desproporcional ao resto da migration, mesmo sem nenhum erro de sintaxe. [TSQL-09-C-10] {ACORDO 1 / media}
  - Limite: Não se aplica quando a tabela de histórico é criada vazia pelo próprio CREATE TABLE (cenário padrão), nem quando se desabilita explicitamente a verificação de consistência (aceitando o risco de dados inconsistentes não detectados).
- **Avalie RCSI para reduzir bloqueios de leitura** — Sob READ_COMMITTED_SNAPSHOT, o leitor não solicita shared lock — o SQL Server entrega a última versão commitada da linha a partir do version store; isso elimina a espera do leitor por um lock exclusivo de escritor, mas exige que todo UPDATE/DELETE copie a versão anterior da linha para o version store antes da mudança, aumentando o custo de escrita. Em .NET: Uma API com EF Core 8 sob leitura e escrita concorrentes na mesma tabela, com READ COMMITTED padrão, sofre bloqueios em cascata (SELECTs esperando UPDATEs); habilitar RCSI no banco remove essa espera sem alterar nenhuma linha de código C#, mas aumenta o I/O em tempdb proporcional ao volume de UPDATE/DELETE. [TSQL-10-A-6] {ACORDO 1 / alta}
  - Limite: Não elimina a necessidade de locks de escrita nem previne atualizações perdidas; não pode ser ativado por sessão/query — é uma flag de banco que exige acesso exclusivo ao banco para ser ligada.
- **Verifique os índices antes de redesenhar transações** — Sem um índice que atenda ao filtro, o SQL Server precisa varrer (e travar) todas as linhas da tabela ou página para localizar as que interessam, mesmo que duas transações concorrentes filtrem chaves totalmente diferentes; o conflito de lock passa a existir por causa da varredura, não porque as transações disputam o mesmo dado de negócio. Em .NET: Duas chamadas concorrentes de SaveChanges() no EF Core 8 que fazem UPDATE em linhas distintas filtrando por uma coluna sem índice podem deadlockar entre si mesmo operando sobre chaves diferentes, porque cada UPDATE varre e trava linhas além das que realmente modifica. [TSQL-10-A-11] {ACORDO 1 / alta}
  - Limite: Não se aplica se as colunas de filtro já têm índice adequado — nesse caso, deadlocks recorrentes indicam conflito de dados real.
- **Reutilize o índice criado pela constraint UNIQUE** — PRIMARY KEY e UNIQUE recebem índice único físico do SQL Server para impor a regra. Em .NET: Criar um segundo índice UNIQUE para a mesma coluna após migrar EF Core 8 duplica manutenção e espaço sem nova garantia lógica, penalizando INSERT e UPDATE. [TSQL-01-B-31] {ACORDO 1 / alta}
  - Limite: Um índice adicional pode se justificar por chave de acesso diferente, não por repetir a unicidade.
- **Evite FORMAT em grandes volumes** — FORMAT depende internamente do motor de formatação do CLR hospedado dentro do SQL Server para interpretar strings de formato arbitrárias, com overhead por chamada ordens de magnitude maior do que os caminhos nativos de CONVERT/CAST, resolvidos diretamente pelo motor relacional sem cruzar a fronteira do CLR hospedado. Em .NET: Se uma projeção do EF Core 8 for traduzida pelo provider SQL Server para usar FORMAT (formatação de data customizada num `.Select()`), ou se um dev escrever isso manualmente em `FromSqlRaw`, o custo por linha se acumula da mesma forma que o benchmark do capítulo — quase um minuto contra menos de um segundo em 1 milhão de linhas — tornando relatórios com FORMAT numa tabela grande visivelmente mais lentos que alternativas equivalentes com CONVERT/estilo numérico. [TSQL-02-A-13] {ACORDO 1 / media}
  - Limite: Não se aplica a chamadas pontuais de FORMAT sobre poucas linhas (ex.: um único valor agregado), onde o overhead por chamada é irrelevante.
## Manutenção

- **Habilite mensagens detalhadas de truncamento somente após validar o suporte da versão** — a validação de tamanho de string/binário ocorre no mesmo ponto em qualquer nível de compatibilidade, mas o motor só anexa metadados (nome de tabela, coluna e valor truncado) à mensagem de erro quando o banco roda sob o modelo de compatibilidade 150 ou superior; abaixo disso, retorna apenas a mensagem genérica 8152. Em .NET: uma exceção SqlException capturada num try/catch em torno de SaveChangesAsync (EF Core 8) ou ExecuteNonQueryAsync (ADO.NET), contra um banco com nível de compatibilidade herdado (ex.: migrado de versão antiga sem ALTER DATABASE ... SET COMPATIBILITY_LEVEL), chega ao tratamento sem indicar qual propriedade causou o truncamento. [TSQL-08-A-2, TSQL-08-B-5, TSQL-08-C-2] {ACORDO 3 / media}
  - Limite: não se aplica a Azure SQL Database, que já roda em compatibilidade recente por padrão, nem a violações de CHECK/FK, que sempre incluem o nome da constraint.
- **Projete somente as colunas necessárias e acesse-as por nome** — SQL preserva posições ordinais conforme a ordem do CREATE TABLE (ao contrário do modelo relacional puro), então qualquer alteração de schema que reordene colunas muda silenciosamente o que `SELECT *` devolve, sem erro de compilação em quem consome por posição. Em .NET: Um `DbDataReader` lido por índice ordinal (`reader.GetInt32(0)`) a partir de `SELECT * FROM Sales.Orders` num Dapper/ADO.NET cru quebra silenciosamente assim que a tabela é reconstruída com colunas em outra ordem (ex.: uma ferramenta de design que faz drop+recreate para reordenar); o EF Core 8, por materializar por nome de coluna mapeado na entidade, é imune a esse risco específico, mas apenas enquanto as colunas explícitas do modelo continuarem existindo. [TSQL-02-A-5, TSQL-02-C-20] {ACORDO 2 / media}
  - Limite: Não se aplica a leitura por nome de coluna (`reader.GetOrdinal("col")` ou mapeamento por nome via Dapper/EF Core), que permanece correta mesmo com reordenação de colunas.
- **Preserve definições exigidas pelas ferramentas** — ENCRYPTION grava a definição do objeto em formato ofuscado; `OBJECT_DEFINITION` retorna NULL e `sp_helptext` retorna apenas uma mensagem informando que o texto está criptografado — não há caminho suportado para recuperar o texto original. Em .NET: Rodar `dotnet ef dbcontext scaffold` contra um banco cuja view esteja marcada WITH ENCRYPTION resulta em uma entidade sem a lógica de origem documentável, e qualquer ferramenta interna que gere documentação ou compare definições de views entre ambientes a partir de `OBJECT_DEFINITION` falha silenciosamente (retorna NULL) para esse objeto especificamente. [TSQL-05-A-14, TSQL-05-B-10] {ACORDO 2 / media}
  - Limite: Não se aplica quando a definição da view nunca precisa ser lida programaticamente, por exemplo quando ENCRYPTION é usada apenas para restringir acesso via permissões, sem necessidade de auditoria de texto.
- **Qualifique objetos com o schema** — O schema é namespace e, quando omitido, SQL Server tenta resolver o objeto no schema padrão do usuário e depois em dbo, podendo escolher um objeto diferente. Em .NET: Gere ou escreva SQL Server/EF Core 8 com schema explícito, como `Sales.Orders`, para tornar a resolução determinística. [TSQL-01-A-35, TSQL-01-C-18] {ACORDO 2 / media}
  - Limite: O capítulo não trata objetos temporários ou regras de resolução além do padrão descrito.
- **Extraia para uma CTE a lógica de subquery usada mais de uma vez** — Uma CTE é nomeada numa cláusula WITH antes da cláusula FROM da query externa ser processada, então, do ponto de vista do FROM, o nome da CTE já existe como objeto citável — isso permite dar dois aliases diferentes à mesma definição dentro de um join, mantendo só uma cópia do texto da query. Em .NET: Ao escrever SQL bruto para EF Core 8 via `FromSqlRaw` que precisa comparar linhas com as do período anterior (self-join), definir a lógica uma vez como CTE e referenciá-la duas vezes no FROM evita manter duas cópias do texto SQL sincronizadas manualmente, do mesmo jeito que o capítulo demonstra em T-SQL puro. [TSQL-05-A-8, TSQL-05-B-12] {ACORDO 2 / alta}
  - Limite: Nenhum conhecido dentro do escopo de uma única instrução; CTEs continuam de escopo único-statement, não sobrevivendo além da query que as define.
- **Qualifique objetos com nomes de duas partes** — Sem schema, SQL Server tenta o schema padrão do usuário e depois dbo; objetos homônimos em schemas diferentes podem resolver para o objeto errado. Em .NET: Use Sales.Orders em SQL ou raw SQL e configure schema explícito no EF Core 8; a consulta SQL Server deixa de depender do usuário conectado. [TSQL-01-A-30, TSQL-01-B-18] {ACORDO 2 / media}
  - Limite: Nenhum conhecido.
- **Configure e provisione filegroups explicitamente** — Tabelas memory-optimized (In-Memory OLTP) exigem uma filegroup do banco marcada como contendo dados memory-optimized, com pelo menos um caminho de pasta associado, onde o SQL Server grava os arquivos de checkpoint usados para recuperar os dados após reinício. Em .NET: modelBuilder.Entity<X>().ToTable(tb => tb.IsMemoryOptimized()) no EF Core 8 gera um CREATE TABLE ... WITH (MEMORY_OPTIMIZED = ON); se a migration não criou antes a filegroup e o arquivo correspondentes via SQL bruto, essa instrução falha na primeira execução. [TSQL-01-C-11, TSQL-01-C-12] {ACORDO 1 / baixa}
  - Limite: Não se aplica a tabelas comuns (disk-based), que nunca exigem essa filegroup específica.
- **Liste explicitamente as colunas das views** — O SQL Server grava a lista de colunas da view em metadados no momento da criação (ou do último `sp_refreshview`); novas colunas adicionadas depois à tabela base não são incorporadas automaticamente à view, mesmo que a definição textual use `SELECT *`. Em .NET: Uma entidade EF Core 8 mapeada para uma view (`ToView`) via scaffold de banco de dados nunca vai expor uma coluna nova adicionada à tabela subjacente após a criação da view, mesmo que o desenvolvedor rode `dotnet ef dbcontext scaffold` novamente, porque a própria view no banco não enxerga a coluna até um refresh explícito. [TSQL-05-B-7] {ACORDO 1 / alta}
  - Limite: Não se aplica a consultas ad hoc com `SELECT *` direto na tabela (que sempre refletem o schema atual) nem após a execução de `sp_refreshview`/`sp_refreshsqlmodule` ou um `CREATE OR ALTER VIEW` que redefina a view.
- **Ative isolamento por snapshot por meio de migration** — Diferente de SET TRANSACTION ISOLATION LEVEL (opção de sessão) ou de um hint de tabela por query, READ COMMITTED SNAPSHOT é uma flag do banco (ALTER DATABASE) que precisa de acesso exclusivo ao banco no momento da ativação, porque muda a semântica padrão de leitura para todas as sessões simultaneamente. Em .NET: A ativação correta em um projeto EF Core 8 é uma migration com migrationBuilder.Sql("ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON") aplicada numa janela de manutenção sem outras conexões ativas — não é algo definido via connection string, DbContextOptions ou IsolationLevel por chamada. [TSQL-10-A-14] {ACORDO 1 / alta}
  - Limite: SNAPSHOT (isolamento por transação) já pode ser usado após ALLOW_SNAPSHOT_ISOLATION estar ligado, sem exigir exclusividade por transação individual — só a ativação inicial da flag exige acesso exclusivo.
- **Ordene por nomes de coluna, não por posições ordinais** — A posição se refere à ordem física das colunas na lista do SELECT no momento em que a query foi escrita; qualquer alteração futura nessa lista (reordenar, inserir uma coluna no meio) muda silenciosamente qual coluna passa a controlar a ordenação, sem gerar erro. Em .NET: Uma view ou raw SQL usada por um relatório .NET 8 com `ORDER BY 1` continua compilando e rodando sem erro depois que alguém adiciona uma nova coluna calculada no início do SELECT numa migration; o relatório passa a ordenar por um campo diferente do pretendido, e ninguém percebe até um usuário reclamar da ordem. [TSQL-02-B-15] {ACORDO 1 / media}
  - Limite: Não se aplica a queries dinâmicas/geradas que nunca têm a lista de SELECT alterada manualmente.
