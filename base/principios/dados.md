## Correção

- **Não usar relógio de parede/timestamp para resolver escrita concorrente vencedora nem como token de concorrência ou ordenação** — Resolver conflitos por "maior timestamp" (last write wins) é uma ordem arbitrária forçada sobre escritas concorrentes, e como relógios de máquinas diferentes sofrem desvio (clock skew), essa ordem pode não corresponder à ordem real de commit — descartando silenciosamente uma escrita que na verdade venceu. Em .NET: Uma lógica de resolução de conflito escrita à mão compara uma coluna `LastModifiedUtc DATETIME2` preenchida por `DateTime.UtcNow` em cada instância da aplicação (ex.: dois pods atrás de um load balancer com relógios levemente dessincronizados) para decidir qual gravação concorrente "vence" na tabela, em vez de usar a coluna `rowversion`/`[Timestamp]` do SQL Server, cujo valor é um contador monotônico interno ao banco e independente do relógio da máquina. [DDIA-05-B-6, DDIA-08-A-2, DDIA-08-B-12, DDIA-08-B-2, DDIA-08-C-3, DDIA-09-B-4 +3] {ACORDO 3 / media}
  - Limite: Não se aplica se houver garantia de escritor único por chave (sempre a mesma instância grava aquele registro).
- **Entender que Snapshot/RCSI não impede write skew; reconhecer o padrão de código (ler conjunto, decidir, escrever fora do lido) e que snapshot não protege decisão dependente de leitura de outras linhas** — Snapshot isolation congela a visão de leitura e detecta conflito quando duas transações escrevem a MESMA linha. Ela não detecta o caso em que duas transações leem o mesmo conjunto de linhas e cada uma escreve uma linha DIFERENTE: a premissa que cada uma validou foi invalidada pela outra, mas não há colisão física de linha para detectar. Os nomes dos níveis são acidente histórico, não hierarquia de força — o padrão SQL foi escrito antes de snapshot isolation existir, então fornecedores encaixaram snapshot nos rótulos antigos ("repeatable read", e em alguns casos "serializable") para alegar conformidade. Em .NET: `ctx.Database.BeginTransaction(IsolationLevel.Snapshot)` com `CountAsync()` de validação seguido de `SaveChangesAsync()` que altera outra linha comete a anomalia em silêncio. Só `IsolationLevel.Serializable` (2PL com range locks) a bloqueia. [DDIA-07-A-23, DDIA-07-A-25, DDIA-07-B-1, DDIA-07-C-13, DDIA-07-C-16, DDIA-09-A-4] {ACORDO 3 / media}
  - Limite: se o `UPDATE` final toca exatamente a linha que foi lida e a decisão depende só dela, snapshot + detecção de conflito de atualização já basta.
- **Usar unique index/lock de intervalo (UPDLOCK+HOLDLOCK) para invariante de ausência e impedir inserção concorrente** — Uma classe inteira de bugs de concorrência tem a forma: consultar por linhas que satisfazem uma condição, não achar nenhuma, e inserir uma que satisfaz. O passo de leitura não tem nada para bloquear — não existe linha. É por isso que o padrão "verifica e insere" é irremediavelmente racy sob qualquer nível baseado em versões, e por isso que a proteção precisa vir de um lock sobre o intervalo do índice ou de uma constraint que a engine avalia no momento da inserção. Em .NET: `if (!await ctx.Usuarios.AnyAsync(u => u.Login == login)) { ctx.Add(...); await ctx.SaveChangesAsync(); }` cria logins duplicados. Correto: `HasIndex(u => u.Login).IsUnique()` e capturar `DbUpdateException` com `SqlException.Number` 2601/2627, traduzindo para erro de domínio. Quando a unicidade é sobre um intervalo (horário, faixa), não há constraint — cai em `HOLDLOCK` ou tabela de slots. [DDIA-07-B-13, DDIA-07-B-14, DDIA-07-C-17, DDIA-07-C-18, DDIA-08-C-6, DDIA-09-B-2] {ACORDO 2 / media}
  - Limite: nenhum conhecido para unicidade de coluna. Para sobreposição de intervalos, o SQL Server não tem constraint equivalente, então a saída é lock ou materialização de conflito (DDIA-07-B-32).
- **Tratar timeout de commit/escrita como resultado desconhecido** — a resposta perdida na rede é indistinguível de commit não realizado; o cliente não tem informação para decidir e nenhum protocolo local resolve isso. Em .NET: `SqlException` com `Number == -2` durante `CommitAsync()` ou `SaveChangesAsync`. Chamar `SqlTransaction.Rollback()` nesse ponto normalmente lança, porque a conexão já está inutilizável. [DDIA-04-A-10, DDIA-07-C-4, DDIA-08-A-1, DDIA-08-B-4, DDIA-08-C-1] {ACORDO 3 / media}
  - Limite: se a unidade de trabalho for idempotente, a ambiguidade desaparece e o retry cego passa a ser correto — UPSERT por chave de negócio, ou INSERT protegido por índice único sobre um `RequestId` fornecido pelo cliente. É a única saída barata. Onde a operação não tem chave natural (lançamento contábil, envio), a chave de idempotência explícita é obrigatória; "só tentar de novo" não é opção.
- **Envolver transação explícita na execution strategy do EnableRetryOnFailure** — Retentar uma operação só é seguro se a unidade retentada for a unidade que abortou. Com transação iniciada pela aplicação, o EF não sabe onde a unidade começa nem o que já foi executado nela, então se recusa a adivinhar. A execução tem de ser reentregue inteira à estratégia. Em .NET: verificado no código do EF Core 8: `ExecutionStrategy` lança `InvalidOperationException` (`ExecutionStrategyExistingTransaction`) quando há retry configurado e existe `Database.CurrentTransaction`, transação enlistada ou `TransactionScope` ambiente. O padrão correto é `var s = ctx.Database.CreateExecutionStrategy(); await s.ExecuteAsync(async () => { await using var tx = await ctx.Database.BeginTransactionAsync(); ...; await tx.CommitAsync(); });`. Também verificado: a lista de erros considerados transientes do provider SQL Server inclui 1205 (deadlock), 1222 (lock timeout) e 3960 (conflito de snapshot), e NÃO inclui 2627 nem 547 — ou seja, o retry cobre abortos de concorrência mas nunca violação de constraint. [DDIA-01-B-2, DDIA-04-A-11, DDIA-07-A-39, DDIA-07-B-19, DDIA-08-C-13] {ACORDO 3 / media}
  - Limite: se toda a escrita cabe num `SaveChangesAsync` sem transação explícita, a estratégia funciona sozinha.
- **Nunca disparar efeito externo dentro de transação; usar outbox transacional** — A transação envolve apenas o que o banco controla. Um e-mail enviado, uma mensagem publicada, um cache invalidado ou um webhook chamado no meio da transação acontecem mesmo que a transação aborte, e não há como desfazê-los. A recíproca também dói: um efeito externo executado após o commit pode não acontecer se o processo morrer, deixando banco e mundo externo divergentes. Em .NET: `await bus.PublishAsync(...)` antes do `CommitAsync`, ou dentro de um `SaveChangesInterceptor`, publica eventos de transações que não existiram. O padrão correto: inserir a mensagem numa tabela `OutboxMessages` no mesmo `SaveChangesAsync` e ter um worker separado que a lê e publica com semântica de pelo menos uma vez. [DDIA-07-A-41, DDIA-07-B-22, DDIA-09-B-7, DDIA-09-C-7, DDIA-11-A-4] {ACORDO 3 / baixa}
  - Limite: para efeito externo idempotente e sem valor de consistência (métrica, log), o outbox é peso morto.
- **Restringir retry automático a operações determinísticas/idempotentes; gerar valores não determinísticos antes de operação retriável** — A tolerância a falhas do processamento em lote só funciona porque recomputar um operador determinístico produz uma saída idêntica, permitindo que o resultado de uma tarefa reexecutada substitua com segurança a saída descartada da tentativa anterior; um operador não determinístico produziria um resultado diferente a cada nova tentativa, contradizendo o que consumidores já podem ter observado. Em .NET: A execution strategy de retry do SQL Server no EF Core 8 (`EnableRetryOnFailure`) reexecuta automaticamente uma falha transitória, mas se o `SaveChanges` gera um valor não determinístico por tentativa (por exemplo, um `Guid.NewGuid()` atribuído por um `SaveChangesInterceptor` a cada chamada) e a primeira tentativa já havia commitado antes da conexão cair, a nova tentativa insere uma segunda linha diferente em vez de reproduzir a primeira com segurança. [DDIA-04-C-11, DDIA-10-B-11, DDIA-10-C-7, DDIA-11-A-6] {ACORDO 3 / media}
  - Limite: O risco existe para operações multi-instrução sem chave de idempotência; um `INSERT` puramente aditivo protegido por uma constraint de unicidade (que faz uma repetição falhar ruidosamente em vez de duplicar silenciosamente) não sofre desse problema, assim como retries de operações somente leitura.
- **Adicionar rowversion a entidades com gravação concorrente, como token de concorrência em entidades editáveis, protegendo coluna JSON contra read-modify-write** — Sem um token de concorrência, o EF Core gera um `UPDATE` filtrado apenas pela chave primária, então duas gravações concorrentes na mesma linha simplesmente se sobrescrevem sem nenhuma detecção — exatamente o "last write wins" que descarta a gravação mais antiga silenciosamente; com um token de concorrência, o `UPDATE` passa a incluir `WHERE RowVersion = @original`, e zero linhas afetadas indica que a linha mudou entre a leitura e a escrita. Em .NET: Marcar `public byte[] RowVersion { get; set; }` com `[Timestamp]` (mapeado para uma coluna `rowversion` no SQL Server) faz o EF Core 8 lançar `DbUpdateConcurrencyException` no segundo `SaveChanges()` quando duas instâncias de `DbContext` carregam a mesma linha e ambas tentam salvar mudanças concorrentes. [DDIA-05-A-17, DDIA-05-C-12, DDIA-07-A-20, DDIA-07-A-47] {ACORDO 2 / media}
  - Limite: Só detecta conflito dentro de uma única instância/réplica SQL Server (mesma linha, mesma tabela); não detecta conflitos que já foram resolvidos de forma independente em dois primaries diferentes de uma topologia multi-leader, porque cada primary tem sua própria sequência de `rowversion` local.
- **Rotear sharding por partições lógicas fixas em vez de cálculo direto, não usando hash(chave)%N com N variável nem GetHashCode() para chave de partição estável** — Com essa camada de indireção, adicionar um banco físico só exige mover algumas partições lógicas inteiras entre bancos, sem recalcular a atribuição de nenhuma chave individual. Em .NET: Em vez de `shardIndex = hash(tenantId) % shardCount`, calcular `logicalPartition = hash(tenantId) % 1024` uma vez e manter uma tabela de mapeamento `logicalPartition → connectionString`; adicionar um shard físico move só um subconjunto das 1024 entradas dessa tabela, sem tocar na fórmula de hash nem nas chaves dos tenants. [DDIA-06-A-2, DDIA-06-A-3, DDIA-06-B-5, DDIA-06-B-6] {ACORDO 2 / alta}
  - Limite: Não compensa o custo de manutenção quando o sistema sabe, desde o início, que nunca vai crescer além do número de shards já provisionado.
- **Exigir fencing token validado no destino para locks distribuídos** — A posse do lock só é conhecida pelo processo que a verificou no momento em que checou; se esse processo pausar (GC, fila de threads) e outro processo obtiver o lock enquanto o primeiro ainda "acha" que o possui, a escrita do primeiro chega ao recurso depois — sem um número que só cresce para ordenar as escritas, o recurso não tem como saber que essa escrita é obsoleta. Em .NET: Gerar o token como uma coluna IDENTITY/SEQUENCE incrementada a cada sp_getapplock bem-sucedido e propagá-lo em cada escrita subsequente; a tabela de destino só aplica o UPDATE se @token > UltimoTokenAceito (checado e atualizado na mesma instrução), rejeitando (linhas afetadas = 0) qualquer escrita com token inferior, mesmo vinda de um processo que ainda acredita ser dono do lock. [DDIA-08-A-4, DDIA-09-A-6, DDIA-09-B-6, DDIA-09-C-9] {ACORDO 3 / baixa}
  - Limite: Não se aplica a recursos que não conseguem armazenar/checar um token (ex.: uma chamada de efeito colateral externo sem estado); nesse caso a proteção precisa ser movida para antes da chamada.
- **Não tratar réplica assíncrona como durabilidade nem leitura consistente** — Em commit assíncrono, o primário confirma sem esperar o log endurecer na secundária; num failover, os commits ainda em trânsito não existem no novo primário. E toda leitura numa secundária legível é servida por versionamento, com o atraso de aplicação do log entre o commit e a visibilidade — o nível de isolamento que você pediu não altera isso. Em .NET: `ApplicationIntent=ReadOnly` na string de conexão roteando leituras. Um fluxo que grava no primário e lê logo em seguida na secundária pode não encontrar o que acabou de gravar; e hints de lock enviados via `FromSql` são ignorados lá. [DDIA-05-C-8, DDIA-05-C-9, DDIA-07-A-44, DDIA-09-B-1] {ACORDO 3 / media}
  - Limite: Com commit síncrono a perda no failover é evitada, mas a visibilidade na secundária ainda tem atraso de redo — síncrono garante durabilidade, não leitura-após-escrita.
- **Não assumir leitura em réplica retorna última escrita confirmada** — replicação assíncrona propaga o log de transações depois do commit no líder; a réplica pode atender a leitura antes de aplicar (redo) o log da escrita recém-commitada, então não há garantia de recência (linearizabilidade) entre o commit no primário e a visibilidade no seguidor — mesmo se o pedido de leitura foi feito depois do commit terminar. Em .NET: EF Core com `ApplicationIntent=ReadOnly` roteando para o secundário de um Always On Availability Group em modo assíncrono (ou uma réplica de leitura de escala do Azure SQL) pode retornar a versão anterior de uma linha logo após um `SaveChanges()` bem-sucedido contra o primário. [DDIA-05-A-5, DDIA-05-B-1, DDIA-09-C-1, DDIA-09-C-13] {ACORDO 3 / media}
  - Limite: não se aplica se a leitura reusa a mesma conexão/transação do commit (sempre vai ao primário); também não se aplica se o secundário está em modo síncrono e a aplicação aguarda explicitamente a aplicação (redo) do log antes de rotear a leitura — o "hardening" síncrono do log por si só não garante isso.
- **Adicionar invalidação explícita ao denormalizar valor derivado, preferindo copiar valores computados na origem em vez de reexecutar lógica no destino** — Armazenar o texto humano diretamente (em vez do ID) duplica a informação e obriga a atualizar todas as cópias quando ela muda; uma FK só garante que o ID referenciado existe, não sincroniza nenhuma cópia de texto derivada dele. Em .NET: Uma tabela `Pedidos` no SQL Server com `ClienteId` (FK íntegra) e uma coluna extra `NomeClienteCache` preenchida no INSERT fica desatualizada silenciosamente quando o EF Core 8 atualiza `Cliente.Nome` sem trigger ou lógica adicional tocando `Pedidos`. [DDIA-02-C-8, DDIA-05-B-13, DDIA-07-C-45] {ACORDO 2 / media}
  - Limite: Denormalizar sem sincronização é aceitável quando o valor cacheado é um snapshot histórico intencional (ex.: nome do cliente no momento do pedido); nesse caso a divergência é o comportamento correto, não um bug.
- **Serializar long/bigint como string para clientes JS** — JSON não distingue inteiro de ponto flutuante nem define precisão; o consumidor interpreta o número segundo o tipo numérico da própria linguagem, e o JavaScript representa todo número como double IEEE-754, que só é exato para inteiros até 2^53 — acima disso, o valor sofre arredondamento silencioso na desserialização, ainda que o texto JSON transmitido estivesse correto. Em .NET: uma entidade EF Core 8 com `long Id` mapeada para `bigint` no SQL Server (IDENTITY de alto volume ou um identificador tipo snowflake) serializada por `System.Text.Json` como número JSON puro perde precisão quando um cliente JavaScript faz `JSON.parse` do payload, para qualquer valor acima de 9007199254740992. [DDIA-04-A-1, DDIA-04-B-7, DDIA-04-C-6] {ACORDO 3 / media}
  - Limite: não se aplica se o valor nunca excede 2^53 na prática, ou se nenhum consumidor da API é JavaScript/TypeScript.
- **Usar token de versão para read-then-write dividido entre requisições** — A proteção contra decisão sobre premissa obsoleta existe apenas dentro dos limites da transação — o banco só pode invalidar o que ele viu você ler. Se a leitura ocorreu num GET e a escrita num POST minutos depois, não há transação que englobe as duas: o instante da leitura e o da escrita estão separados por uma eternidade e por um usuário. Cada requisição inicia uma transação nova. Em .NET: subir para `Serializable` no handler do POST não protege nada, porque a leitura que embasou a decisão está no passado. A defesa é enviar o token de versão ao cliente e reenviá-lo no POST, com `rowversion` como `[ConcurrencyCheck]`/`IsRowVersion`, ou revalidar toda a precondição dentro da transação de escrita. [DDIA-07-A-46, DDIA-07-B-27, DDIA-07-C-42] {ACORDO 3 / media}
  - Limite: se a precondição é revalidada integralmente dentro da transação de escrita, o problema volta a ser o dos itens de write skew e é resolvível por isolamento.

Em .NET: `ExecuteSqlRaw("EXEC sp_getapplock @Resource={0}, @LockMode='Exclusive', @LockOwner='Transaction'", chave)` dentro de `BeginTransaction`, ou uma tabela de slots lida com `WITH (UPDLOCK, HOLDLOCK)`.   - Limite: É contorno, não solução: acopla controle de concorrência ao modelo de dados e é fácil esquecer de adquirir o lock em um caminho novo. Prefira SERIALIZABLE ou índice único quando couberem.
- **Não depender do banco para invariantes não expressas como constraint** — o "C" de ACID é propriedade da aplicação. O motor só garante o que foi declarado; o resto depende de a aplicação estruturar as transações corretamente. Em .NET: SQL Server declara `UNIQUE`, `FOREIGN KEY` e `CHECK` sobre colunas da própria linha. Um `IEntityTypeConfiguration` que só mapeia essas três não protege nada além disso. [DDIA-07-B-31, DDIA-07-C-2] {ACORDO 2 / media}
  - Limite: `CHECK` com UDF escalar que faz subconsulta é aceito pelo SQL Server e parece resolver invariante multi-linha — não resolve: é avaliado no isolamento do statement, não é serializado contra transações concorrentes, e ainda força execução linha a linha. Invariante multi-linha só tem três saídas reais: view indexada em forma restrita (item 44), trigger, ou nível serializable (item 16).
- **Particionar consumo paralelo por chave quando ordem causal importa, serializando processamento por chave em mensageria concorrente** — entregar mensagens em paralelo sem preservar a ordem por chave quebra a garantia de entrega totalmente ordenada; dois eventos causalmente dependentes do mesmo agregado podem ser aplicados fora de ordem no destino se forem distribuídos livremente entre tasks concorrentes. Em .NET: um worker .NET 8 lê uma tabela `Outbox` no SQL Server e distribui as linhas entre N tasks paralelas (por throughput) sem agrupar por `AggregateId`; o evento `PaymentReceived` é persistido no read model via EF Core antes do evento `OrderCreated` referente ao mesmo pedido. [DDIA-09-B-10, DDIA-11-A-15] {ACORDO 2 / media}
  - Limite: não se aplica se o processamento for particionado por `AggregateId` (mesma chave sempre na mesma task/partição) ou se os eventos aplicados forem comutativos e idempotentes entre si.
- **Separar remoção/rename de coluna em dois deploys (expand/contract); inventariar consumidores antes de renomear coluna SQL Server** — numa rolling upgrade, instâncias da versão antiga e da nova ficam ativas simultaneamente contra o mesmo banco por um período; se a coluna some do schema físico antes de toda instância antiga ser substituída, qualquer requisição ainda atendida pela versão antiga — cujo modelo ainda referencia a coluna — falha, porque o motor rejeita qualquer SELECT/INSERT que cite uma coluna inexistente, sem meio-termo possível. Em .NET: se uma migration do EF Core 8 remove uma coluna (`migrationBuilder.DropColumn`) no mesmo release em que o `DbContext` para de mapeá-la, qualquer instância ainda rodando a imagem anterior lança `SqlException: Invalid column name` na primeira query que a referencia, assim que a migration é aplicada — mesmo sem nenhuma mudança de código nessa instância. [DDIA-04-A-4, DDIA-04-C-14] {ACORDO 2 / media}
  - Limite: não se aplica a deploys com parada total do serviço antes da migration, nem a ambientes de instância única reiniciada atomicamente junto com a migration.
- **Manter ignorar propriedades desconhecidas ao desserializar JSON de fila, não reserializando e perdendo campos desconhecidos de schema mais novo** — numa implantação gradual, publicadores mais novos e consumidores mais antigos coexistem por um tempo; se o publicador adiciona uma propriedade nova à mensagem, o consumidor antigo precisa poder ignorá-la sem falhar, exatamente como um leitor Avro/Protobuf ignora um campo desconhecido — forçar o desserializador a rejeitar qualquer propriedade não mapeada transforma toda evolução aditiva do contrato numa quebra imediata para quem ainda não foi atualizado. Em .NET: `System.Text.Json` no .NET 8 introduziu `JsonSerializerOptions.UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow`, que faz o desserializador lançar `JsonException` ao encontrar qualquer propriedade JSON sem correspondência no tipo C#; usar essa opção num worker que consome mensagens de fila (Azure Service Bus, RabbitMQ etc.) faz o processamento falhar assim que o publicador manda uma mensagem com um campo novo, mesmo irrelevante para o consumidor. [DDIA-04-A-13, DDIA-04-C-4] {ACORDO 2 / media}
  - Limite: `Disallow` é apropriado em fronteiras internas fortemente versionadas e implantadas atomicamente, onde detectar um campo digitado errado cedo vale mais que tolerância a evolução — não no caminho de um consumidor assíncrono de fila.
- **Adicionar propriedade opcional a DTO sem versionamento coordenado, verificando compatibilidade de desserialização ao adicionar campo JSON** — clientes já implantados (apps mobile publicados, SPA em cache no navegador) não podem ser atualizados no mesmo instante que o servidor; o desserializador do cliente antigo, por padrão, ignora propriedades JSON que não conhece, então a propriedade nova é tratada como se não existisse — a superfície de dados que o cliente antigo já espera não muda em nada. Em .NET: um cliente .NET (ou qualquer cliente usando `System.Text.Json` com comportamento padrão) que desserializa a resposta de uma Web API ASP.NET Core continua funcionando sem erro quando o servidor passa a incluir uma propriedade nova no JSON, porque `JsonSerializer.Deserialize` ignora por padrão qualquer propriedade sem correspondência no tipo de destino. [DDIA-04-A-15, DDIA-04-C-12] {ACORDO 2 / media}
  - Limite: não se aplica a remover ou mudar o tipo de uma propriedade existente, nem a campos de requisição obrigatórios enviados pelo cliente — nesses casos a direção da compatibilidade se inverte e uma nova versão do endpoint costuma ser necessária.
- **Não confiar em tipos não anuláveis do C# como garantia pós-desserialização, nem tratar nullable reference types como garantia em runtime** — o capítulo observa que JSON não impõe um schema obrigatório para reforçar tipos — a interpretação correta depende inteiramente de quem escreve o parser; anotações de nulidade do C# são checadas em tempo de compilação, não em tempo de execução pelo desserializador. Em .NET: em .NET 8, System.Text.Json não valida nullable reference type annotations (esse enforcement só existe a partir de opções introduzidas no .NET 9); desserializar um JSON que omite uma propriedade declarada como `string Nome` (não anulável) simplesmente atribui `null` a `Nome`, sem lançar exceção. [DDIA-01-C-6, DDIA-04-B-10] {ACORDO 2 / media}
  - Limite: não se aplica se o código usa `[JsonRequired]`/`required` explicitamente nas propriedades que precisam estar presentes, ou validação manual pós-desserialização.
- **Não confiar em mapeamento posicional padrão do SqlBulkCopy; declarar ColumnMappings explícitos** — o capítulo observa que formatos sem schema (como CSV) deixam a cargo da aplicação interpretar cada coluna — sem nomes explícitos, qualquer mudança na ordem das colunas muda silenciosamente o significado de cada valor; o SqlBulkCopy herda esse mesmo modo de falha quando não recebe mapeamento explícito. Em .NET: `SqlBulkCopy` sem `ColumnMappings` associa a N-ésima coluna da fonte (`DataTable`/leitor) à N-ésima coluna ordinal da tabela de destino; inserir uma nova coluna no meio da tabela de destino, ou reordenar as colunas da fonte, desloca todos os valores subsequentes para a coluna errada sem lançar exceção, caso os tipos sejam compatíveis (ex.: todas `NVARCHAR` ou todas `INT`). [DDIA-04-A-9, DDIA-04-C-5] {ACORDO 2 / media}
  - Limite: inofensivo se `ColumnMappings` é sempre especificado por nome, ou se o conjunto e a ordem de colunas entre origem e destino são congelados e nunca mudam; o risco cresce exatamente quando alguém "só adiciona uma coluna" sem revisar todos os pontos de bulk load.
- **Habilitar ALLOW_SNAPSHOT_ISOLATION/IsolationLevel.Snapshot previamente no banco** — SNAPSHOT depende do version store estar sendo mantido para aquele banco. Se `ALLOW_SNAPSHOT_ISOLATION` está desligado, as versões simplesmente não são geradas; o motor não tem como servir a leitura, então rejeita a transação em vez de degradar silenciosamente para outro nível. Em .NET: `ctx.Database.BeginTransaction(IsolationLevel.Snapshot)` lança `SqlException` (família 3952) se o banco não foi preparado. Note que `ALLOW_SNAPSHOT_ISOLATION` e `READ_COMMITTED_SNAPSHOT` são chaves independentes: ligar a segunda não habilita a primeira. [DDIA-07-A-16, DDIA-07-B-5] {ACORDO 2 / media}
  - Limite: Nenhum conhecido; é comportamento determinístico de configuração.
- **Implementar retry para deadlock como comportamento esperado, retentando apenas erro transitório e não permanente** — O detector de deadlock varre o grafo de espera periodicamente, escolhe como vítima a transação de menor custo de rollback e a desfaz por inteiro. Isso não é falha do motor: é a única saída de um ciclo em que ambas as partes já seguram o que a outra precisa e nenhuma pode soltar antes do commit. Como a vítima é desfeita completamente, repetir é seguro do ponto de vista do banco. Em .NET: Durante `SaveChanges` o 1205 chega embrulhado: `DbUpdateException.InnerException is SqlException { Number: 1205 }`. O retry precisa refazer a unidade de trabalho a partir das leituras, com um `DbContext` novo, e com backoff — repetir imediatamente recria o mesmo entrelaçamento. [DDIA-07-A-31, DDIA-07-C-5] {ACORDO 2 / alta}
  - Limite: Retry só é válido para a vítima; para erros permanentes (2627, 2601, 547) repetir nunca converge (item 39).
- **Usar operação de escrita atômica em vez de incremento via change tracker, escrevendo delta no servidor em vez de resultado calculado no cliente** — Ler, calcular em memória e escrever de volta é o ciclo read-modify-write clássico. Duas execuções concorrentes leem o mesmo valor e a segunda escrita sobrepõe a primeira sem incorporá-la: a atualização não é corrompida, é apagada. Nenhum nível de isolamento abaixo de serializável impede isso por conta própria, porque a segunda escrita é perfeitamente legítima do ponto de vista do banco — ela ocorre depois do commit da primeira. Em .NET: `e.NaoLidas += 1; await ctx.SaveChangesAsync();` gera `UPDATE ... SET NaoLidas = @p0 WHERE Id = @id` com o valor já calculado. O correto é `await ctx.Set<X>().Where(x => x.Id == id).ExecuteUpdateAsync(s => s.SetProperty(x => x.NaoLidas, x => x.NaoLidas + 1))`, que delega o cálculo ao servidor num único statement. [DDIA-07-A-37, DDIA-07-B-8] {ACORDO 2 / alta}
  - Limite: se a lógica de decisão não cabe numa expressão SQL (regra de negócio, validação), a operação atômica não serve — aí é lock explícito ou detecção de conflito. E o incremento atômico deixa de ser livre de conflito se a mesma transação também LÊ o contador.
- **Não tratar DbUpdateConcurrencyException como único sinal de conflito; recarregar entidade após a exceção antes de retry** — São dois mecanismos distintos. O token de versão é uma condição no `WHERE` avaliada pela aplicação (linhas afetadas = 0). O conflito de atualização de snapshot isolation é detectado pela engine e abortado por ela. O primeiro produz exceção de concorrência do EF; o segundo produz uma `SqlException` (número 3960) empacotada em `DbUpdateException`. Um `catch` escrito para o primeiro não pega o segundo. Em .NET: sob `IsolationLevel.Snapshot`, atualizar uma linha modificada e commitada por outra transação depois do início da sua faz o `SaveChangesAsync` estourar com `DbUpdateException` cuja `InnerException` é `SqlException { Number = 3960 }`. Só o `catch (DbUpdateConcurrencyException)` do handler não trata isso e o erro sobe como 500. [DDIA-07-A-22, DDIA-07-B-12] {ACORDO 2 / media}
  - Limite: em read committed/RCSI esse erro não existe — a mesma escrita apenas sobrescreve. É por isso que trocar de Snapshot para RCSI faz os erros desaparecerem e os dados errados aparecerem (DDIA-07-B-4).
- **Passar TransactionOptions explícitas ao TransactionScope** — O nível de isolamento efetivo é o mais restritivo pedido em qualquer camada, e `System.Transactions` tem seu próprio default, escolhido independentemente do banco. Quem não passa opções está pedindo 2PL com locks de intervalo sem saber, e herda todos os custos do item DDIA-07-B-15 — inclusive em código legado que "sempre funcionou" porque nunca teve concorrência. Em .NET: `using var scope = new TransactionScope();` no .NET 8 usa `IsolationLevel.Serializable`. Para read committed é preciso `new TransactionScope(TransactionScopeOption.Required, new TransactionOptions { IsolationLevel = IsolationLevel.ReadCommitted, Timeout = ... })`. [DDIA-07-A-3, DDIA-07-B-23] {ACORDO 2 / media}
  - Limite: se o requisito realmente é serializável, o default está certo — mas então deveria estar escrito.
- **Não inferir ordem de criação por IDENTITY independente entre shards; não usar IDENTITY como chave de correlação externa** — cada shard gera sua própria sequência de forma independente, sem coordenação entre bancos — equivale a cada nó gerar apenas números pares ou apenas ímpares: o contador de um shard pode avançar mais rápido ou mais devagar que o do outro, então comparar os números diretamente entre shards não revela qual operação aconteceu antes na realidade. Em .NET: relatório/migração faz `UNION ALL` de tabelas com `IDENTITY` de dois bancos SQL Server (um por região) e usa `ORDER BY Id` para reconstruir a timeline de eventos entre as duas regiões. [DDIA-05-C-3, DDIA-09-B-9] {ACORDO 2 / alta}
  - Limite: não se aplica dentro de um único banco/shard (ali o `IDENTITY` reflete corretamente a ordem local de commit); também não se aplica se cada linha carregar um identificador de ordenação global coordenado externamente.
- **Upsert idempotente por chave de janela em agregações com eventos atrasados** — não existe um momento garantido em que "todos os eventos de uma janela já chegaram", pois um evento pode estar atrasado numa fila ou num dispositivo offline; se a agregação grava com `INSERT` assumindo definitividade, um evento atrasado que chega depois exige uma segunda escrita, e sem uma chave de deduplicação por janela essa segunda escrita cria uma linha duplicada em vez de corrigir a existente. Em .NET: `MERGE INTO AgregadoPorMinuto USING (...) ON AgregadoPorMinuto.JanelaMinuto = @janela WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...`, ou um índice `UNIQUE` em `JanelaMinuto` com upsert via EF Core 8 (buscar por chave e atualizar o contador), em vez de sempre `_context.Agregados.Add(novo)`. [DDIA-11-A-11, DDIA-11-A-13] {ACORDO 1 / media}
  - Limite: não se aplica se a fonte garante contratualmente que nenhum evento chega fora do prazo já coberto pela janela de tolerância da agregação.
- **Não guardar estado mutável em memória do processo em app escalável** — Distribuir um serviço sem estado é simples porque qualquer instância pode atender qualquer requisição; guardar estado local quebra essa propriedade e reintroduz, na camada de aplicação, a mesma dificuldade que sistemas de dados com estado enfrentam ao distribuir. Em .NET: Usar `IMemoryCache` para armazenar resultado de uma consulta EF Core funciona em uma única instância, mas ao escalar para múltiplas instâncias atrás de um load balancer sem sticky sessions, cada instância mantém sua própria cópia desatualizada — é preciso `IDistributedCache` para que a informação seja consistente entre instâncias. [DDIA-01-C-13, DDIA-11-B-15] {ACORDO 2 / alta}
  - Limite: Tornar a camada de aplicação sem estado não resolve o problema de escalar o próprio SQL Server; se o gargalo real é o banco, essa mudança não move a agulha e o esforço deveria ir para o lado dos dados, não da aplicação.
- **Não marcar propriedade como required após contrato já estar em produção** — o capítulo é explícito que todo campo adicionado após o deploy inicial só preserva compatibilidade retroativa se for opcional ou tiver default; `required` é o equivalente em C# de tornar um campo obrigatório, então payloads já gravados (mensagens em fila, eventos persistidos, chamadas de clientes antigos) que não incluem esse campo passam a ser inválidos para o novo leitor. Em .NET: em System.Text.Json (.NET 8), desserializar um JSON que não contém uma propriedade marcada `required` lança `JsonException`, mesmo que a propriedade tivesse um valor default plausível — diferente de uma propriedade opcional comum, que simplesmente ficaria com o valor padrão do tipo. [DDIA-04-B-5, DDIA-04-C-9] {ACORDO 2 / media}
  - Limite: não se aplica a campos que existem desde a primeira versão do contrato, nem quando se garante que nenhum dado antigo sem esse campo ainda será lido.
## Performance

- **Avaliar custo de escrita antes de criar índice/view materializada, adicionando índice apenas a partir de padrão de consulta real e só quando ganho de leitura justifica o custo** — diferente de uma view comum, que é só reescrita em tempo de leitura, uma indexed view guarda uma cópia física do resultado agregado; sempre que os dados de origem mudam, essa cópia precisa ser atualizada para não ficar inconsistente, e essa atualização acontece de forma síncrona, dentro da mesma transação que fez a mudança original nas tabelas base. Em .NET: uma indexed view do SQL Server (`CREATE VIEW ... WITH SCHEMABINDING` + índice clusterizado único) é mantida automaticamente pelo motor a cada INSERT/UPDATE/DELETE nas tabelas base; o EF Core 8 não gerencia indexed views nativamente, então o custo de escrita adicional se aplica a qualquer comando emitido pelo DbContext que toque as tabelas cobertas, mesmo sem o EF "saber" que a view existe. [DDIA-02-A-3, DDIA-03-A-1, DDIA-03-A-17, DDIA-03-B-1, DDIA-03-B-8, DDIA-03-C-9] {ACORDO 3 / media}
  - Limite: não se aplica a views comuns (não indexadas), que não têm custo de manutenção porque são expandidas apenas na leitura.
- **Não deixar espera externa dentro de transação aberta** — Transação aberta é recurso mantido: locks retidos até o commit e versões antigas impedidas de serem coletadas. Como não há limite de duração, uma transação que espera algo lento converte latência externa em contenção interna, e uma fila de esperadores se forma atrás dela. A prática consolidada é o oposto: a transação nasce e morre dentro do mesmo request, curta o suficiente para não acumular fila; nada de estender transação através de interações. Em .NET: `await httpClient.PostAsync(...)`, `await bus.PublishAsync(...)` ou `await Task.Delay(...)` entre `BeginTransactionAsync` e `CommitAsync` mantém locks pelo tempo do serviço externo. Sob Snapshot/RCSI, também segura o version store (DDIA-07-B-7). [DDIA-07-A-34, DDIA-07-A-45, DDIA-07-B-26, DDIA-07-C-38] {ACORDO 3 / media}
  - Limite: nenhum conhecido para chamadas externas. Cálculo puro em memória de microssegundos é irrelevante.
- **Evitar chave clusterizada não sequencial/aleatória em alta inserção; preferir chave primária monotonicamente crescente** — o índice clusterizado armazena as linhas fisicamente na ordem da própria chave, então cada inserção precisa cair exatamente no ponto da árvore correspondente ao seu valor; valores fora de ordem caem no meio de páginas já cheias, forçando divisão de página (split) e realocação, em vez do simples acréscimo no final que uma chave crescente permitiria. Em .NET: no EF Core 8, a chave primária vira por padrão a chave do índice clusterizado no SQL Server; usar `Guid.NewGuid()` (aleatório) como PK em vez de `IDENTITY`, `SEQUENCE` crescente ou `NEWSEQUENTIALID()` gera inserções espalhadas por toda a árvore, aumentando fragmentação e splits de página. [DDIA-03-A-7, DDIA-03-B-2, DDIA-03-C-11, DDIA-06-B-1] {ACORDO 3 / media}
  - Limite: não se aplica se a tabela é majoritariamente lida por chave secundária e raramente recebe INSERTs, ou se reorganizações de índice rodam com frequência suficiente para neutralizar o efeito.
- **Usar índice dedicado (columnstore/espacial) para consultas multidimensionais/agregações amplas, sem converter índice clusterizado OLTP para columnstore** — uma B-tree ordena por uma sequência fixa de colunas; ela restringe eficientemente um intervalo contíguo na coluna líder, mas dentro desse intervalo as demais colunas aparecem fora de ordem, então restringir uma segunda dimensão dentro do resultado já filtrado exige varrer e testar linha por linha em vez de fazer seek direto. Em .NET: uma tabela com colunas `Latitude` e `Longitude` e um índice composto `(Latitude, Longitude)` no SQL Server consegue seek eficiente no intervalo de latitude, mas o filtro de longitude vira predicado residual (scan) dentro daquele intervalo, porque os valores de longitude não ficam ordenados dentro de cada faixa de latitude; a alternativa correta é um tipo `geography`/`geometry` com índice espacial dedicado. [DDIA-03-A-12, DDIA-03-A-15, DDIA-03-B-11, DDIA-03-B-9] {ACORDO 2 / media}
  - Limite: não se aplica quando uma das duas dimensões tem cardinalidade baixa o suficiente para ser tratada como igualdade, reduzindo o problema a uma única dimensão de intervalo.
- **Carregar dados em bloco em vez de consultar registro a registro em loop** — uma consulta remota por registro tem sua vazão limitada pelo tempo de ida-e-volta (round-trip) da rede/banco, não pelo custo de processamento; multiplicar esse RTT pelo número de registros do dataset grande transforma um job de minutos em um job de horas, e paralelizar essas consultas agrava a carga sobre o banco de origem. Em .NET: EF Core 8 - iterar uma lista de eventos e chamar `context.Users.Find(evento.UserId)` (ou `FirstOrDefaultAsync`) dentro do `foreach` gera uma round trip por evento; a alternativa é um único `Join`/`Include` traduzido para SQL, ou carregar os usuários necessários em um `Dictionary<int,User>` com uma única consulta `Where(u => ids.Contains(u.Id))` antes do loop. [DDIA-01-C-7, DDIA-10-B-1, DDIA-10-C-2] {ACORDO 2 / media}
  - Limite: se o número de chaves distintas a buscar é pequeno (dezenas) e cabe em uma única consulta com índice, a busca pontual continua sendo a opção mais eficiente; o problema é buscar repetidamente por registro dentro de um laço sobre um dataset grande.
- **Ordenar índice composto pela coluna mais filtrada isoladamente primeiro** — um índice composto concatena os campos numa única chave ordenada pela sequência declarada; a ordenação resultante só garante contiguidade útil para buscas que fixam um prefixo contíguo dessa chave a partir do primeiro campo — pular direto para um campo do meio ou do fim quebra a contiguidade necessária para localizar as linhas sem varrer a estrutura inteira. Em .NET: um índice EF Core 8 criado com `HasIndex(x => new { x.Sobrenome, x.Nome })` resolve com Index Seek filtros por `Sobrenome` isolado ou por `Sobrenome` e `Nome` juntos, mas uma consulta que filtra só por `Nome` não consegue usar esse índice como seek e o SQL Server recorre a um Index Scan completo. [DDIA-03-A-11, DDIA-03-B-5, DDIA-03-C-5] {ACORDO 3 / media}
  - Limite: não se aplica a índices columnstore, que não dependem de ordem física de chave para responder agregações.
- **Particionar chave quente em sub-chaves em vez de resolver via hash, sem esperar que particionamento resolva contenção em chave hot** — Hash não resolve uma chave quente porque toda escrita para o mesmo valor de chave sempre mapeia para o mesmo destino físico; dividir a chave em si em N variantes espalha fisicamente as escritas, exigindo somar as N variantes no momento da leitura. Em .NET: Em vez de um único `Counter(Id, Value)` atualizado por `UPDATE ... SET Value = Value + 1` a cada evento, modelar `CounterShard(Id, ShardIndex, Value)` com `ShardIndex = Random.Shared.Next(N)` no insert e `SumAsync(c => c.Value)` na leitura via EF Core 8. [DDIA-06-A-9, DDIA-06-B-7, DDIA-06-C-7] {ACORDO 3 / media}
  - Limite: Não se aplica quando o throughput de escrita na chave nunca se aproxima do limite de contenção de uma única linha, ou a leitura exige valor exato sem custo adicional de agregação.
- **Encurtar transação a partir da primeira escrita, evitando transação longa que trava coleta de versões antigas** — O lock exclusivo de escrita é retido até o fim da transação em todos os níveis de isolamento, inclusive READ UNCOMMITTED e inclusive com versionamento de linha ligado. Versionamento resolve leitor-vs-escritor; escritor-vs-escritor continua sendo fila de lock. Portanto o relógio de contenção começa a correr no primeiro UPDATE/INSERT/DELETE e só para no COMMIT. Em .NET: Um `BeginTransaction` que faz `SaveChanges` cedo e só commita depois de mais trabalho (validações, chamadas, laços) segura X locks durante todo o resto. Reordene: leituras e trabalho primeiro, escritas coladas ao commit. [DDIA-07-A-12, DDIA-07-A-8, DDIA-07-C-43] {ACORDO 2 / media}
  - Limite: Nenhum conhecido dentro do SQL Server; o comportamento é o mesmo em RCSI e SNAPSHOT.
- **Considerar a partição mais carregada ao estimar tempo de job paralelo** — quando o volume de dados por chave é muito desigual (algumas chaves concentram desproporcionalmente mais registros), particionar o trabalho por essa chave produz uma partição muito maior que as demais, e como o job só termina quando todas as partições terminam, o tempo total fica limitado pela partição mais lenta, não pela média. Em .NET: em C# 12/.NET 8, um `Parallel.ForEach` (ou `Task.WhenAll`) que agrupa o trabalho por uma chave (por exemplo, processar todos os pedidos de cada tenant em uma única task por tenant) sofre esse efeito quando um tenant grande concentra a maior parte das linhas; a mitigação é subparticionar chaves grandes (processar o tenant grande em vários lotes menores) em vez de uma task por chave. [DDIA-10-A-11, DDIA-10-B-6, DDIA-10-C-8] {ACORDO 3 / baixa}
  - Limite: não se aplica se a chave de particionamento tem distribuição aproximadamente uniforme entre os valores, ou se o particionamento é dinâmico por lote de linhas (não por valor de chave).
- **Não expor varbinary grande via JSON sem medir custo** — JSON só representa nativamente texto Unicode, não sequências de bytes arbitrárias; para caber numa string JSON válida, cada grupo de 3 bytes binários vira 4 caracteres imprimíveis em Base64 — um overhead fixo de 33% sobre qualquer conteúdo binário, aplicado sempre que o serializador precisa transformar bytes em texto. Em .NET: `System.Text.Json` serializa automaticamente qualquer propriedade `byte[]` (um `varbinary(max)` ou até um `RowVersion`/`timestamp`) como string Base64; uma entidade EF Core 8 que expõe `byte[] Documento` de 1 MB gera ~1,33 MB de JSON na resposta, sem nenhuma configuração adicional causar isso. [DDIA-04-A-2, DDIA-04-C-7] {ACORDO 2 / media}
  - Limite: não se aplica a colunas binárias pequenas (poucos bytes, como um `RowVersion` de 8 bytes) onde o overhead absoluto é irrelevante, nem quando o binário é servido por stream dedicado fora do JSON.
- **Ler com intenção de escrita (lock de atualização) quando for atualizar em seguida** — deadlock por conversão. Dois leitores obtêm S simultaneamente; ao converterem para X, cada um espera o S do outro. O lock U é compatível com S mas não com outro U, então só um leitor entra na fase de conversão. Em .NET: o par `FindAsync` + mutação + `SaveChanges` é exatamente esse padrão. A correção é ler com `WITH (UPDLOCK, ROWLOCK)` via `FromSqlRaw`, ou eliminar a leitura com `ExecuteUpdate` condicional (item 32). [DDIA-07-A-29, DDIA-07-C-20] {ACORDO 2 / media}
  - Limite: `UPDLOCK` troca deadlock por bloqueio: sob contenção alta a taxa de erro cai e a latência sobe. Se o SLA é de latência de cauda e o retry de 1205 é barato, deixar o deadlock acontecer pode ser a escolha melhor. Não existe resposta universal — depende de qual métrica você está defendendo.
- **Deixar agregação/filtro executar no SQL Server, não materializar antes** — uma tabela hash de agregação só é viável enquanto o working set (uma entrada por chave distinta) couber na memória disponível; quando a cardinalidade de chaves é grande, um agrupamento feito em memória no processo cliente cresce sem limite, enquanto o mecanismo de banco pode ordenar/derramar em disco (tempdb) para lidar com um working set maior que a memória. Em .NET: em EF Core 8, chamar `.AsEnumerable()` (ou qualquer operação que force materialização) antes de `.GroupBy(...)` faz o agrupamento rodar em `Dictionary` interno do LINQ-to-Objects sobre todas as linhas trazidas para o processo .NET; manter a consulta como `IQueryable` até o `GroupBy` deixa o SQL Server traduzir para `GROUP BY` e devolver só os grupos. [DDIA-10-B-10, DDIA-10-B-2] {ACORDO 1 / media}
  - Limite: se a cardinalidade das chaves de agrupamento é pequena o bastante para caber confortavelmente em memória, agrupar do lado do cliente não causa problema prático.
- **Não usar coluna JSON para campo filtrado/ordenado com frequência, nem assumir cobertura completa de filtro sobre campo JSON aninhado** — um documento JSON, como qualquer formato sem schema embutido, precisa carregar o nome de cada campo dentro de cada registro para ser autodescritivo; isso repete a mesma string de nome em toda linha e, além do espaço extra, o motor relacional não consegue construir um índice B-tree comum diretamente sobre um valor dentro do documento sem antes projetá-lo para fora via uma coluna computada. Em .NET: uma propriedade dentro de uma entidade owned mapeada com `.ToJson()` no EF Core 8 fica armazenada como texto dentro de uma coluna JSON do SQL Server; para filtrar eficientemente por ela (`WHERE JSON_VALUE(Col, '$.Status') = 'Ativo'`), é preciso criar manualmente uma coluna computada persistida sobre `JSON_VALUE` e indexá-la — um índice normal do EF Core (`HasIndex`) não enxerga campos dentro do JSON. [DDIA-02-B-11, DDIA-04-A-14] {ACORDO 2 / media}
  - Limite: não se aplica a campos só lidos junto com o resto do documento (nunca usados isoladamente em WHERE/ORDER BY/JOIN), onde o formato JSON é apropriado e o overhead de espaço é aceitável.
- **Processar datasets grandes via streaming, não materializar tudo** — um pipeline que mantém apenas um buffer pequeno em memória e processa registro a registro tem uso de memória constante independente do tamanho da entrada; materializar a entrada inteira antes de processar faz o uso de memória crescer linearmente com o tamanho do dataset até esgotar a RAM disponível. Em .NET: em EF Core 8, `.ToListAsync()` sobre uma consulta que retorna milhões de linhas materializa tudo em memória antes de processar; usar `.AsAsyncEnumerable()` com `await foreach` mantém o `SqlDataReader` subjacente entregando linha a linha, com uso de memória limitado ao registro atual. [DDIA-10-A-8, DDIA-10-A-9] {ACORDO 1 / media}
  - Limite: não se aplica quando o resultado precisa ser acessado múltiplas vezes ou fora de ordem, já que streaming permite apenas uma passada.
- **Projetar apenas colunas necessárias em vez da entidade inteira** — uma projeção declarativa de colunas pode ser empurrada para a camada de armazenamento antes da execução, que decide o que ler de cada página, enquanto carregar a entidade completa obriga o motor a materializar e transportar todas as colunas mapeadas antes que qualquer filtro de "quais campos eu uso" possa ser aplicado no cliente. Em .NET: em EF Core 8, `context.Orders.Select(o => new { o.Id, o.Total })` gera um `SELECT Id, Total FROM Orders`, trazendo só as duas colunas pela rede; `context.Orders.ToList()` sobre uma entidade `Order` com colunas grandes (como `varbinary(max)` ou `nvarchar(max)`) traz todas as colunas mapeadas mesmo que o código use só duas delas depois. [DDIA-03-B-10, DDIA-10-A-14] {ACORDO 2 / media}
  - Limite: não se aplica quando o código realmente precisa de todas as colunas, por exemplo para depois persistir de volta o objeto completo via change tracking.
- **Não assumir que índice sempre acelera consulta analítica de scan, nem que índice B-tree acelera LIKE '%termo%'** — uma busca por índice tem custo por linha (navegar a árvore B, e depois um lookup na tabela base se o índice não for coberto); somado sobre uma fração grande das linhas, esse custo por linha supera o de uma varredura sequencial única, que é exatamente o motivo pelo qual mecanismos de processamento em lote leem o dataset inteiro em vez de fazer buscas pontuais quando o objetivo é agregar sobre muitos registros. Em .NET: em SQL Server, uma consulta agregada gerada por EF Core 8 (`Sum`, `GroupBy`, `Count`) que toca a maior parte de uma tabela normalmente recebe um plano de Clustered Index Scan mesmo existindo um índice não clusterizado na coluna filtrada; adicionar esse índice não clusterizado só para "ajudar" essa consulta específica não muda o plano de forma proveitosa e ainda adiciona custo de manutenção (escrita) em todo INSERT/UPDATE/DELETE que passe a manter esse índice. [DDIA-03-B-6, DDIA-10-B-3] {ACORDO 1 / media}
  - Limite: não se aplica quando a consulta é seletiva (lê uma pequena fração das linhas) - nesse caso o índice reduz drasticamente o trabalho e deve ser criado.
- **Avaliar custo de default em ALTER TABLE de coluna nova, fazendo backfill em lotes e não em transação única** — Um schema explícito (schema-on-write) normalmente aplica mudanças de metadados sem reescrever linhas existentes, mas isso só vale quando o valor a preencher é conhecido de antemão para todas as linhas; quando o valor depende de uma função avaliada por linha, o motor precisa materializar e gravar um valor físico em cada linha existente, uma operação proporcional ao tamanho da tabela. Em .NET: Uma migração do EF Core que executa `ALTER TABLE ... ADD Coluna int NOT NULL DEFAULT 5` é uma operação de metadados quase instantânea no SQL Server, mas trocar o valor padrão por uma expressão não determinística por linha (como `SYSUTCDATETIME()`) força o SQL Server a reescrever fisicamente cada linha da tabela sob um lock de schema modification, bloqueando toda a tabela pelo tempo da operação. [DDIA-02-B-2, DDIA-02-B-3] {ACORDO 1 / alta}
  - Limite: Não se aplica a colunas NULL sem valor padrão (sempre metadados) nem a tabelas pequenas onde a diferença de custo é imperceptível.
- **Não assumir escrita pequena ao atualizar campo aninhado em JSON** — Um documento armazenado como uma única string precisa, na prática, ser reescrito por inteiro a cada modificação, porque só alterações que não mudam o tamanho codificado podem ser feitas fisicamente no lugar; alterar qualquer campo aninhado normalmente produz um novo valor de tamanho diferente. Em .NET: O mapeamento nativo de JSON do EF Core 8 (`OwnsMany(...).ToJson()`) grava a coleção aninhada em uma única coluna `nvarchar(max)`; salvar uma mudança em uma única propriedade aninhada gera um `UPDATE` que substitui o valor inteiro da coluna, então o custo de I/O e o tamanho do log de transação escalam com o tamanho do documento inteiro, não com o tamanho do campo alterado. [DDIA-02-B-7, DDIA-04-B-14] {ACORDO 1 / baixa}
  - Limite: Não se aplica a documentos pequenos ou a campos que raramente mudam depois de escritos.
- **Definir durabilidade SCHEMA_ONLY para tabela memory-optimized de cache** — Um armazenamento em memória só ganha desempenho se evitar o overhead de codificar e persistir estruturas em disco; se a durabilidade padrão registra cada escrita no log de transações, o "cache" paga o mesmo custo de gravação em disco de uma tabela comum, sem necessidade. Em .NET: `CREATE TABLE ... WITH (MEMORY_OPTIMIZED = ON)` sem especificar `DURABILITY = SCHEMA_ONLY` (ficando no padrão `SCHEMA_AND_DATA`) para uma tabela usada por EF Core 8 puramente como cache de sessão/rate-limit que pode ser reconstruída do zero a qualquer momento. [DDIA-03-B-12, DDIA-10-C-13] {ACORDO 2 / media}
  - Limite: Não se aplica quando os dados dessa tabela precisam sobreviver a um restart do SQL Server (então `SCHEMA_AND_DATA` é a escolha correta e necessária).
- **Incluir coluna de particionamento no predicado de consulta, minimizando número de partições consultadas em fan-out** — O otimizador só elimina partições inteiras da busca quando o predicado restringe explicitamente a coluna que define os limites das partições; sem isso ele varre todas as partições e combina os resultados. Em .NET: Uma tabela particionada por `OrderDate` consultada via EF Core 8 com `Where(o => o.CustomerId == id)` sem filtro de data força leitura de todas as partições; adicionar `&& o.OrderDate >= start && o.OrderDate <= end` ao predicado LINQ permite eliminação de partições. [DDIA-06-A-10, DDIA-06-A-6] {ACORDO 1 / media}
  - Limite: Não se aplica a tabelas não particionadas, nem quando funções sobre a coluna de particionamento impedem sargabilidade.
- **Calcular p99 de fan-out paralelo pelo máximo das latências dos shards** — `Task.WhenAll` só retorna quando a última task termina, então a latência do resultado combinado é a do shard mais lento entre N — e quanto mais shards forem consultados, maior a chance de que pelo menos um deles esteja no seu próprio percentil alto, mesmo que cada shard individualmente seja rápido na maioria das vezes. Em .NET: Um endpoint que agrega dados chamando `Task.WhenAll` sobre 20 shards, cada um com p99 individual de 200ms mas mediana de 20ms, tem p99 agregado muito mais próximo de 200ms (ou pior) do que os 20ms esperados ao "paralelizar para não somar as latências". [DDIA-06-B-9, DDIA-06-C-12] {ACORDO 2 / media}
  - Limite: Não se aplica quando o número de shards consultados é pequeno o suficiente, ou quando a variância de latência por shard é desprezível.
- **Reconhecer que muitos locks numa transação escalam para lock de tabela** — manter locks finos custa memória; a partir de um limiar (ordem de 5.000 locks sobre um objeto) o motor troca todos por um lock de tabela. É a mesma degradação que o livro descreve quando não há onde pendurar lock de faixa, só que disparada por volume em vez de por ausência de índice. Em .NET: `SaveChanges` de dezenas de milhares de linhas dentro de uma transação — o provider SQL Server do EF Core 8 quebra em lotes (`MaxBatchSize` padrão 42), mas os locks se acumulam na transação, não no lote. [DDIA-07-C-23, DDIA-07-C-37] {ACORDO 1 / media}
  - Limite: dá para desligar com `ALTER TABLE ... SET (LOCK_ESCALATION = DISABLE)`, mas a memória de lock tem teto — estourar troca bloqueio por erro de recurso, que é pior. E não se aplica a leituras sob RCSI/SNAPSHOT, que não pegam lock de linha: a mesma tabela pode ter escrita escalando e leitura completamente imune.
- **Nunca fazer await de recurso externo dentro de transação de banco** — sob bloqueio, o tempo de retenção do lock é o tempo de parede da transação. Um round-trip HTTP de 200 ms ao lado de um commit de 1 ms multiplica a contenção por duas ordens de grandeza. Em .NET: `using var tx = await ctx.Database.BeginTransactionAsync(); ... await http.GetAsync(...); ... await tx.CommitAsync();`. [DDIA-07-A-33, DDIA-07-C-24] {ACORDO 2 / media}
  - Limite: sob SNAPSHOT ou RCSI, leitores não bloqueiam ninguém — então o mesmo padrão num caminho só de leitura é praticamente invisível. É exatamente por isso que ele sobrevive à revisão de código e depois é copiado para o caminho de escrita, onde mata. A revisão precisa perguntar "essa transação escreve?", não "esse padrão é feio?".
- **Não assumir que ADD COLUMN é sempre operação instantânea de metadados** — A maioria dos bancos relacionais executa ALTER TABLE em milissegundos por não reescrever linhas existentes; isso vale no SQL Server para colunas NULL ou com DEFAULT constante, mas quebra quando o default não é determinístico, pois o motor precisa calcular e gravar um valor por linha. Em .NET: Uma migration do EF Core 8 que adiciona coluna `NOT NULL DEFAULT NEWID()` (ou GETUTCDATE()) numa tabela de dezenas de milhões de linhas dispara reescrita física de todas as linhas sob lock de schema, ao contrário de uma coluna com DEFAULT 0. [DDIA-02-C-10, DDIA-04-A-5] {ACORDO 2 / baixa}
  - Limite: Não se aplica a colunas NULL sem default nem a colunas com DEFAULT literal constante (numérico, string fixa, booleano) — permanecem operações de metadado independentemente do tamanho da tabela.
- **Evitar escalonamento a MSDTC com múltiplas conexões na mesma transação** — o commit distribuído em duas fases exige que cada participante prometa poder commitar e mantenha os locks de linha até receber a decisão final do coordenador; se o coordenador falhar entre o "prepare" e o "commit", a transação fica em dúvida e o SQL Server mantém os locks indefinidamente até resolução manual — além de ser bem mais lento (o capítulo cita transações distribuídas de banco relatadas como mais de 10x mais lentas que single-node). Em .NET: `using var scope = new TransactionScope(); using var conn1 = new SqlConnection(connA); using var conn2 = new SqlConnection(connB);` — abrir a segunda conexão dentro do mesmo `TransactionScope` faz o .NET escalonar automaticamente para o MSDTC. [DDIA-09-A-9, DDIA-09-C-6] {ACORDO 2 / baixa}
  - Limite: não se aplica a transações que tocam uma única conexão/banco SQL Server (não há escalonamento a MSDTC); também não se aplica quando as duas operações podem ser modeladas como outbox pattern (gravação de intenção na mesma transação local + processamento assíncrono idempotente) em vez de commit atômico distribuído.
## Manutenção

- **Reconhecer limite do token de concorrência do EF Core (change tracker/coluna)** — o EF gera `UPDATE ... WHERE Id = @id AND Version = @v` e converte `@@ROWCOUNT = 0` em `DbUpdateConcurrencyException` — é compare-and-set. Quem não gera esse UPDATE não é verificado por ninguém. Em .NET: `[Timestamp] public byte[] Version { get; set; }` cobre `SaveChanges`. `ExecuteUpdate`, `ExecuteDelete`, `FromSqlRaw`, procedures, jobs de manutenção e scripts de correção escrevem sem checar nada. [DDIA-07-A-19, DDIA-07-B-11, DDIA-07-C-30, DDIA-07-C-31] {ACORDO 3 / media}
  - Limite: `rowversion` é por linha, não por coluna — duas atualizações a colunas disjuntas da mesma linha conflitam. Em agregados largos e quentes isso gera conflito falso em volume, e a resposta natural (laço de retry) vira livelock (item 33). Nesses casos dividir a entidade, ou usar UPDATE condicional por coluna, é melhor do que o token. Adicionar `[Timestamp]` não é uma melhoria monotônica.
- **Escolher nível de isolamento por unidade de trabalho, orçando custo de versionamento pelo volume de escrita concorrente e reconhecendo diferença do RepeatableRead do .NET frente ao livro** — elevar o nível globalmente muda o comportamento de todas as queries, inclusive as escritas assumindo read committed, e é impossível auditar a aplicação inteira para saber quais sobrevivem — que é exatamente a dificuldade que o capítulo aponta. Em .NET: `BeginTransaction(IsolationLevel.Snapshot)` no relatório e `IsolationLevel.Serializable` no caso que precisa, em vez de um `DbConnectionInterceptor` emitindo `SET TRANSACTION ISOLATION LEVEL` em toda conexão. [DDIA-07-C-12, DDIA-07-C-14, DDIA-07-C-41] {ACORDO 1 / media}
  - Limite: a escolha por transação não alcança o `SaveChanges` implícito, que roda no nível corrente da conexão. Se o caso crítico não abre transação explícita, a decisão foi tomada por omissão e você não percebeu. E o nível efetivo de uma conexão reutilizada do pool nem sempre é o que o código pretendia — a verificação tem que ser observacional, não por leitura de código.
- **Tratar durabilidade como escolha de latência configurável** — O commit só é durável quando o registro correspondente do log está fisicamente no disco. Confirmar antes disso é possível e rápido, porque a espera do commit é justamente a descarga síncrona do buffer de log. Trocar essa espera por confirmação imediata devolve latência de escrita proporcional ao tempo de flush — e abre uma janela em que commits confirmados desaparecem numa queda abrupta. Em .NET: `ALTER DATABASE ... SET DELAYED_DURABILITY = FORCED` (ou `COMMIT WITH (DELAYED_DURABILITY = ON)`). O código .NET não muda em nada: o `SaveChangesAsync` retorna com sucesso do mesmo jeito, e o dado pode não existir depois de um crash. [DDIA-07-A-43, DDIA-07-B-33, DDIA-08-A-9] {ACORDO 2 / media}
  - Limite: Aceitável para dados reconstituíveis (telemetria, sessões, cache); inaceitável onde o retorno de sucesso ao usuário é uma promessa.
- **Usar percentis (p95/p99), não média, para decidir otimização e SLA** — a média é puxada para o comportamento do grosso das execuções rápidas e esconde uma minoria de execuções muito mais lentas. Um nível abaixo: quando o tempo de execução varia por parâmetro (seletividade diferente, plano de execução reaproveitado para um parâmetro atípico), a distribuição fica assimétrica — a média absorve essa cauda em vez de expô-la, ao contrário do percentil, que a isola explicitamente. Em .NET: `avg_worker_time`/`avg_elapsed_time` de `sys.dm_exec_query_stats` para uma stored procedure pode parecer aceitável mesmo quando uma fração das execuções leva muito mais tempo por variação de parâmetro; é preciso olhar o histórico de execuções do Query Store por período ou instrumentar percentis no lado do EF Core (interceptor de DbCommand) para enxergar o problema. [DDIA-01-A-8, DDIA-01-B-9, DDIA-01-C-8] {ACORDO 3 / baixa}
  - Limite: não se aplica a queries com distribuição de tempo de execução homogênea (baixa variância), onde média e percentil praticamente coincidem.
- **Saber se READ COMMITTED é por lock ou versão** — "Read committed" descreve uma garantia, não um mecanismo. Existem duas implementações: locks de leitura de curta duração, ou manter a versão antiga da linha e entregá-la ao leitor. A maioria das engines escolheu versões; o SQL Server com `READ_COMMITTED_SNAPSHOT` desligado (o default de qualquer banco novo) escolheu locks. Logo o leitor precisa do shared lock que o escritor não commitado está retendo. Em .NET: um `ToListAsync()` no EF Core 8 sobre a linha que outra transação está atualizando fica pendurado até o `CommandTimeout` estourar (`SqlException` com `Number` 1222 ou timeout do cliente, -2); ele não retorna o valor antigo. Intuição importada de PostgreSQL/InnoDB está errada aqui. [DDIA-07-A-9, DDIA-07-B-2] {ACORDO 2 / alta}
  - Limite: com `ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON` o nível passa a usar versões e essa espera desaparece — mas isso muda a semântica de read-then-write (DDIA-07-B-4). Azure SQL Database já vem com RCSI ligado.
- **Referenciar valor compartilhado por FK em vez de duplicar texto** — O texto duplicado é copiado fisicamente em cada linha que o referencia, então corrigir esse valor exige escrever (e bloquear) todas essas linhas; a chave estrangeira mantém uma única cópia na tabela de apoio, então a mesma correção é uma escrita de uma linha só, e cada linha que referencia enxerga a mudança através de um join feito na leitura. Em .NET: No EF Core 8 com SQL Server, modele `Region`/`Industry` como entidades próprias com `RegionId`/`IndustryId` como chave estrangeira em `Users`, em vez de uma coluna `RegionName` repetida; renomear uma região vira um `UPDATE Regions SET Name = ...` de uma linha, em vez de um `UPDATE Users SET RegionName = ...` (ou `ExecuteUpdate` em massa) tocando cada usuário daquela região. [DDIA-02-A-2, DDIA-02-B-6] {ACORDO 2 / media}
  - Limite: não compensa para valores que nunca mudam e cujo domínio é pequeno e fixo, onde o custo do join supera o risco de update.
- **Não fixar hints de plano de consulta manualmente** — A vantagem central de uma linguagem declarativa é permitir que o otimizador escolha automaticamente o plano de execução conforme os dados e estatísticas mudam; forçar manualmente o caminho de acesso reproduz o problema do modelo de rede antigo, em que o desenvolvedor tinha que reescrever o código sempre que os dados ou o acesso mudavam. Em .NET: Um hint como `WITH (INDEX(...))` ou `OPTION (FORCE ORDER)` embutido em uma consulta SQL Server via `FromSqlRaw` ou em uma stored procedure trava o SQL Server nesse caminho de acesso mesmo depois que um índice melhor é criado ou a distribuição dos dados muda, enquanto uma consulta sem hint se adapta automaticamente ao novo plano. [DDIA-02-B-10, DDIA-07-A-7] {ACORDO 2 / media}
  - Limite: Não se aplica a casos raros e documentados em que o otimizador comprovadamente escolhe um plano pior de forma consistente e o hint corrige isso com evidência de plano antes/depois.
- **Usar teste de carga open-loop (taxa fixa) para medir latência** — um gerador closed-loop nunca acumula mais de uma requisição em voo por cliente virtual, então, conforme o servidor desacelera, o próprio gerador reduz a taxa de carga oferecida — encolhendo artificialmente a fila que se está tentando medir (ex.: a fila do pool de conexões). Um gerador open-loop mantém a taxa de chegada constante e deixa a fila crescer como clientes independentes reais fariam. Em .NET: gerar carga com `HttpClient` em loop sequencial (`await SendAsync()` seguido do próximo) contra um endpoint ASP.NET Core com EF Core mede uma latência sob carga otimista; para reproduzir o head-of-line blocking do pool de conexões é preciso agendar requisições com um `PeriodicTimer` disparando em taxa fixa, deixando requisições pendentes se acumularem. [DDIA-01-A-10, DDIA-01-C-10] {ACORDO 2 / baixa}
  - Limite: não se aplica a testes cujo objetivo é medir só o tempo de serviço isolado de uma única requisição, sem concorrência.
- **Usar CDC em vez de ler artefatos internos do storage engine** — Um log lógico registra mudanças na granularidade de linha, com valores antes/depois, desacoplado do formato físico de disco; assim o consumidor externo não depende da versão nem da representação interna do storage engine, ao contrário de um log físico que descreve blocos e páginas. Em .NET: Um worker .NET 8 lê cdc.fn_cdc_get_all_changes_dbo_<tabela> via ADO.NET para implementar um padrão outbox/ETL a partir de uma tabela SQL Server, em vez de interpretar o transaction log bruto. [DDIA-05-A-8, DDIA-05-C-7] {ACORDO 2 / media}
  - Limite: Não se aplica quando o requisito é replicar bytes idênticos de disco, como em backup físico, caso em que o log físico é o mecanismo correto.
- **Usar CDC nativo em vez de dual-write/triggers para propagar mudanças** — CDC lê o log de transações do próprio motor — a mesma fonte que a replicação usa — e produz uma sequência de mudanças na ordem real de commit; escrever a mesma informação duas vezes a partir do código da aplicação (uma vez no banco, outra no destino derivado) cria dois caminhos de escrita independentes que podem ser reordenados de formas diferentes sob concorrência, já que nenhum dos dois destinos sabe da ordem que o outro observou. Em .NET: mapear as funções `cdc.fn_cdc_get_all_changes_<instância>` como uma consulta somente leitura via EF Core 8 (`FromSqlRaw`/mapeamento de função de tabela), consumida por um `BackgroundService` que aplica os deltas ao índice de busca ou cache, em vez de o handler HTTP escrever no banco e no destino derivado dentro do mesmo método. [DDIA-05-A-10, DDIA-11-A-3] {ACORDO 1 / baixa}
  - Limite: CDC do SQL Server exige edição Standard/Enterprise com o SQL Server Agent job de captura rodando continuamente, e não está disponível da mesma forma no Azure SQL Database (que oferece Change Tracking, sem histórico de valores, apenas o fato de que a linha mudou).
