## Correção

- **Não reescrever expressões de ponto flutuante assumindo equivalência algébrica/associativa** — cada multiplicação e cada adição arredondam (e podem estourar) de forma independente; expandir a expressão insere um estouro para infinito em um caminho que antes cancelava com segurança (ou vice-versa), então "infinito menos infinito" pode aparecer em uma forma da fórmula e não na outra, mesmo sendo matematicamente a mesma expressão. Em .NET: expandir uma fórmula de negócio com fatores `float`/`double` em uma coluna computada ou projeção LINQ do EF Core — escrever `preco*qtd1 + preco*qtd2` em vez de `preco*(qtd1+qtd2)` — não é uma simplificação algébrica segura; as duas formas podem divergir silenciosamente para overflow/`NaN` com fatores grandes, mesmo sendo "a mesma fórmula". [CSAPP-02B-A-8, CSAPP-02B-A-9, CSAPP-02B-B-10, CSAPP-02B-B-11, CSAPP-02B-C-14, CSAPP-05-A-8 +1] {ACORDO 3 / alta}
  - Limite: não importa para fatores/somas bem dentro da faixa de precisão dupla, longe do limite de overflow, ou ao usar `decimal`.
- **Tratar leitura de bytes crus como escolha explícita de sinal e ordem de bytes** — Na memória, um valor não carrega nenhuma marca de tipo — os mesmos bits só "são" assinados ou sem sinal porque uma instrução específica foi escolhida para operá-los (divisão com ou sem sinal, extensão de sinal ou de zero ao mover um byte para um registrador maior); a CPU não valida essa escolha, apenas executa a instrução que o código pediu sobre o padrão de bits que estiver ali. Em .NET: Ler os mesmos 4 bytes com `BinaryPrimitives.ReadInt32LittleEndian` versus `ReadUInt32LittleEndian`, ou converter `byte`↔`sbyte` com `unchecked`, produz números diferentes a partir de um bit a bit idêntico, sem nenhuma exceção em tempo de execução indicando "tipo errado". [CSAPP-02A-A-2, CSAPP-02A-B-11, CSAPP-02A-C-10, CSAPP-03A-A-5, CSAPP-03A-A-6, CSAPP-03A-B-9 +1] {ACORDO 3 / baixa}
  - Limite: não se aplica quando a leitura passa por um serializador que grava/valida um marcador de tipo junto aos bytes (ex.: BSON, Protobuf com wire type).
- **Usar >>> em vez de >> para deslocamento lógico em valores com sinal** — Deslocamento aritmético à direita (padrão em tipos com sinal) preenche os bits à esquerda com cópias do bit de sinal para preservar o valor numérico em divisões por potência de dois; para um valor negativo, os bits que entram pela esquerda são todos 1, não 0 — o oposto do que se espera ao tratar o número como sequência de bits arbitrária (máscara, hash, extração de campo). Em .NET: Em C# 12, `algumInt >> k` sobre um `int` negativo sign-extende (preenche com 1s); `algumInt >>> k` faz deslocamento lógico (preenche com 0s) independentemente do sinal — usar `>>` para extrair um subcampo de bits de um valor que pode ser negativo (ex.: decompor um hash de 32 bits armazenado como `int`) produz bits de máscara incorretos nos bits altos. [CSAPP-02A-A-12, CSAPP-02A-C-8, CSAPP-03A-A-1, CSAPP-03A-B-2, CSAPP-03A-C-3] {ACORDO 3 / alta}
  - Limite: Não se aplica a tipos sem sinal (`uint`, `ulong`), onde `>>` já é sempre lógico, nem a valores garantidamente não negativos.
- **Contagem de deslocamento é mascarada módulo largura do tipo, nunca zera** — A instrução de deslocamento de hardware, para operandos de w bits, considera apenas os log2(w) bits menos significativos da quantidade de deslocamento — o deslocamento efetivo é calculado como (quantidade mod w), não truncado para zero nem tratado como erro. Em .NET: Em C#, o operando direito de `<<`/`>>`/`>>>` sobre `int`/`uint` é mascarado para os 5 bits menos significativos (mod 32) e sobre `long`/`ulong` para os 6 bits menos significativos (mod 64) pela especificação da linguagem — `1 << 32` sobre um `int` não é `0`, é `1` (32 mod 32 = 0); código que calcula uma máscara de bit a partir de um índice que pode chegar exatamente à largura do tipo produz colisão com o bit 0 em vez do valor esperado. [CSAPP-02A-A-13, CSAPP-02A-B-6, CSAPP-02A-C-7, CSAPP-03A-B-1, CSAPP-03A-C-15] {ACORDO 3 / alta}
  - Limite: Não se aplica quando a quantidade de deslocamento é sempre garantidamente menor que a largura do tipo, o que é a prática recomendada.
- **Multiplicar em tipo largo não evita overflow se operandos são estreitos** — Os operadores aritméticos operam sobre o tipo estático dos operandos, não sobre o tipo de destino da atribuição; `int * int` é calculado inteiramente em aritmética de 32 bits módulo 2^32 (a mesma truncagem modular que o hardware aplica a inteiros de largura fixa), e só depois o resultado já truncado é convertido para `long` — o valor real já foi perdido antes da conversão. Em .NET: `int linhas = 60000, colunas = 60000; long total = linhas * colunas;` (por exemplo, ao somar o total de células de uma grade paginada) produz um `total` negativo, porque `linhas * colunas` já estourou os 32 bits do `int` antes da conversão implícita para `long`; a correção exige `(long)linhas * colunas` ou declarar um dos operandos como `long` antes de multiplicar. [CSAPP-02A-B-1, CSAPP-03A-A-2, CSAPP-03A-B-4, CSAPP-03A-C-5, CSAPP-03C-C-4] {ACORDO 3 / media}
  - Limite: Não se aplica se pelo menos um dos operandos já for `long`/`double`/`decimal` antes da primeira multiplicação, pois nesse caso a promoção numérica ocorre antes do cálculo.
- **Não confiar em exceção para detectar divisão por zero ou NaN em ponto flutuante; verificar explicitamente** — o padrão define zero com sinal (+0 e −0 são bit patterns distintos) e propaga esse sinal pela divisão, de modo que 1/+0 e 1/−0 resolvem para infinitos com sinais opostos em vez de não terem resultado definido — não existe caso "indefinido" ali para disparar uma falha de hardware. Em .NET: `1.0 / 0.0` em C# avalia para `double.PositiveInfinity` sem lançar exceção, ao contrário de `1 / 0` com operandos `int`, que lança `DivideByZeroException`; código que só se protege com `try/catch` ao redor de uma divisão nunca captura o caso de denominador zero quando os operandos são `double`/`float`, deixando `Infinity` fluir silenciosamente para o cálculo seguinte ou para a persistência. [CSAPP-02B-A-10, CSAPP-02B-A-11, CSAPP-02B-B-5, CSAPP-02B-C-7, CSAPP-02B-C-8] {ACORDO 3 / baixa}
  - Limite: não se aplica a `int`/`long`/`decimal`, onde divisão por zero sempre lança exceção.
- **Conversão float/double para int trunca em direção a zero, não arredonda** — a conversão de ponto flutuante para inteiro descarta a parte fracionária diretamente (trunca), independentemente do sinal; não existe etapa de arredondamento embutida na conversão — é um mecanismo diferente do modo de arredondamento round-to-even usado nas operações aritméticas de ponto flutuante. Em .NET: `(int)someDouble` em C# corta a parte fracionária sempre em direção a zero — `(int)1.999` vale 1 e `(int)(-1.999)` vale -1 — o que difere de `Math.Round(someDouble)` (que arredonda para o inteiro mais próximo); usar a conversão direta onde se queria arredondamento produz contagens/índices sistematicamente errados. [CSAPP-02B-A-4, CSAPP-02B-C-5, CSAPP-03A-C-6, CSAPP-03C-B-2] {ACORDO 3 / alta}
  - Limite: não se aplica se o código sempre chama `Math.Round` (ou `Convert.ToInt32`, que arredonda) antes de converter para inteiro.
- **Liberar recursos deterministicamente em vez de depender do GC** — O alocador explícito deve responder imediatamente, sem reordenar ou buferizar pedidos; já a liberação por GC é adiada e não determinística, podendo reter recursos indefinidamente. Em .NET: Use `using`/`Dispose` para `IDisposable` (ex.: `SqlConnection`, `SqlCommand`) — a devolução à pool é imediata; não confie no finalizador para liberar na hora certa. [CSAPP-09-C-16, CSAPP-09-C-6, CSAPP-10-A-4, CSAPP-10-C-9] {ACORDO 2 / media}
  - Limite: Memória puramente gerenciada não precisa de free manual — o GC cuida; a regra vale para recursos não gerenciados ou poolados.
- **Não usar swap via XOR quando endereços podem coincidir** — A troca via XOR (`a ^= b; b ^= a; a ^= b;`) depende de `a` e `b` serem armazenamentos distintos — quando são o mesmo local, cada operação lê e escreve a mesma célula, e como qualquer valor XOR ele mesmo é zero, a primeira operação já zera o conteúdo antes que as etapas seguintes possam restaurá-lo. Em .NET: Uma função `Swap(ref int a, ref int b)` implementada com XOR bit a bit, chamada com `ref lista[i]` e `ref lista[j]` onde `i == j` (índices convergindo no meio de uma reversão de array), zera o elemento em vez de deixá-lo inalterado. [CSAPP-02A-A-18, CSAPP-05-A-1, CSAPP-05-B-1] {ACORDO 2 / alta}
  - Limite: Não se aplica à troca via desconstrução de tupla do C# (`(a, b) = (b, a)`) ou via variável temporária, que funcionam corretamente mesmo com aliasing.
- **Não assumir que aritmética unchecked detecta/impede overflow por padrão** — A flag de overflow (OF) do processador é calculada a cada soma/subtração em complemento de dois, mas nenhuma instrução subsequente desvia automaticamente quando OF é ligada — é preciso testar essa flag explicitamente para reagir a ela. Em .NET: O contexto padrão do C# é `unchecked`; `int.MaxValue + 1` vira `int.MinValue` sem exceção, a menos que o código esteja em bloco `checked` ou o projeto tenha `CheckForOverflowUnderflow` habilitado. [CSAPP-02A-C-3, CSAPP-03A-B-3, CSAPP-03A-C-2] {ACORDO 2 / alta}
  - Limite: Não se aplica a `decimal` (sempre lança `OverflowException`) nem a código já em bloco `checked`.
- **Parenteizar explicitamente cast+deslocamento em aritmética de ponteiros** — O cast de tipo tem precedência maior que a soma, então `(T*) p + n` primeiro reinterpreta `p` como `T*` e só depois soma `n` elementos de tamanho `sizeof(T)`, enquanto `(T*) (p + n)` soma `n` unidades do tipo original de `p` antes de reinterpretar — duas operações com resultados numericamente diferentes que parecem a mesma expressão. Em .NET: Em C# `unsafe`, dado `byte* p`, a expressão `(int*)p + 3` aponta 12 bytes à frente (3 ints), enquanto `(int*)(p + 3)` aponta apenas 3 bytes à frente antes de reinterpretar; um parser de protocolo binário que escreve `(int*)buffer + fieldIndex` pensando em "avançar fieldIndex bytes e ler como int" lê do lugar errado. [CSAPP-02A-B-7, CSAPP-03B-B-4, CSAPP-03B-C-13] {ACORDO 2 / alta}
  - Limite: Não se aplica quando cast e ponteiro base já são do mesmo tipo (não há reinterpretação de escala envolvida).
- **Validar comprimento de entrada antes de escrever em stackalloc/buffer nativo** — `stackalloc` e a escrita via ponteiro bruto ocorrem fora da checagem de limites que o CLR normalmente aplica a arrays e `Span<T>` indexado; a partir do momento em que se usa aritmética de ponteiro manual, a máquina volta a escrever byte a byte sem saber onde o buffer termina, exatamente como o `gets()` clássico. Em .NET: Um parser de protocolo "de alta performance" que faz `Span<byte> buf = stackalloc byte[4];` e depois escreve `len` bytes nele via ponteiro bruto (`Unsafe.Add`/loop manual) sem checar `len <= 4`, quando `len` vem de um cabeçalho de mensagem controlado pelo remetente, sobrescreve memória adjacente na pilha da mesma forma que o `gets()` do capítulo sobrescrevia registradores salvos. [CSAPP-03B-A-1, CSAPP-03B-B-12, CSAPP-03B-C-6] {ACORDO 3 / media}
  - Limite: Não se aplica a escrita através de indexador de `Span<T>`/`Array` normal, que sempre verifica limites e lança exceção em vez de corromper memória.
- **O mínimo de um tipo com sinal não tem inverso aditivo representável** — na representação em complemento de dois o bit de sinal tem peso −2^(w−1) e o intervalo é assimétrico: existe um negativo a mais que positivos, então negar o mínimo não cabe no tipo. Em .NET: `unchecked { -min }` devolve o próprio `int.MinValue` silenciosamente e `checked { -min }` lança `OverflowException`. **Para `Math.Abs`, veja o item com EVIDENCIA no topo deste arquivo — o comportamento é diferente do da negação unária.** [CSAPP-02A-A-4, CSAPP-02A-B-3, CSAPP-02A-C-5] {ACORDO 3 / media / corrigido pelo red team: a versão original afirmava que `Math.Abs(int.MinValue)` em `unchecked` devolve `int.MinValue`, o que é falso}
  - Limite: Não se aplica a tipos sem sinal (`uint`, `ulong`), nem a `long`/`int` quando o valor de entrada nunca pode ser o mínimo do tipo (validado por contrato).
- **Garantir alinhamento explícito para SIMD aligned load/store** — Diferente do acesso comum a memória (que o IA32 tolera mesmo desalinhado, só com perda de desempenho), certas instruções vetoriais operam em blocos de 16 bytes e exigem que o endereço seja múltiplo de 16; a checagem de alinhamento é feita pelo próprio hardware, e a violação não gera um resultado errado silencioso, gera uma exceção de acesso à memória. Em .NET: Código de alto throughput que usa `System.Runtime.Intrinsics.X86.Sse2.LoadAlignedVector128` (ou `Avx.LoadAlignedVector256`) sobre um ponteiro obtido de `Marshal.AllocHGlobal` ou de um `stackalloc` sem arredondar o endereço para o múltiplo exigido falha com `AccessViolationException` (não capturável em .NET moderno, derruba o processo) mesmo que o restante do código pareça correto e passe em testes com buffers "que deram certo por acaso". [CSAPP-03B-A-12, CSAPP-03B-B-2, CSAPP-03B-C-16] {ACORDO 3 / media}
  - Limite: Não se aplica ao código gerenciado comum (arrays do CLR, `Span<T>` sem intrínsecos), nem às variantes "unaligned" das intrínsecas, que toleram qualquer endereço.
- **Envolver conversão float/double->int em checked quando valor pode exceder faixa** — quando o valor truncado não cabe em nenhum inteiro representável, não existe resultado numericamente correto para devolver; o padrão não fixa um comportamento único para esse caso — o hardware simplesmente produz um bit pattern de "indefinido" (no caso de processadores Intel, o menor inteiro negativo) em vez de sinalizar erro, transformando um valor positivo enorme em um número negativo sem aviso. Em .NET: em C#, uma conversão `(int)algumDouble` fora de faixa em contexto `unchecked` (o padrão) produz um valor não especificado pela linguagem, sem lançar exceção; somente envolver a conversão em `checked { ... }` faz o runtime lançar `OverflowException` de forma determinística quando o valor está fora da faixa de `int`. [CSAPP-02B-A-5, CSAPP-02B-B-7, CSAPP-02B-C-6] {ACORDO 3 / media}
  - Limite: não se aplica dentro de um bloco/contexto `checked`, onde o overflow lança `OverflowException` em vez de produzir um valor indefinido.
- **Tratar recursão sem condição de parada comprovada como erro fatal e limitar profundidade** — A pilha de execução é uma região fixa e finita de memória, e qualquer posição além do topo atual é considerada inválida — não existe checagem de hardware "suave" nesse limite; quando a região reservada se esgota, a violação de acesso ocorre no meio da própria maquinaria que trataria uma exceção normal, então não há como desenrolar a pilha com segurança quando ela mesma já estourou. Em .NET: `StackOverflowException` do CLR é, por design, não capturável por nenhum `try`/`catch` — o processo é encerrado diretamente, porque, ao atingir o limite da pilha reservada, o runtime não tem mais espaço garantido para executar o mecanismo de tratamento de exceções. [CSAPP-03A-A-10, CSAPP-03B-A-2, CSAPP-03B-B-5] {ACORDO 2 / alta}
  - Limite: não se aplica quando a recursão tem profundidade comprovadamente limitada por uma condição de parada sempre alcançável antes de esgotar a pilha disponível.
- **Zerar memória não gerenciada antes de ler** — Páginas anônimas são demand-zero (o kernel grava zeros no primeiro toque), por isso regiões como .bss nascem zeradas; malloc/allocators, porém, devolvem blocos sem garantia de conteúdo — diferentemente de memória que o runtime zera. Em .NET: new byte[n] e GC.AllocateArray saem zeros; NativeMemory.Alloc, stackalloc e Marshal.AllocHGlobal devolvem bytes com valor residual. [CSAPP-03C-B-4, CSAPP-09-A-2, CSAPP-09-B-6] {ACORDO 2 / media}
  - Limite: Rotina que grava todos os bytes antes de qualquer leitura — zerar antes é redundante.
- **Proteger incremento/atualização de estado compartilhado com lock** — Um incremento é uma sequência de carregar, atualizar e gravar que pode se entrelaçar com a mesma sequência de outro fluxo, perdendo uma atualização. Em .NET: Em C# 12, proteja `++_contador` compartilhado com `lock` ou use uma operação atômica; declarar o campo `volatile` não torna a sequência de incremento indivisível. [CSAPP-12-A-6, CSAPP-12-B-1, CSAPP-12-B-2] {ACORDO 2 / media}
  - Limite: Nenhum conhecido quando cada fluxo possui sua própria instância do contador.
- **Manter buffer alugado vivo até consumidor terminar** — Liberar ou reutilizar a memória logo após iniciar o consumidor cria uma corrida entre a leitura dele e a próxima gravação nessa mesma região. Em .NET: Não devolva um `byte[]` ao `ArrayPool<byte>` depois de iniciar uma `Task` que ainda o lê; faça o consumidor devolvê-lo após terminar ou copie os dados antes. [CSAPP-09-B-8, CSAPP-09-C-15, CSAPP-12-B-4] {ACORDO 2 / media}
  - Limite: Nenhum conhecido quando o trabalho recebe uma cópia privada dos dados.
- **Repetir leitura até completar bytes pedidos** — Uma chamada read devolve apenas o número de bytes realmente movidos naquele instante; sockets, terminais e pipes entregam menos que o pedido por buffering interno e atrasos, sem que isso seja erro. Só o retorno 0 sinaliza fim de arquivo; devolução curta não é falha. Em .NET: Stream.Read mantém o contrato de poder retornar menos bytes que o tamanho do buffer; NetworkStream encurta sob latência. Use Stream.ReadExactly/ReadAtLeast ou um laço até completar, em vez de assumir buffer cheio. [CSAPP-10-A-1, CSAPP-10-B-8, CSAPP-10-C-3] {ACORDO 3 / baixa}
  - Limite: FileStream em disco local regular quase sempre devolve o pedido completo (fora do fim de arquivo); a exigência é crítica para rede.
- **Detectar fim de fluxo pelo retorno zero da leitura** — Não existe byte de fim de arquivo gravado no fim; o kernel reporta fim devolvendo 0 quando a posição passa do tamanho. Um byte 0x00 no meio é dado legítimo, não terminador. Em .NET: Stream.Read devolve 0 no fim, ReadByte devolve -1 e StreamReader.ReadLine devolve null. Tratar byte zero como terminador trunca arquivos binários. [CSAPP-10-A-2, CSAPP-10-C-1, CSAPP-10-C-2] {ACORDO 2 / media}
- **Preservar desvio de controle ao traduzir condicional com efeito colateral/exceção; calcular ambos os lados e selecionar apenas em laço quente imprevisível sem efeitos colaterais** — Uma transferência condicional de dados só é uma tradução válida de uma expressão condicional quando calcular os dois resultados possíveis incondicionalmente é seguro; compilar `ponteiro ? *ponteiro : 0` dessa forma dereferencia o ponteiro mesmo quando o teste falha, causando uma falha de acesso que o código original nunca teria — por isso o operador ternário do C# é definido para avaliar só o ramo escolhido, exatamente a garantia que uma tradução ingênua para código sem desvio quebraria. Em .NET: O operador `?:` do C# tem curto-circuito garantido pela especificação da linguagem (só o ramo escolhido é avaliado); reescrever manualmente essa lógica como "calcule os dois, depois selecione" para tentar forçar código sem desvio reintroduz o mesmo risco de null-dereference/exceção incondicional. [CSAPP-03A-A-8, CSAPP-03A-B-8, CSAPP-05-C-6] {ACORDO 3 / baixa}
  - Limite: não se aplica quando ambos os ramos são comprovadamente livres de efeito colateral e não podem lançar exceção — nesse caso o JIT pode legitimamente gerar código sem desvio.
- **Usar extensão de sinal vs zero corretamente ao alargar tipos** — Expandir um número preservando seu valor exige replicar, nos bits novos de alta ordem, o que o bit mais significativo original representava: para complemento de dois isso é o próprio bit de sinal repetido; para representação sem sinal isso é sempre zero, porque não existe bit de sinal a preservar. Em .NET: Reinterpretar um `Span<byte>` como `sbyte` e depois atribuir a `int` sign-extende (um byte `0xFF` interpretado como `sbyte` vira `-1` e depois `int -1`), enquanto reinterpretar o mesmo byte como `byte` e atribuir a `int` zero-extende (`0xFF` vira `255`) — usar `MemoryMarshal.Cast<byte, sbyte>` onde o protocolo espera valores sem sinal (ou vice-versa) inverte silenciosamente o sinal de todo valor acima de 127. [CSAPP-02A-A-7, CSAPP-03A-C-4] {ACORDO 2 / alta}
  - Limite: Não se aplica a valores sempre menores que 128 (bit de sinal sempre 0), onde extensão de sinal e de zero produzem o mesmo resultado.
- **Usar && e || em vez de &/| para curto-circuito em condições** — Operadores lógicos avaliam o segundo operando apenas quando o primeiro não é suficiente para determinar o resultado; operadores bit a bit sempre avaliam e combinam os dois operandos, sem noção de "parar cedo" — a diferença não é só de performance, é de quais efeitos colaterais (incluindo exceções) chegam a ser executados. Em .NET: `objeto != null && objeto.Propriedade > 0` nunca acessa `objeto.Propriedade` quando `objeto` é `null`; a versão com `&` é sintaticamente válida em C# (bool aceita `&`/`|`) mas avalia sempre os dois lados, lançando `NullReferenceException` quando `objeto` é `null`. [CSAPP-02A-A-14, CSAPP-02A-C-12] {ACORDO 2 / alta}

  - Limite: Não se aplica quando a contagem já é `int`/`long` com sinal (como `Array.Length`/`List<T>.Count` no .NET, que nunca são negativos por invariante e permitem `length - 1` com segurança mesmo em zero).
- **Envolver cast estreitando inteiros em contexto checked** — Truncar um número de w bits para k bits equivale a calcular o valor módulo 2^k e reinterpretar o padrão de bits resultante como o tipo menor; se o bit mais significativo do resultado truncado virar 1, o valor muda de sinal, e nenhum mecanismo desse processo sinaliza a perda de dados por padrão. Em .NET: Um `int` calculado (soma de itens de um pedido) convertido com `(short)valor` para gravar numa propriedade `short` mapeada para `smallint` pelo EF Core trunca silenciosamente quando o valor ultrapassa 32.767, podendo até virar negativo; fora de um bloco `checked(...)` a conversão nunca lança exceção. [CSAPP-02A-B-2] {ACORDO 1 / alta}
  - Limite: Não se aplica quando o valor de origem está comprovadamente dentro do intervalo do tipo destino, ou quando a conversão já ocorre dentro de um contexto `checked`.
- **Não usar >> para extrair bits altos esperando zeros em valores possivelmente negativos** — Em C#, `>>` sobre um tipo com sinal realiza deslocamento aritmético, repetindo o bit de sinal nas posições liberadas à esquerda; só tipos sem sinal (`uint`/`ulong`) ou o operador `>>>` garantem deslocamento lógico preenchido com zeros. Em .NET: Extrair o byte alto de um `int` empacotado (chave composta shard+sequência) com `int alto = valorEmpacotado >> 24;` devolve bits 1 à esquerda quando `valorEmpacotado` é negativo, corrompendo o campo extraído; a correção é `valorEmpacotado >>> 24` ou converter para `uint` antes de deslocar. [CSAPP-02A-B-5] {ACORDO 1 / alta}
  - Limite: Não se aplica quando o operando já é `uint`/`ulong`, nem quando se sabe que o bit mais significativo do valor nunca estará ligado.
- **Usar teste de overflow apenas para tipos sem sinal, não para signed** — em adição não sinalizada modular, overflow implica exatamente que a soma truncada é menor que qualquer um dos operandos (s = x+y-2^w), então s<x é necessário e suficiente (Eq. 2.11); em complemento de dois, overflow pode empurrar o resultado tanto para positivo quanto para negativo dependendo dos sinais dos operandos (Eq. 2.14 define quatro casos distintos), então não existe uma única desigualdade equivalente. Em .NET: `bool overflow = unchecked(x + y) < x;` é um teste correto e sem alocação para `uint x, y`, útil em caminhos quentes que evitam o custo de um bloco `checked`; aplicar a mesma expressão a `int x, y` produz diagnósticos errados de overflow. [CSAPP-02A-C-4] {ACORDO 1 / alta}
  - Limite: só vale para adição sem sinal; para `int`/`long`, x=int.MinValue e y=int.MinValue somam (unchecked) 0, e 0<x é falso mesmo havendo overflow negativo real — o teste falha exatamente no caso que deveria detectar.
## Performance

- **Percorrer array retangular na ordem row-major (linha externa, coluna interna)** — o capítulo mostra explicitamente que acessar B[0][k], B[1][k], ... (variando a linha, "andando" pela coluna) força acessos espaçados 64 bytes entre si, enquanto acessar os elementos de uma mesma linha (Arow[j]) é sequencial — a ordem de armazenamento "row major" só é contígua ao longo da última dimensão. Em .NET: em um `T[,]` do .NET (também row-major), um laço `for j for i matriz[i,j]` (variando a linha mais rápido) salta `NumCols * sizeof(T)` bytes a cada iteração, gerando um cache miss por acesso; o laço `for i for j matriz[i,j]` acessa endereços consecutivos, aproveitando a linha de cache já carregada. [CSAPP-03B-C-11, CSAPP-06-A-2, CSAPP-06-A-3, CSAPP-06-B-1, CSAPP-06-B-3, CSAPP-06-C-1 +1] {ACORDO 3 / media}
  - Limite: só se aplica a `T[,]` (armazenamento contíguo garantido); não vale para `T[][]` irregular, onde cada linha é uma alocação separada e não há garantia de que linhas fiquem próximas na memória, então a ordem de percurso por linha não traz o mesmo benefício determinístico.
- **Usar estruturas contíguas em vez de encadeadas em iteração quente** — O prefetcher de hardware identifica padrões sequenciais e busca blocos à frente; o memory mountain mostra um platô alto para strides 1–2 que cai conforme o stride cresce — ponteiros espalhados não dão endereço contíguo para prefetchar. Em .NET: Iterar `List<T>`/`T[]` em ordem deixa o CPU buscar os próximos elementos antes do uso; `LinkedList<T>` exige seguir ponteiros por toda a memória, sem localidade espacial, e cada elemento pode custar um miss. [CSAPP-05-A-7, CSAPP-06-B-9, CSAPP-06-C-12, CSAPP-09-B-10, CSAPP-09-C-3] {ACORDO 3 / media}
  - Limite: Não se aplica a coleções pequenas que cabem na cache, nem quando inserção/remoção no meio domina o padrão de uso — aí a estrutura encadeada tem outra razão que não a varredura.
- **Ordenar/alinhar campos de struct para minimizar padding** — O alocador arredonda e preenche para satisfazer o alinhamento, e o tamanho mínimo do bloco nasce de header mais alinhamento; padding desperdiça bytes por instância. Em .NET: Em `struct`/`[StructLayout]`, ordenar campos do maior para o menor reduz padding; um `struct { byte; int; byte; }` ocupa 12 bytes em vez de 6 compactados. [CSAPP-03B-A-4, CSAPP-03C-B-3, CSAPP-09-C-13] {ACORDO 3 / media}
  - Limite: Tipos de referência (heap) e structs raras não justificam otimizar; `Pack` para interop muda o alinhamento e pode ferir o acesso.
- **Compartilhar dados entre processos via arquivo mapeado em memória** — Mapear um objeto como shared aponta as PTEs dos processos para as mesmas páginas físicas; escritas ficam visíveis aos outros mapeamentos e refletidas no arquivo, sem cópia nem serialização intermediária. Em .NET: MemoryMappedFile.CreateFromFile/CreateNew (nomeado) compartilha um bloco entre processos .NET 8 sem IPC de cópia. [CSAPP-09-A-1, CSAPP-09-A-7, CSAPP-09-B-4] {ACORDO 2 / alta}
  - Limite: Dados que exigem coerência transacional forte ou serialização de tipos complexos — o mapeamento é bruto.
- **Evitar leitura síncrona bloqueante em loop de eventos** — Um cliente que transmite apenas parte de uma linha faz a leitura bloqueante esperar o restante, impedindo transições dos demais fluxos no único loop. Em .NET: Em um loop de Socket.Select, acumule bytes disponíveis no ConnectionState em vez de chamar StreamReader.ReadLine de forma síncrona. [CSAPP-06-A-12, CSAPP-06-B-11, CSAPP-12-A-4] {ACORDO 2 / media}
  - Limite: Não se aplica quando cada conexão possui trabalhador próprio que pode bloquear sem reter o agendador comum.
- **Não presumir custo constante de switch/if dependendo de densidade/padrão de dados** — O compilador só constrói uma tabela de saltos (um array de endereços de código indexado diretamente pelo valor testado) quando os valores dos `case` cobrem uma faixa pequena e razoavelmente contígua; fora dessa condição, o ganho de indexar diretamente no array desaparece e o compilador gera uma cadeia de comparações sequenciais, cujo custo cresce com o número de casos testados até encontrar o correspondente. Em .NET: Um `switch` do C# sobre valores inteiros esparsos ou muito espalhados (em vez de uma faixa pequena e contígua) não recebe despacho de tabela de saltos e se comporta, em custo, como uma sequência de comparações — diferente de um `switch` sobre uma faixa densa, que se aproxima de custo constante independentemente de qual `case` é o correto. [CSAPP-03A-A-12, CSAPP-03A-A-7, CSAPP-03A-B-13] {ACORDO 2 / media}
  - Limite: não se aplica a `switch` sobre `string` (tratado via tabela de hash, não indexação direta), nem a `switch` com poucos casos, que compila para comparação sequencial de qualquer forma.
- **Favorecer acessos sequenciais e agrupar campos quentes de struct para aproveitar prefetcher e cache** — O mecanismo de prefetch identifica padrões de referência e antecipa o trazer de blocos antes do acesso; ele funciona melhor para stride 1–2, onde consegue manter o ritmo do loop, e perde efetividade quando o passo cresce além do tamanho do bloco. Em .NET: Em C#, varreduras lineares de `Span<T>`/array sustentam vazão quase constante mesmo quando o buffer excede o cache, porque o prefetcher acompanha; o mesmo loop com stride saltado cai para a vazão de misses síncronos. [CSAPP-06-A-14, CSAPP-06-B-8, CSAPP-06-C-4] {ACORDO 3 / media}
  - Limite: Em saltos grandes (≥ tamanho de bloco) ou acessos imprevisíveis (pointer-chasing), o prefetcher não ajuda.
- **Mover computação invariante para fora do laço** — O compilador não move chamadas de função porque não pode provar a ausência de efeitos colaterais; se o custo da chamada é proporcional ao tamanho da entrada e ela é executada a cada iteração, o custo total vira o produto dos dois — quadrático (em C, `strlen` O(n) chamado n vezes adiciona n² passos ao invés de n). Em .NET: `Enumerable.Count()` sobre um `IEnumerable` re-enumera a sequência inteira a cada chamada (O(n)); usá-la como condição de um `for` (ou no corpo, sobre a mesma coleção) transforma um laço linear em O(n²). `List<T>.Count` e `array.Length` são O(1) e não sofrem disso. [CSAPP-05-A-3, CSAPP-05-B-3] {ACORDO 2 / alta}
  - Limite: Coleções cujo `Count` é O(1) (`List<T>`, arrays) e chamadas já invariantes por natureza; não se aplica quando o tamanho precisa ser reconsultado porque a coleção muda dentro do laço.
- **Acumular em variável local e gravar na memória só ao final (evitar write→read no loop)** — Gravar no destino e relê-lo toda iteração é trabalho desnecessário (2 leituras + 1 escrita); manter o acumulador em registrador reduz a 1 leitura e melhorou o CPE em ≥2,4×. Em .NET: Em C#, `acc += x; destino = acc;` a cada iteração (ou acumular direto em `obj.Campo`, `soma[0] += x`, `entidade.Propriedade += x` num EF Core tracked) impõe load+store por iteração; segurar numa variável local deixa o valor em registrador e grava uma vez. [CSAPP-05-B-12, CSAPP-05-B-4] {ACORDO 1 / alta}
  - Limite: Quando a posição de destino é observável/alias de uma entrada (a versão "otimizada" muda o resultado quando `dest` aponta para um elemento sendo combinado); nesse caso a leitura-escrita por iteração é semântica, não só desperdício.
- **Vetorizar loops elemento a elemento com SIMD** — Uma instrução SIMD soma/multiplica 4 valores single (ou 2 double) de uma vez num registrador; SIMD + unroll 8× atingiu CPE ~0,25 (float) e ~0,50 (double), o teto de throughput do hardware. Em .NET: Em C# 12, use `System.Numerics.Vector<T>`/`Vector256<T>` (ou intrinsics `Avx2`) sobre `Span<T>` para somar/multiplicar arrays; é o mesmo SIMD do x86-64, e um loop escalar de `float[]` deixa 4× na mesa. Lembre: a redução SIMD é pairwise e muda o arredondamento FP (ver item de não-associatividade). [CSAPP-05-A-15, CSAPP-05-B-17] {ACORDO 2 / media}
  - Limite: Quando há dependência serial inter-elemento (o próximo depende do anterior) ou o acesso não é contíguo; aí a vetorização não se aplica.
- **Passar structs grandes por in em métodos frequentes** — o capítulo recomenda explicitamente passar um ponteiro para a struct (como no exemplo `area(struct rect *rp)`) em vez de copiá-la, porque copiar todos os bytes da struct para o frame da procedure chamada tem custo proporcional ao tamanho da struct, enquanto passar um ponteiro custa um único registrador. Em .NET: um parâmetro `in MinhaStructGrande` (C# 12) evita copiar a struct inteira para cada chamada, análogo a receber o ponteiro do exemplo do capítulo; sem `in`, cada chamada do método copia todos os bytes da struct para o frame da chamada. [CSAPP-03B-C-9, CSAPP-03C-B-6] {ACORDO 2 / media}
  - Limite: para structs pequenas (até ~16 bytes, 1–2 palavras de máquina) copiar por valor é mais barato que a indireção de passar por referência; usar `in` nesse caso pode até piorar, invertendo o conselho — o ganho só aparece a partir de structs maiores que não cabem em poucos registradores.
- **Adiar leitura/cópia de dados até primeiro acesso real** — A paginação por demanda só traz a página quando a CPU a toca; o loader nunca copia antecipadamente, então materializar tudo antes paga IO desnecessário. Em .NET: Use `IQueryable` com execução adiada e streaming (`AsNoTracking` com iteração) em vez de materializar a tabela inteira com `ToList()`; leia com `SqlDataReader.ReadAsync` linha a linha. [CSAPP-09-C-11, CSAPP-09-C-2] {ACORDO 1 / media}
  - Limite: Se o conjunto exige acesso aleatório ou reprocessamento repetido, materializar tudo de uma vez pode ser mais barato; conjuntos pequenos não justificam o cuidado.
- **Ler stream em blocos grandes com buffer em vez de byte a byte** — Cada chamada de leitura dispara uma operação cara de sistema (trap ao kernel); ler 1 byte por chamada multiplica esse custo por byte, como o programa que chama `Read` de 1 byte num loop. Em .NET: `Stream.ReadByte()` em `NetworkStream` (que não tem buffer interno) vira uma chamada por byte (array de 1 elemento + read); em `FileStream` o mesmo loop é barato porque ele bufferiza — o código "funciona" no arquivo e colapsa no socket. Prefira `StreamReader`, `BufferedStream` ou `Read` de blocos grandes. [CSAPP-10-B-6, CSAPP-10-B-7] {ACORDO 1 / media}
  - Limite: `FileStream.ReadByte` e streams já bufferizados (`StreamReader`, `BufferedStream`) não sofrem; o custo por byte atinge streams crus sem buffer (`NetworkStream`/sockets).
- **Preferir array jagged a retangular em loops quentes** — acessar um elemento de uma matriz cujo número de colunas só é conhecido em tempo de execução exige uma multiplicação inteira a cada acesso para calcular o deslocamento da linha; quando o número de colunas é constante em tempo de compilação, essa multiplicação pode ser trocada por deslocamentos e somas mais baratos — um array jagged expõe cada linha como referência direta, evitando a multiplicação por completo. Em .NET: `int[,]` sempre calcula o índice de acesso com multiplicação em tempo de execução (as dimensões não são constantes para o JIT), enquanto `int[][]` acessa cada linha por referência e soma apenas o índice de coluna — em laços quentes sobre matrizes grandes, essa diferença de custo por acesso é mensurável. [CSAPP-03B-A-7, CSAPP-03B-B-13] {ACORDO 2 / media}
  - Limite: não se aplica a matrizes pequenas ou laços com trabalho por iteração muito maior que o custo do acesso, onde a diferença fica imensurável.
- **Usar estilo funcional (seleção de valor) em branch imprevisível** — Um misprediction custa dezenas de ciclos (44 no Core i7) e dado aleatório causa ~50% de erro; o estilo funcional vira transferência condicional de valor sem desvio, com CPE estável (minmax2 ~5 em qualquer dado contra ~14,5 de minmax1 em dado aleatório). Em .NET: Em C#, use ternário/computação de valor (`var t = a[i] < b[i] ? a[i] : b[i]`, `Math.Min/Max`) em vez de `if (a[i] > b[i]) { troca }` para escolha por elemento com dado imprevisível; o RyuJIT pode emitir `cmov` para ternários simples. [CSAPP-05-A-6, CSAPP-05-B-8] {ACORDO 2 / baixa}
  - Limite: Quando o branch é previsível (padrão regular, como `i < n`), o custo é ~nulo e o estilo não importa; ou quando avaliar ambos os lados é caro/tem efeito colateral que não deve ser executado.
- **Meça com profiler dados realistas antes de otimizar** — O gargalo real frequentemente não é o esperado — no exemplo do capítulo supôs-se que a recursão era o custo, quando na verdade era a posição de inserção na lista encadeada — e perfis sobre dados pequenos/não-representativos escondem o comportamento assintótico; otimizar sem medir costuma mirar a parte errada. Em .NET: Use `dotnet-trace`/`dotnet-counters`/BenchmarkDotNet e planos de execução SQL (ou `LogTo` no EF Core) para medir o tempo por componente antes de reescrever; a ordem de grandeza de qual trecho domina o tempo é o que decide o alvo. [CSAPP-05-A-11, CSAPP-05-B-14] {ACORDO 2 / alta}
  - Limite: Não se aplica a correção de bugs funcionais, apenas a decisões de desempenho; perfis valem para os dados testados e devem ser repetidos sobre carga representativa.
- **Evitar intercalar criação/liberação de objetos grandes por fragmentação** — fragmentação externa ocorre quando há memória livre agregada suficiente mas nenhum bloco livre único grande o bastante; blocos livres vizinhos podem estar separados por blocos alocados ainda vivos. Em .NET: o Large Object Heap não compacta por padrão, então alternar alocar e liberar `byte[]` de tamanhos mistos deixa buracos e um `byte[100MB]` subsequente pode dar `OutOfMemoryException` mesmo com centenas de MB "livres"; a fragmentação de heap/índice por page splits no SQL Server é a mesma ideia. [CSAPP-09-B-5, CSAPP-09-C-9] {ACORDO 2 / baixa}
  - Limite: cargas com tamanhos uniformes, ou quando o GC compacta via `GCSettings.LargeObjectHeapCompactionMode`.
- **Não chamar método virtual/interface/delegado não provável em loop quente** — O compilador raramente prova que uma função é pura; `f()+f()+f()+f()` não pode virar `4*f()` porque `f` pode ter efeito colateral (`counter++`) e mudar o número de chamadas muda o comportamento. Em .NET: Em C# 12, chamadas a membros de interface ou virtuais (um acessor em `IReadOnlyList<T>`, um `IComparer<T>.Compare`, uma propriedade trackeada de entidade EF Core) dentro do loop pagam dispatch e bloqueiam inlining ao redor; um campo/propriedade simples é barato, a chamada de interface por elemento não. [CSAPP-05-A-16, CSAPP-05-B-2] {ACORDO 2 / media}
  - Limite: Quando o call-site é genérico e o tipo concreto é um `struct` (RyuJIT pode desvirtualizar, sobretudo com PGO), ou o método é estável e inlinável; ou fora de caminho crítico.
- **Desconfiar de tamanhos potência de 2 em acesso paralelo a buffers (conflito de cache)** — Em caches de mapeamento direto (ou poucas vias), o índice do conjunto sai dos bits do meio do endereço; dois arrays separados por um múltiplo potência-de-2 do tamanho do conjunto mapeiam para os mesmos conjuntos e se despejam mutuamente a cada iteração (thrashing), mesmo sobrando espaço no cache. Em .NET: Em C#, dois `double[]` ou dois `struct[]` de tamanho potência de 2 acessados em lockstep (ex.: `x[i]*y[i]` num produto escalar) podem sofrer thrash se o alinhamento do heap os colocar na mesma distância de conjunto; o sintoma é um slowdown de 2–3x num loop de localidade aparentemente boa. [CSAPP-06-A-6, CSAPP-06-A-7] {ACORDO 1 / media}
  - Limite: Em caches bem associativas (L3 de 16 vias, por exemplo) o efeito diminui; também depende do alinhamento de alocação, difícil de prever.
- **Não substituir multiplicação por constante por deslocamentos manuais** — Multiplicação por hardware é mais lenta que deslocamento e soma, então compiladores já reescrevem multiplicações por constantes conhecidas em tempo de compilação como combinações de `<<` e `+`/`-` automaticamente (ex.: `x*14` vira `(x<<3)+(x<<2)+(x<<1)` ou `(x<<4)-(x<<1)`) — o dev não precisa nem deveria fazer essa transformação manualmente no código-fonte. Em .NET: O JIT (RyuJIT) do .NET 8 aplica redução de força equivalente para multiplicações por constantes conhecidas em tempo de compilação; reescrever `contador * 4` como `contador << 2` manualmente no C# não produz código de máquina mais rápido, só piora a legibilidade e obscurece a intenção para quem revisa o código depois. [CSAPP-02A-A-21, CSAPP-03A-B-12] {ACORDO 2 / media}
  - Limite: Não se aplica quando a constante multiplicadora não é conhecida em tempo de compilação (é uma variável em tempo de execução), caso em que o JIT não pode aplicar essa transformação.
- **Limitar paralelismo de trabalho CPU-bound ao número de núcleos** — Depois que cada núcleo já executa um thread, workers adicionais disputam o mesmo núcleo e acrescentam trocas de contexto. Em .NET: Para uma etapa CPU-bound no .NET 8, configure ParallelOptions.MaxDegreeOfParallelism com Environment.ProcessorCount como ponto de partida; acima desse ponto a latência pode aumentar em vez de reduzir. [CSAPP-12-B-19, CSAPP-12-C-16] {ACORDO 2 / media}
  - Limite: Não se aplica a trabalho predominantemente bloqueado em E/S, no qual workers extras podem sobrepor esperas.
- **Usar teste manual de sinais em vez de checked/try-catch em loop quente** — a fórmula de overflow do capítulo — sinal de a igual ao sinal de b, mas sinal do resultado diferente de a — é exatamente o teste que o hardware calcula na flag OF a cada `add`; reproduzir essa fórmula em C# é uma comparação e um XOR de bits, enquanto lançar/capturar exceção no .NET envolve captura de stack trace e desenrolamento de pilha, ordens de magnitude mais caro que um branch. Em .NET: `checked { a + b }` dentro de `try/catch` lança `OverflowException` quando estoura, e lançar/capturar exceções em .NET custa microssegundos; num laço que processa milhões de somas com estouro frequente, o custo agregado de exceções pode dominar o tempo total, enquanto testar `(a < 0) == (b < 0) && (resultado < 0) != (a < 0)` manualmente é um punhado de instruções de CPU sem custo de exceção. [CSAPP-03A-C-14] {ACORDO 1 / alta}
  - Limite: só compensa quando o estouro é medido como frequente o bastante para o custo de exceção dominar (perfilar antes de aplicar); para overflow raro/excepcional, `checked`/exceção é mais simples e seguro de manter. A fórmula manual aqui detecta overflow de adição; subtração e multiplicação têm fórmulas diferentes, não reutilizáveis diretamente.
- **Preferir array irregular a retangular quando índice não é constante em tempo de compilação** — o capítulo mostra que o endereço de um elemento de array de tamanho variável exige uma multiplicação em tempo de execução (xA + L*(n*i+j)) — descrita como "uma penalidade de desempenho significativa, mas inevitável" — enquanto arrays irregulares acessam cada linha por um único ponteiro/deref, sem multiplicação de stride. Em .NET: acessar `matriz[i,j]` em um `T[,]` do .NET calcula o offset com uma multiplicação pelo comprimento da linha (mais uma checagem de limites por dimensão) a cada acesso; `matriz[i][j]` em um `T[][]` acessa a linha por referência direta e depois indexa um array unidimensional simples, evitando a multiplicação. [CSAPP-03B-C-10] {ACORDO 1 / alta}
  - Limite: não compensa a reescrita quando o array é pequeno, acessado poucas vezes, ou quando a clareza/contiguidade garantida de `T[,]` (uma única alocação, sem risco de linhas de tamanhos diferentes) é mais importante que o ganho de desempenho.
- **Permitir reordenação/paralelização de agregação de inteiros mas não de float/double** — A aritmética inteira é feita em dois-complemento com wrap-around; adição e multiplicação são associativas e comutativas mesmo quando o overflow ocorre, pois o resultado módulo 2^w é o mesmo em qualquer ordem de combinação. Em .NET: Em contexto `unchecked` (padrão em C#), dividir uma soma de `int`/`long` em N acumuladores, em `Parallel`/`AsParallel()` ou em `Aggregate` preserva o resultado idêntico ao laço sequencial, mesmo com overflow interno; no contexto `checked` (opção de projeto) o overflow passa a lançar e muda o contrato. [CSAPP-05-A-9] {ACORDO 1 / alta}
  - Limite: `checked` explícito (overflow lança exceção) e agregações de ponto flutuante, onde a reordenação altera o arredondamento.
- **Combinar múltiplas agregações numa única passada pela coleção** — Reusar um dado assim que ele foi lido é localidade temporal; varrer o array em duas passadas refaz toda a carga, dobrando o tráfego de memória e, se o conjunto não cabe na cache, dobrando os misses. Em .NET: Em vez de `TotalX = data.Select(d => d.X).Sum(); TotalY = data.Select(d => d.Y).Sum();` (duas varreduras), faça um único `foreach` acumulando `x += d.X; y += d.Y` para tocar cada elemento uma vez. [CSAPP-06-B-5] {ACORDO 1 / alta}
  - Limite: Quando o working set inteiro cabe na cache, a segunda passada acerta e o ganho da fusão é pequeno; tampouco compensa se os dois agregados exigirem lógica substancialmente diferente por passada.
## Manutenção

- **Limitar número de trabalhos concorrentes/capacidade de canal** — Criar um fluxo para cada cliente incorre custo de criação repetido; um conjunto preexistente de trabalhadores com buffer limitado controla esse custo e a pressão de admissão. Em .NET: Em um serviço .NET 8, limite a concorrência de processamento com um conjunto fixo de trabalhadores e uma fila limitada, em vez de iniciar uma `Task` de processamento sem limite por requisição. [CSAPP-12-A-16, CSAPP-12-A-8, CSAPP-12-B-10, CSAPP-12-C-9] {ACORDO 3 / media}
  - Limite: Não se aplica a uma carga comprovadamente limitada cujo custo por trabalho é desprezível e não se acumula.
- **Tratar nint/IntPtr como dependente da plataforma, não tamanho fixo** — o CLI fixa o tamanho de `int` (4 bytes) e `long` (8 bytes) igual em toda plataforma .NET, eliminando o problema clássico de C em que esses tamanhos variam com a palavra da máquina (Figura 2.3 do livro); mas o único tipo numérico deixado intencionalmente dependente do tamanho de palavra é o inteiro nativo/de ponteiro (`nint`, `IntPtr`), espelhando exatamente a linha `char *` da mesma figura. Em .NET: `IntPtr.Size` (ou `sizeof(nint)` em contexto `unsafe`) retorna 4 em processo 32 bits e 8 em processo 64 bits; um struct com campo `nint`/`IntPtr` serializado ou marshaled com layout fixo produz tamanho e layout diferentes conforme a arquitetura de build (x86 vs x64/ARM64). [CSAPP-02A-A-1, CSAPP-02A-C-9] {ACORDO 2 / media}
  - Limite: não vale para nenhum outro tipo numérico embutido do C#/.NET (todos os demais têm tamanho fixo em qualquer plataforma); só `nint`, `nuint`, `IntPtr`, `UIntPtr` e tipos ponteiro (`T*`) variam com a palavra.
- **Usar InlineArray em vez de campo T[] para buffer fixo embutido em struct** — um array declarado como campo dentro de uma struct de tamanho fixo ocupa espaço contíguo dentro da própria struct, no mesmo bloco de memória, endereçado por deslocamento fixo mais índice — diferente de um campo que é apenas um ponteiro para um bloco separado alocado em outro lugar. Em .NET: `[InlineArray(N)]` sobre uma struct com um único campo faz o runtime tratá-la, para fins de layout, como N elementos contíguos embutidos na própria struct — sem alocação extra e sem indireção de referência; usar um campo `T[]` comum no mesmo lugar introduz um objeto separado no heap gerenciado, com uma referência armazenada na struct em vez dos dados propriamente ditos. [CSAPP-03B-A-11, CSAPP-03B-C-5] {ACORDO 2 / alta}
  - Limite: `[InlineArray]` exige tamanho fixo conhecido em tempo de compilação; não se aplica quando o tamanho do buffer só é conhecido em tempo de execução — nesse caso a indireção via `T[]`/heap é inevitável.
- **Limitar trabalho de cada fluxo por passagem do loop de eventos** — Um loop dirigido por eventos só agenda outro fluxo após retornar ao ponto de seleção; consumir muitas unidades de um cliente adia todos os demais. Em .NET: Após Socket.Select, processe no máximo um registro disponível por conexão antes de voltar ao loop principal para manter latência entre clientes previsível. [CSAPP-12-A-3, CSAPP-12-C-3] {ACORDO 2 / media}
  - Limite: Não se aplica quando o protocolo exige terminar atomicamente a unidade inteira antes de expor qualquer outro evento.
- **Não equiparar decimal do C# a long double** — a precisão estendida do capítulo ainda é um formato binário ao estilo IEEE, apenas com mais bits de expoente/significando, enquanto decimal usa uma representação inteiramente diferente, em base 10 e escala fixa, sem infinitos nem NaN. Em .NET: `decimal` não tem equivalente a `double.PositiveInfinity`/`double.NaN`, e converter um double infinito para decimal lança `OverflowException` em vez de produzir um valor especial; decimal também tem alcance de magnitude menor (~7.9×10^28) que double (~1.8×10^308) apesar de ocupar mais bits (128 contra 64). [CSAPP-02B-C-9] {ACORDO 1 / alta}
  - Limite: nenhum dentro de C# 12/.NET 8 — a diferença de modelo (binário vs. decimal de escala fixa) sempre se aplica, pois não existe tipo long double em C#.
- **Definir posse de stream embrulhado com leaveOpen explícito** — Fechar dois fluxos sobre o mesmo descritor fecha no primeiro e falha no segundo; o capítulo diz que fechar um descritor já fechado em programa com threads "é receita para desastre". Em .NET: `StreamReader`/`StreamWriter`/`BinaryWriter` descartam o stream base no `Dispose` (default `leaveOpen: false`); embrulhar o mesmo `NetworkStream`/`FileStream` em `StreamWriter` E `StreamReader` faz o primeiro `Dispose` fechar o stream e o segundo lançar `ObjectDisposedException`. [CSAPP-10-B-5] {ACORDO 1 / alta}
  - Limite: Um único wrapper dono do stream; ou todos os wrappers com `leaveOpen: true` e o dono descartando o stream uma única vez.
- **Ao ler só parte dos campos de um array de structs, separe os campos em arrays distintos (estrutura-de-arrays) para não b** — O cache busca o bloco inteiro de 64 bytes, então tocar um campo de um struct traz também os demais campos (e os dos vizinhos) para a linha; se você só lê `.X`, parte da largura de banda é gasta arrastando `.Y`. Em .NET: Em C#, iterar `Point[]` (dois `int`s, 8 bytes) lendo só `X` traz bytes mortos por linha; um `int[] xs` separado dobra o throughput útil. O mesmo princípio desaconselha `SELECT *` em EF Core/SQL Server quando só algumas colunas são usadas: cada página de 8 KB traz colunas que nunca serão lidas. [CSAPP-06-A-5] {ACORDO 1 / alta}
  - Limite: Se todos os campos são lidos na mesma passada, a estrutura-de-arrays não traz ganho.
- **Reconhecer teto de ~2^31 elementos em coleções indexadas por int mesmo em 64 bits** — o livro liga diretamente o espaço de endereços de uma máquina ao seu tamanho de palavra w (endereços virtuais de 0 a 2^w-1, §2.1.2); o .NET em processo 64 bits não fica limitado a endereçamento de 32 bits, mas a superfície de indexação de `Array`/`List<T>` é tipada `int` de propósito, um limite mais estreito imposto por cima do espaço de endereços mais largo do hardware/SO. Em .NET: `Array.MaxLength` (constante documentada, 0x7FFFFFC7 para a maioria dos tipos de elemento) limita qualquer array de uma dimensão independentemente da RAM disponível ou do endereçamento de 64 bits; tentar `new byte[maior_que_isso]` lança `OverflowException` mesmo que o processo pudesse endereçar muito mais memória. [CSAPP-02A-C-11] {ACORDO 1 / alta}
  - Limite: não vale para `Span<T>`/múltiplos arrays menores, para `Memory<T>` composto de vários segmentos, nem para tipos que deliberadamente usam `long`/`nint` para tamanho (regiões de `Marshal.AllocHGlobal`, arquivos mapeados em memória via `MemoryMappedViewAccessor`), que podem exceder esse teto.
- **Aquecer cache/JIT antes de medir desempenho** — Uma cache vazia produz só misses compulsórios ("cold misses"), que são transitórios e não ocorrem em estado estacionário depois que o working set foi puxado para níveis superiores; a primeira execução contabiliza o custo de carga, não o custo do algoritmo. Em .NET: Em .NET 8, a primeira soma sobre um `double[]` grande paga a transferência das linhas da memória principal para L1/L2 além do JIT; a segunda soma sobre o mesmo array colhe os hits — que é o motivo de `BenchmarkDotNet` fazer warmup. [CSAPP-06-B-4] {ACORDO 1 / alta}
  - Limite: Não relevante quando o que se mede é justamente o custo de cold start do processo (ex.: partida de serviço) nem para workload que nunca reutiliza os dados.
- **Dimensionar tipo base de enum de flags pelo número real de flags** — Um vetor de bits de w bits só codifica até w elementos distintos de um conjunto (cada posição de bit representa presença/ausência de um elemento) — passado esse limite, não há mais posição de bit livre para uma nova flag sem reutilizar uma já usada. Em .NET: Um `[Flags] enum` com tipo base `int` (padrão) tem no máximo 32 valores de flag distintos representáveis como potências de dois (`1 << 0` até `1 << 31`); precisar de uma 33ª flag exige declarar o enum com `: long`/`: ulong` (até 64 flags) ou reestruturar em múltiplos campos — decidir isso cedo evita reescrever todos os usos do enum e sua persistência depois. [CSAPP-02A-A-15] {ACORDO 1 / media}
  - Limite: Não se aplica a enums de flags com poucos valores previstos e sem expectativa de crescimento além do que o `int` padrão comporta.
